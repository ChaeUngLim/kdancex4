# SCH별 에이전트용 버전 맞춤 문서 (.md) 표준

## 목적

이 프로젝트에는 SCH 하나를 설명하는 문서가 셋이다. 독자가 다르다.

| 문서 | 위치 | 독자 | 표준 |
|---|---|---|---|
| 소스 안 학습 주석 | 소스 파일 | 6개월차 비전공자 | `beginner-comment-style.md` |
| 완벽분석가이드 | `_workspace/guides/SCH-XX(기능명).html` | 6개월차 비전공자 | `sch-guide-template.md` |
| **에이전트용 문서** | **`_workspace/guides/SCH-XX(기능명).md`** | **AI 코딩 에이전트** | **이 문서** |

앞의 둘은 **모르는 독자**를 가르친다. 이 문서는 **잘못 아는 독자**를 교정한다. 그 차이가
구성 전체를 가른다.

## 왜 따로 필요한가

에이전트의 학습 데이터에는 구버전 API 가 들어 있다. 설명해 두지 않으면 우리 코드를
옛 방식으로 "고쳐" 놓는다. 실제로 이 프로젝트에서 벌어질 수 있는 일들이다.

- Prisma 8 의 계약 기반 접근을 보고 `new PrismaClient()` 로 되돌린다 (7 계열 API)
- `@prisma/orm-postgres` 를 `@prisma/client` 오타로 판단하고 고친다
- AI SDK 7 의 agent 루프를 6 의 구조로 재작성한다
- Next.js 16 App Router 코드에 15 이전 패턴을 섞는다

Next.js 16.3 이 `node_modules/next/dist/docs/` 와 `AGENTS.md` 를 깔아 주는 이유가 같다 —
**에이전트가 학습 데이터 대신 설치된 버전의 문서를 읽게 만드는 것.** 이 표준은 그 방식을
우리 소스에 적용한 것이다.

## 적용 시점 (트리거)

`beginner-comment-style.md`·`sch-guide-template.md` 와 동일하다. `_workspace/kdance.html`
에서 SCH 가 "완료"로 바뀔 때, Phase 9.5(학습 주석 재구성·SCH 가이드 생성) 안에서
**같은 호출로** 세 산출물을 함께 만든다.

## SCH 표기 규칙

`beginner-comment-style.md` 의 「SCH 표기 규칙」과 동일하다. 번호만 단독으로 쓰지 않고
`SCH-04(어댑터 3종: PG/알림/슬롯락)` 형태로 쓴다. 기능명은 `_workspace/kdance.html` 의
공식 문구를 그대로 가져온다.

## 저장 위치 / 네이밍

`_workspace/guides/SCH-{번호}({기능명}).md` — HTML 가이드와 같은 폴더, 같은 이름, 확장자만
다르다. 둘이 짝이라는 게 파일 목록만 봐도 보여야 한다.

## 필수 구성 (섹션 순서)

### 0. 머리말 — 이 문서의 성격

다섯 줄 이내. "이 문서는 사람이 아니라 에이전트가 읽는다. 학습 데이터의 API 가 아니라
아래 적힌 설치 버전의 API 를 쓴다"는 선언과 기준일.

### 1. 이 SCH 가 쓰는 스택과 정확한 버전

이 SCH 가 실제로 건드리는 패키지만 적는다. 전체 스택을 복사하지 않는다.

- **버전은 추정하지 않는다.** `package.json` 과 `node_modules/*/package.json` 에서 읽은
  실측값을 쓴다(`core-rules.md` 「버전 정책」).
- 프리릴리스는 캐럿 없이 정확히 적는다. 어느 RC 인지가 재현성의 전부다.
- 전체 표는 `docs/kdancex4_service_definition_and_tech_stack.md` 「11. 기술 스택 고정표」가
  원본이다. 여기서는 링크만 걸고 값을 복제하지 않는다 — 복제하면 둘이 어긋난다.

### 2. 쓰면 안 되는 것 — 학습 데이터 함정

**이 문서에서 가장 중요한 절이다.** 에이전트에게는 "무엇을 하라"보다 "무엇을 하지 말라"가
효과가 크다. 잘못된 사전 지식이 기본값으로 깔려 있기 때문이다.

각 항목을 이 형태로 적는다.

```
❌ 쓰지 않는다:  <옛 API 또는 패턴>
✅ 대신:         <이 버전의 올바른 형태>
왜:              <버전이 바뀌며 무엇이 달라졌는지 한 줄>
```

해당 SCH 와 무관한 함정은 넣지 않는다. 길어지면 읽히지 않는다.

### 3. 구조 — 어디에 무엇이 붙는가 (지도바둑)

`beginner-comment-style.md` 의 "전체 구성 내 위치 설명"을 에이전트 기준으로 다시 쓴다.
사람에게는 개념 이해가 목적이지만, 에이전트에게는 **수정 지점을 틀리지 않는 것**이 목적이다.

- 요청이 들어와서 나갈 때까지의 경로를 한 줄 흐름으로 적는다
- 각 계층이 무엇을 책임지고 무엇을 책임지지 않는지 적는다
- "이런 변경은 여기, 저런 변경은 저기"를 명시한다

### 4. 파일별 역할과 호출 관계

표로 적는다: 파일 경로 · 역할 한 줄 · 누가 부르는지 · 무엇을 부르는지.
`_workspace/05_implementer_TS-{번호}_summary.md` 의 변경 파일 목록이 원 소스다.

### 5. 선행 SCH 와 전제

이 SCH 가 무엇 위에 쌓였는지. 각 항목에 "그 SCH 가 만들어 둔 무엇에 의존하는지"를
한 줄씩 붙인다. 번호만 나열하지 않는다.

### 6. 건드릴 때 깨뜨리기 쉬운 것

이 SCH 의 코드를 수정할 때 함께 고쳐야 하는 것들. 시그니처를 바꾸면 따라 바뀌어야 하는
호출부, 스키마를 바꾸면 필요한 마이그레이션, 깨지는 테스트 파일 경로 등.

### 7. 검증 방법

명령과 기대 결과를 **복사해 실행 가능한 형태**로 적는다.

```
$ <명령>
→ 기대: <구체적 결과. "통과" 같은 모호한 말 금지>
```

깨져 있는 검증선이 있으면 명시한다 — 예를 들어 admin-web 의 `npm run lint` 는 별도 사유로
깨져 있으므로 타입 검증은 `next build` 로 한다.

### 8. 미검증 / 알려진 제약

확인하지 못한 것을 확인한 것처럼 적지 않는다(`core-rules.md` 「Investigation & Accuracy」).
RC 를 쓰는 항목은 안정판에서 달라질 수 있다는 점을 적는다.

## 작성 원칙

- **사실관계는 `_workspace/` 산출물에서 가져온다** — `05_implementer_TS-{번호}_summary.md`,
  `06_test-runner_results.md`, `08_code-reviewer_review.md`,
  `09_completion-verifier_report.md`. 추측·미화 금지.
- **HTML 가이드와 모순되면 안 된다.** 같은 SCH 를 설명하는 두 문서가 어긋나면 둘 다 못
  믿게 된다. 사실은 같고 서술 대상만 다르다.
- **짧게 쓴다.** 사람용 가이드는 풀어써도 되지만 이 문서는 에이전트가 컨텍스트에 싣는다.
  길면 다른 걸 밀어낸다. 산문보다 표·목록·코드블록을 쓴다.
- **한국어로 쓴다**(`core-rules.md` 언어 규칙). 단 API 이름·패키지명·명령어는 원문 그대로.
- **윤문 대상이 아니다.** 「AI 티 제거」 절은 사람이 읽는 문서를 대상으로 한다. 이 문서는
  독자가 에이전트이고 정확성이 문체보다 우선이므로 humanize 를 거치지 않는다.

## 하네스 연계 (kdance-dev-harness 오케스트레이터)

Phase 9.5(학습 주석 재구성·SCH 가이드 생성)에서 `kdance-implementer` 를 재호출할 때,
`beginner-comment-style.md`·`sch-guide-template.md` 와 **함께 이 문서 경로도 입력으로**
전달하고 `_workspace/guides/SCH-{번호}({기능명}).md` 생성까지 같은 태스크에 포함한다.

생성 후 `_workspace/kdance.html` 의 해당 SCH `.item` 에 HTML 가이드 링크와 나란히
에이전트 문서 링크를 추가한다.

SCH 대응 관계를 알 수 없는 작업은 다른 두 표준과 동일하게 이 단계를 건너뛴다.
