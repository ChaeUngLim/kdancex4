# 지도바둑식 학습 주석 표준 (6개월차 비전공자 대상)

## 목적

바둑을 배우는 사람에게 고수가 "이 수는 왜 두는지"를 매 수마다 설명해주는 지도바둑처럼,
코드도 "무엇을 하는지"가 아니라 **"왜 이렇게 짜여 있고, 전체 구성에서 어디에 붙는지"**를
설명한다. 대상 독자는 개발 경력 약 6개월의 비전공자 — 기본적인 프로그래밍 문법은 알지만
이 프로젝트의 아키텍처(FastAPI 계층 구조, SQLAlchemy ORM, Next.js App Router, Expo 등)에는
아직 익숙하지 않다고 가정한다.

## 적용 시점 (트리거)

`_workspace/SCH_kdance.html`에서 특정 SCH 항목이 "완료"로 바뀌는 시점에, 그 SCH가 건드린
파일들에 한해 이 표준으로 주석을 재구성한다.

- 로직은 절대 바꾸지 않는다 — 주석만 추가/수정한다.
- 이미 이 표준으로 재구성된 파일은 다시 건드리지 않는다. 파일 최상단(모듈 docstring
  바로 아래)에 `# 학습 주석: SCH-XX(기능명) 반영` 한 줄을 남겨 중복 작업을 방지한다.
- 한 파일이 여러 SCH에 걸쳐 계속 수정되는 경우, 새 SCH가 건드린 부분만 추가로
  반영하고 마커 줄의 SCH 번호를 갱신한다(`SCH-05(취소 오케스트레이션 서비스 + deps.py),
  SCH-09(...) 반영`).

## SCH 표기 규칙 — 번호만 쓰지 않는다

> 이 규칙은 `core-rules.md`의 「식별자·용어 표기 통일」 절을 SCH에 구체화한 것이다.
> 같은 원칙이 Task(`T1~`)·Phase·화면 ID에도 적용되며, 영문 용어는 `영문(한글)`로 병기한다.

주석이든 마커든, **`SCH-04`처럼 번호만 단독으로 쓰지 않는다.** 번호만으로는 그게 뭘
가리키는지 알 수 없어서 지도바둑 취지(왜/무엇인지 설명)에 어긋난다. 항상
`SCH-04(어댑터 3종: PG/알림/슬롯락)`처럼 **번호 바로 뒤 괄호에 기능명**을 붙인다.

- 기능명은 `_workspace/SCH_kdance.html`에 적힌 그 SCH의 공식 한 줄 설명(`<span class="t">`
  안의 문구)을 그대로 쓴다 — 새로 지어내지 않는다. 문구가 길면 핵심만 축약해도 되지만
  같은 SCH를 가리킬 때는 프로젝트 전체에서 같은 축약을 일관되게 쓴다.
- "SCH-05 참고", "SCH-01에서 설명함" 같은 상호 참조 문구도 예외 없이
  `SCH-05(취소 오케스트레이션 서비스 + deps.py) 참고`처럼 기능명을 붙인다.
- 첫 언급 이후 같은 주석 블록/같은 문단 안에서 반복 언급할 때는 번호만 써도 된다
  (매번 괄호를 반복하면 오히려 읽기 어렵다) — 새로운 블록·새로운 파일·새로운 섹션에서
  다시 언급할 때는 다시 기능명을 붙인다.
- 이 규칙은 `sch-guide-template.md` 기반 HTML 가이드에도 동일하게 적용된다.

## 구성 규칙

1. **파일 상단 사전 개념 요약** — 이 파일을 이해하는 데 필요한 배경 개념을 3~6줄로
   미리 요약한다. 예: 의존성 주입이 뭔지, 왜 여기서 `async def`를 쓰는지, SQLAlchemy
   관계(relationship)가 뭔지. 이전 SCH에서 이미 설명한 개념은 반복하지 않고
   "의존성 주입 개념은 SCH-05 `deps.py` 참고" 식으로 참조만 한다 — 학습자가
   SCH 순서대로 누적해서 읽는다는 전제.
2. **함수/클래스 단위 위치 설명** — 각 함수·클래스 바로 위에 "전체 구성에서 어느
   계층이고, 누가 호출하고 어디로 이어지는지"를 1~2줄로 적는다.
   예: `# 라우터(reservations.py)가 취소 요청을 받으면 이 함수를 호출하고,
   여기서 계산한 환불액은 adapters/payment_gateway.py로 넘어가 실제 환불을 실행한다.`
3. **왜(why) 중심 인라인 주석** — 코드가 "무엇을 하는지"는 코드 자체로 알 수 있으므로
   쓰지 않는다(core-rules.md의 주석 원칙과 동일). 분기/예외 처리/제약 조건처럼
   "왜 이렇게 처리하는지" 의도가 드러나야 하는 부분에만 인라인 주석을 남긴다.
4. **한국어 작성** — core-rules.md의 언어 규칙과 동일하게 전부 한국어로 쓴다.
5. **재검증** — 재구성 후 해당 파일과 관련된 테스트를 재실행해 로직이 바뀌지
   않았음을 확인한다.

## 하네스 연계 (kdance-dev-harness 오케스트레이터)

- **트리거**: Phase 9(`kdance-completion-verifier`)가 COMPLETE 판정을 내리고, 해당
  작업이 `_workspace/SCH_kdance.html`의 SCH 항목에 대응할 때.
- **실행**: 오케스트레이터가 `kdance-implementer`를 "주석 재구성" 태스크로 재호출한다.
  입력은 Phase 5 산출물의 변경 파일 목록 + 이 문서 경로. 새 파일 생성이나 로직
  변경은 금지하고 주석만 추가/수정하도록 명시한다.
- **완료 후**: Phase 6(`kdance-test-runner`)로 관련 테스트만 가볍게 재실행해 그린
  유지를 확인한 뒤, `_workspace/SCH_kdance.html`의 해당 SCH 항목을 "완료"로 갱신한다
  (SCH 관리는 그 문서에서만 한다는 기존 원칙 유지).
- SCH 대응 관계를 알 수 없는 임시/실험적 작업(예: SCH 미부여 버그 수정)은 이 단계를
  건너뛰고 사용자에게 "이 작업은 SCH가 없어 학습 주석 재구성을 생략했다"고 보고한다.
