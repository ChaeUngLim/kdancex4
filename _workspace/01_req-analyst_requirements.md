## 1. 요구사항 요약

### 1.1 What (무엇을)

회원이 이미 결제한 **단건 수업 예약을 취소**했을 때, (a) 취소 시점에 따라 환불액을 산정하고, (b) 결제수단에 맞는 환불을 실행하며, (c) 비워진 수업 슬롯을 다시 예약 가능하게 되돌리는 일련의 로직.

### 1.2 Why (왜)

- `kdance-screens-spec.html`(약관 요약 §결제·환불)과 `docs/requirements-analysis.md` **FR-22**가 "수업 시작 24시간 전 취소 — 전액 환불 / 24시간 이내 — 학원 정책에 따름"을 이미 약속하고 있다. 체크아웃 화면(`kdance-screens-spec.html` 화면04)에는 "주문 내용과 취소·환불 정책에 동의합니다" 동의 체크박스가 이미 설계되어 있어, **환불 로직 없이는 결제 화면이 약관상 지킬 수 없는 약속을 받는 상태**가 된다.
- 플랫폼은 통신판매중개자로 고지하므로(같은 약관), 환불 이행 주체·절차가 정의되지 않으면 컴플라이언스 리스크가 된다.

### 1.3 요청에 포함되지 않는 것 (Out of scope, 근거 있음)

- **월 구독(정기결제) 중도 해지 환불** — 약관상 "월 구독은 언제든 해지 가능 — **해지 시 다음 결제일부터 미청구**"로 확정. 즉 일할 환불이 아니라 갱신 중단 방식이므로 환불 로직 대상이 아니다. 요청의 "예약 취소"도 단건 예약을 가리킨다.
- **학원(업주) 측 수업 폐강에 따른 환불** — 사용자 취소가 아닌 공급자 귀책 취소. 별도 요구사항이며 이번 요청 문구에 없음. (§6-Q5에서 확인 요청)

## 2. 전제 조건 — 선행 도메인 부재 (가장 중요)

**현재 코드베이스에는 예약·결제 도메인이 존재하지 않는다.** 환불 로직을 "추가"할 대상 코드가 없다.

확인한 사실:

| 확인 항목 | 실제 상태 |
|---|---|
| `backend/app/main.py` | `GET /health` 단일 엔드포인트뿐 (전체 8줄) |
| backend 소스 파일 | `main.py`, `__init__.py`, `alembic/env.py`, `tests/test_health.py` — 이것이 전부 |
| SQLAlchemy 모델 | 없음. `Reservation`·`Order`·`Payment`·`ClassSchedule`·`Academy`·`User` 모두 미정의 |
| Alembic 마이그레이션 | `backend/alembic/versions/`에 `.gitkeep`만 있고 리비전 0건 |
| PG 연동 | 미착수. PG사 선정조차 미완 (`payment-method-policy.md` 오픈 이슈) |
| Redis 슬롯 락 (FR-42) | 미구현 |
| admin-web / mobile | 헬스체크 문자열 표시 수준의 스캐폴드 |

`docs/requirements-analysis.md` §3 갭 분석도 "예약/멤버십(FR-20~23) 미구현", "결제/가격정책(FR-30~40) 미구현, PG 연동 자체가 미착수"로 동일하게 기록하고 있다.

**따라서 이 요청은 그대로는 실행 불가능하며, 구현 범위를 먼저 정해야 한다 (§6-Q1).** 환불은 결제의 역연산이므로, 결제 레코드(무엇을 얼마에 어떤 수단으로 결제했는지)와 예약 레코드(언제 시작하는 수업인지) 없이는 금액 산정도 슬롯 복구도 정의되지 않는다.

## 4. 대상 범위 (Phase 2 탐색 범위 입력)

`backend` 중심, `mobile`·`admin-web` 동반. 단 §6-Q1의 답에 따라 축소될 수 있다.

### backend (필수, 작업량 대부분)
- 도메인 모델: `Reservation`(상태 머신), `Order`/`Payment`, `Refund`, `ClassSchedule`(시작시각 — 24h 판정 기준), `Academy`(학원별 환불 정책을 둘 경우)
- 환불액 산정 로직 (순수 계산 계층 — 테스트 가능하게 분리 권장)
- 취소 API (`POST /reservations/{id}/cancel` 형태 예상), 환불 상태 조회
- PG 환불 호출 어댑터 + 환불 웹훅 수신
- Redis 슬롯 락 해제 / 정원 복구 (FR-42 연계)
- Expo Push 환불 알림 (FR-43·FR-92 재사용, **SMS 금지**)
- Alembic 마이그레이션

### mobile (Expo)
- 예약 상세에서 취소 진입, **취소 전 환불 예상액 사전 고지 화면** (약관 동의를 받은 이상 필수)
- 환불 진행 상태 표시 (가상계좌의 경우 즉시 완료가 아님)
- 가상계좌 결제건이면 **환불 수령 계좌 입력** UI (§6-Q2 결정 시 필요)

### admin-web (React+Vite)
- 취소·환불 요청 목록 및 처리 화면 (§6-Q3에서 관리자 승인제로 결정될 경우 필수)
- 정산 대시보드(FR-39)에 환불 반영 — 총 결제액/수수료/실지급액이 환불로 달라짐

## 5. 제약 조건

1. **무료 API 우선 원칙** (`payment-method-policy.md`) — PG 외 새 유료 API 도입 금지. 환불 알림은 Expo Push, SMS 금지. 슬롯 해제는 기존 Redis 재사용.
2. **가상계좌 환불은 카드와 구조가 다르다** — 카드는 승인취소(부분취소 포함)로 원거래를 되돌리지만, 가상계좌는 원거래를 되돌릴 경로가 없어 **수취인 계좌로의 별도 송금(계좌 환불)**이 된다. 즉 (a) 사용자 환불계좌 수집·검증, (b) 예금주명 대조, (c) 송금 실패 재시도 경로가 추가로 필요하다. 단건 예약이 가상계좌 기본이므로 이것이 주 경로다.
3. **PG 결제 수수료는 환불해도 대개 반환되지 않는다** — 가상계좌는 건당 정액 수수료이므로 소액 환불 시 역마진이 발생한다. 누가 부담할지 미정 (§6-Q4).
4. **정산과의 결합** — FR-38(수수료 8%, 베타 6개월 면제), FR-39(정산 대시보드), 매월 5일 정산. **이미 정산이 나간 뒤의 환불**은 학원에 대한 채권이 되므로 정산 로직과 반드시 함께 설계해야 한다.
5. **쿠폰·할인 결제건의 환불** — FR-32(대학생 3개월 램프), FR-33(분기 1+1 쿠폰), `pricing-policy.md`(차액 업주 부담)가 얽힌다. 쿠폰 사용 예약을 취소하면 쿠폰을 복원할지, 복원 시 분기 말 소멸(FR-33)과 어떻게 맞물릴지 미정 (§6-Q4).
6. **동시성** — 취소/환불은 중복 실행되면 이중 환불이 된다. 멱등성(idempotency key) 및 예약 상태 전이의 원자성이 필수. FR-42 Redis 락과 같은 자원을 다룬다.
7. **감사 추적** — 금전 이동이므로 환불 요청·승인·실행·실패 전 이력을 불변 로그로 남겨야 한다. 통신판매중개자 고지와 함께 분쟁 대응의 근거가 된다.
8. **기술 스택 고정** — FastAPI + SQLAlchemy 2 + Alembic + psycopg3 (Python 3.12, uv) / React+Vite+TS / Expo SDK 57.
9. **금액은 정수(원) 정수형으로 다룬다** — 부동소수 금지. 비율 할인·부분 환불의 반올림 규칙 명시 필요.

## 6. 미해결 질문 — 사용자 결정 필요 (BLOCKING)

> 이 에이전트 세션에서는 `AskUserQuestion` 도구를 사용할 수 없었다(도구 미제공). 따라서 추측하지 않고 아래에 정리하며, **오케스트레이터가 사용자에게 전달해 결정을 받아야 한다.**
> Q1~Q3은 Phase 3 착수 전 반드시 필요하고, Q4~Q5는 늦어도 Phase 4 이전에 필요하다.

### Q1. 이번 작업의 구현 범위 — 예약·결제 도메인이 없는데 어디까지 만드나? (최우선)
- **A안 (계산 로직 한정)**: 환불액 산정 규칙만 순수 함수 + 단위테스트로 구현. 모델/API/PG 없음. 가장 작고, 정책이 확정되면 재사용 가능.
- **B안 (수직 슬라이스, 권장 후보)**: 예약·결제·환불 최소 모델 + 취소 API + 환불액 산정 + 슬롯 복구까지. PG는 인터페이스만 두고 가짜 어댑터(fake)로 대체. 실제 PG 연동은 PG사 확정 후 별건.
- **C안 (PG 실연동 포함 전체)**: PG사 선정·계약이 선행되어야 하므로 현시점 착수 불가로 판단됨.

### Q2. 결제수단별 환불 경로 — 어떤 수단을 이번에 지원하나?
`payment-method-policy.md`상 단건 예약은 가상계좌가 기본이다.
- 가상계좌 환불을 위해 **사용자 환불계좌(은행/계좌번호/예금주)를 앱에서 수집**하는 방식으로 가는가?
- 카드 결제 단건도 존재한다고 보고 승인취소 경로를 함께 만드는가?
- 관련 오픈 이슈: `distribution-policy.md`의 **"갤럭시 스토어 인앱결제(Samsung IAP) 재검토 필요"**가 미해결이다. Samsung IAP를 쓰게 되면 환불이 스토어 정책에 종속되어 위 설계가 무의미해진다 — 이 건을 먼저 확정할 것인가?

### Q3. "24시간 이내 취소 — 학원 정책에 따름"의 실체와 승인 주체
FR-22의 이 문구는 어느 문서에도 구체화되어 있지 않다.
- (a) **학원별 설정 필드**로 만들어 관리자가 환불 비율표(예: 24~12h 50%, 12h 이내 0%)를 직접 설정하는가? → admin-web에 설정 화면, `Academy` 모델에 필드, 학원 상세 노출(FR-14)까지 범위 확대
- (b) **플랫폼 고정 기본값**(예: 24h 이내 일괄 0% 환불)으로 단순화하고 학원별 설정은 후순위로 미루는가?
- 그리고 환불 실행 주체는 **자동 즉시 환불**인가, **학원 관리자 승인 후 환불**인가? 승인제면 admin-web 처리 화면과 SLA(미승인 시 자동 승인 기한)가 필요하다.

### Q4. 환불 시 수수료·쿠폰·정산 역산 규칙
`pricing-policy.md`가 "상세 정산 로직은 추후 논의 필요"로 열어둔 영역이다.
- 플랫폼 수수료 8%(FR-38)는 환불 시 함께 환급되는가, 플랫폼이 취하는가? (베타 6개월 면제 기간이면 무의미해질 수 있음)
- **반환되지 않는 PG 건당 수수료**는 플랫폼·학원·회원 중 누가 부담하는가?
- 이미 매월 5일 정산이 나간 뒤의 환불은 어떻게 회수하는가 (다음 달 정산 차감?)
- 1+1 쿠폰(FR-33) 사용 예약 취소 시 쿠폰을 복원하는가? 복원한다면 분기 말 소멸 규칙과 대학생 램프 요금제(FR-32) 차감분은 어떻게 되돌리는가?

### Q5. 부분 취소 및 학원 귀책 취소를 이번 범위에 넣는가?
- 여러 수업을 한 주문으로 결제한 경우 **일부만 취소(부분 환불)**를 지원하는가, 주문 단위 전체 취소만 지원하는가?
- **학원의 폐강·일정 변경으로 인한 취소**는 시점과 무관하게 전액 환불로 보는 것이 통상이나, 문서에 정의가 없다. 이번 범위에 포함하는가?

**Phase 3(kdance-impl-planner)에 대한 지시:** 위 결정을 전제로 계획을 세운다. Q3이 (a)안으로 결정됐으므로 `Academy` 모델에 환불 비율표 필드(예: 시간대별 환불율 JSON/테이블)와 admin-web 설정 화면(CRUD)을 계획에 반드시 포함한다 — §4/§7의 "(b)안 가정" 서술은 이 §9로 대체된다. Q4·Q5는 미확정이므로 해당 로직은 **인터페이스만 열어두고(예: 수수료 부담 규칙을 설정 가능한 함수/상수로 분리, 부분 취소는 API 스펙에서 확장 가능하게) 하드코딩된 임시값으로 최소 구현**한 뒤 계획 산출물에 "Q4/Q5 확정 시 이 부분 재작업 필요"로 명시한다.

## 7. 수용 기준 (Acceptance Criteria)

> §9의 사용자 결정을 반영해 갱신됨(원래 §7 초안은 Q3=(b) 가정이었으나 실제 결정은 (a) 학원별 설정). 체크 표시는 Phase 9(완료 검증)에서 사용한다.

### 기능
- [ ] 확정 상태의 예약을 취소하는 API가 존재하고, 본인 예약만 취소할 수 있다 (타인 예약 취소 시 403).
- [ ] 수업 시작 **24시간 초과** 시점에 취소하면 환불액이 결제액 전액으로 산정된다 (FR-22).
- [ ] 수업 시작 **24시간 이내** 취소는 Q3에서 확정된 규칙대로 환불액이 산정된다.
- [ ] 경계값(정확히 24시간 00분 00초)의 동작이 명시적으로 정의되고 테스트된다.
- [ ] 이미 시작했거나 종료된 수업, 이미 취소된 예약은 취소가 거부된다 (상태 전이 검증).
- [ ] 취소가 확정되면 해당 수업 슬롯의 정원이 복구되어 다시 예약 가능해진다 (FR-42 Redis 락 연계).
- [ ] 환불 요청·산정·실행 결과가 `Refund` 레코드로 영속화되고, 실패 시 상태와 사유가 남는다.
- [ ] 취소 완료 시 회원과 학원 관리자 양쪽에 앱 내 알림이 발송된다 (Expo Push 재사용, **SMS 미사용**).
- [ ] 모바일에서 취소 확정 전에 **예상 환불액이 사전 고지**된다.

### 정합성·안전성
- [ ] 동일 예약에 대한 취소 요청이 동시에 2건 들어와도 환불은 1회만 실행된다 (멱등성 키 또는 DB 제약으로 보장).
- [ ] 환불액이 원결제액을 초과하는 경우가 구조적으로 불가능하다 (누적 환불액 검증).
- [ ] 금액 계산에 부동소수를 쓰지 않으며, 반올림 규칙이 문서화·테스트되어 있다.
- [ ] 환불 관련 모든 상태 변경이 감사 로그로 남는다.

### 정책 준수
- [ ] 새로 도입된 유료 외부 API가 없다 (PG 제외) — `payment-method-policy.md` 무료 API 우선 원칙.
- [ ] 환불 정책이 `pricing-policy.md`·`payment-method-policy.md`와 모순되지 않으며, 이번에 새로 결정된 사항은 해당 정책 문서에 반영된다.

### 검증
- [ ] 환불액 산정 로직에 경계·예외 케이스를 포함한 단위 테스트가 있고 통과한다.
- [ ] 취소 API에 대한 통합 테스트(정상/권한/상태오류/중복요청)가 통과한다.
- [ ] Alembic 마이그레이션이 up/down 모두 정상 동작한다.
- [ ] 기존 `GET /health` 및 기존 테스트가 깨지지 않는다.
