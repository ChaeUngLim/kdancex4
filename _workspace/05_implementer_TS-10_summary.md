## 2. "결정됐으나 이번 슬라이스 미구현"의 구분 처리

지시의 핵심 요구였다. 5항 표에 **"이번 슬라이스 구현 상태"** 열을 별도로 두고 세 범주로 갈랐다.

| 범주 | 항목 | 표기 |
|---|---|---|
| 결정만 완료, **미구현** | 정산 후 환불의 다음 달 차감 / 1+1 쿠폰 복원 | **⚠️ 결정만 완료, 이번 미구현.** + 미구현 사유(정산 모듈 부재 / 쿠폰 모델 부재) + 지금 코드에 남는 것(상수·주석, 복원 훅 위치)까지 명시 |
| 결정 완료, **의도적으로 반영 없음** | PG 수수료 손실 부담 / 8% 수수료 환급 | **반영 없음(의도된 것).** — 미구현이 아니라 계산식에 들어갈 자리가 없다는 뜻임을 구분 |
| 실제 구현됨 | 24h 경계 / 비율표 / 올림·clamp / 가상계좌 환불계좌 | 별도 표기 없이 규칙 그대로 기술 |

표 아래에 못을 하나 더 박았다: **"이 절에서 환불액 산정에 실제로 영향을 주는 항목은 하나도 없다. 회원이 돌려받는 금액은 결제액·취소 시점·학원 비율표만으로 결정된다."** — 5항 전체가 플랫폼↔학원 정산 문제이지 회원 환불 계산과 무관하다는 점을 분리했다.

## 3. `docs/pricing-policy.md`와의 정합성 — 확인 결과

완료 기준의 "쿠폰 차액 업주 부담 서술과 충돌하지 않는지 확인" 항목이다. **직접적인 모순은 없다.** `pricing-policy.md`가 "상세 정산 로직(쿠폰 종류별 부담 비율, 정산 주기 등)은 추후 논의 필요"로 명시적으로 열어둔 영역이라 애초에 충돌할 확정 서술이 없다.

다만 **상충 소지 2건**을 발견해 7항에 명시적으로 적었다. 침묵하지 않았다.

### (1) 부담 주체 원칙이 항목별로 갈린다 — 모순 아님, 주의 필요

- `pricing-policy.md`: 쿠폰/할인 차액 → **업주 부담**
- Q4 확정: PG 건당 수수료 손실 → **플랫폼 부담**

서로 다른 비용 항목이라 논리적 모순은 아니다. 문제는 **통일된 원칙이 없다**는 점이다. "비용은 업주가 진다"도 "플랫폼이 진다"도 아니고 항목별 개별 결정이므로, 새 비용 항목이 생길 때마다 따로 물어야 한다. 7항 1번에 적었다.

### (2) 할인 결제건 취소 시 업주 차액 부담의 소멸 여부가 공백 — **실질적 위험**

이게 진짜 짚어야 할 지점이다.

- 회원 쪽은 문제없다 — 환불액 기준이 "회원이 실제 결제한 금액(할인가)"이므로 정합적이다.
- 정산 쪽이 비었다 — 예약이 취소되면 업주가 부담한 차액도 함께 소멸해야 논리적으로 맞지만, 그 규칙이 어느 문서에도 없다.
- 여기에 Q4의 **"1+1 쿠폰은 복원한다"** 가 겹치면 **업주는 차액을 부담한 채 회원에게는 쿠폰이 돌아가는** 구간이 생길 수 있다. 업주가 한 건에 대해 차액을 두 번 부담하는 경로가 열린다.

7항 2번에 서술하고 "환불 관련 오픈 이슈" 첫 줄로 올렸다. **정산 모듈과 쿠폰 모델을 실제로 구현할 때 반드시 함께 정해야 한다.** 이번 슬라이스에서는 둘 다 미구현이라 당장 드러나지 않지만, 구현 시점에 결정이 없으면 그때 막힌다.

## 4. 구현 중 발견한 이슈

### I-1. Q3 (a)안 채택 사실이 `payment-method-policy.md`에 전혀 없었다 — 해소됨

FR-22의 "24시간 이내 취소는 학원 정책에 따름"이 어느 정책 문서에도 구체화돼 있지 않았다(요구사항 §6-Q3이 지적한 그대로). 이번 2항이 그 공백을 메운다. 학원별 설정 필드 방식임을 문서에 처음으로 못 박았다.

### I-2. 문서의 "PG사 미선정" 전제와 코드의 Fake 어댑터 사이에 간극이 있다 — **미해결, 보고만**

`payment-method-policy.md:56`이 이미 이렇게 쓰고 있다:

> **"PG사 미선정"은 더 이상 유효한 전제가 아니다** — 포트원이 방식 B의 PG로 확정됐다. (…) 가짜 어댑터를 쓰더라도 **포트원 응답 스키마를 흉내 낼 것**.

그런데 Phase 3 계획 D4와 TS-04 명세는 "PG사 미선정"을 근거로 `PaymentGateway`를 단일 메서드 Protocol로 두라고 지시한다. **문서가 코드 계획보다 앞서 있다.**

- TS-10 범위 밖이라 문서를 고치지 않았다. 문서 쪽이 최신이고 정확하다.
- 다만 TS-04 구현자가 `payment-method-policy.md:56`을 읽지 않으면 포트원 응답 스키마를 흉내 내지 않은 Fake를 만들 수 있다.
- `RefundStatus`에 `pending`을 1급 상태로 두라는 지시는 포트원 가상계좌 환불 응답과 방향이 같으므로 큰 충돌은 아닐 것으로 보이나, **실제 포트원 스키마를 확인하지 않고 단정하지 않는다.**
- **Phase 8(코드 리뷰) 확인 항목으로 넘긴다.**

### I-3. 문서 상단 "무료 API 우선 원칙"과 이번 환불 기능 사이에 충돌 없음 — 확인만

수용 기준 "새로 도입된 유료 외부 API가 없다"와 관련해 확인했다. 이번 환불 슬라이스가 추가하는 외부 의존은 없다(알림은 기존 Expo Push 재사용, 락은 기존 Redis). 방식 A의 알림톡·오픈뱅킹 유료 API 예외 건은 이번 환불 기능과 무관한 별건이므로 해당 섹션을 건드리지 않았다.
