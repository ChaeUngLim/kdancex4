1. 개요

SCH-06은 예약 취소 기능이 실제로 앱 밖에서 "HTTP API"로 보이게 만드는 마지막 조각입니다. backend/app/schemas/가 요청·응답 데이터의 형태를 검증하는 Pydantic 클래스들을, backend/app/routers/가 그 데이터를 받아 SCH-05(취소 오케스트레이션 서비스 + deps.py)의 서비스 함수로 옮기는 엔드포인트 4개를, backend/app/main.py가 그 라우터들과 CORS 설정을 하나의 FastAPI 앱으로 조립하는 코드를 담당합니다.

이 SCH가 새로 계산하거나 새로 판단하는 것은 거의 없습니다. 금액 계산은 SCH-03(환불액 산정), 취소 순서와 예외는 SCH-05가 이미 끝내 두었습니다. SCH-06의 일은 "그 결과를 회원 스마트폰과 학원 관리자 브라우저가 이해할 수 있는 JSON 모양으로 바꾸는 것" — 즉 경계 검증과 형태 변환입니다.

한 줄 요약
"잘못된 모양의 요청은 서비스 코드에 닿기도 전에 걸러내고, 서비스가 이미 정해둔 상태 코드(CancellationError.status_code)는 그대로 꺼내 쓴다" — 새 로직을 만들지 않고 연결만 하는 것이 이 SCH의 원칙입니다.

2. 사전 개념

Protocol·Fake·포트-어댑터·Redis는 SCH-04(어댑터 3종: PG/알림/슬롯락), 트랜잭션·행 잠금·멱등성·SAVEPOINT·Depends()는 SCH-05(취소 오케스트레이션 서비스 + deps.py)에서 이미 설명했으므로 반복하지 않습니다. ORM·CHECK/UNIQUE 제약은 SCH-01(기반 배선)·SCH-02(도메인 모델 7개) 가이드를 참고하세요. 이번 SCH에서 처음 등장하는 개념 5가지만 설명합니다.

Pydantic 스키마가 뭔가요?

파이썬 클래스로 "요청/응답 데이터가 이런 모양이어야 한다"를 선언해 두면, FastAPI가 요청이 들어올 때마다 그 클래스로 값을 실제로 만들어 보면서 자동으로 검증합니다. 형태가 안 맞으면(필수값 누락, 타입 불일치, 범위 초과 등) 엔드포인트 함수 본문이 실행되기도 전에 422 에러가 나갑니다. 개발자가 "이 값이 문자열인지, 20자를 넘지 않는지"를 엔드포인트마다 손으로 if문으로 확인하지 않아도 되는 이유입니다.

이 프로젝트는 서비스 계층의 결과값을 dataclass로, HTTP 경계의 요청/응답을 Pydantic BaseModel로 의도적으로 분리합니다. 서비스는 HTTP를 몰라야 단위 테스트가 가볍고, 스키마는 DB를 몰라야 요청 형태가 바뀔 때 서비스까지 흔들리지 않습니다. 라우터가 이 둘 사이를 옮기는 역할을 합니다.

model_validator(mode="after")는 필드 하나하나의 형식 검증이 끝난 뒤 "필드들 사이의 관계"를 검증할 때 씁니다. 예를 들어 CancelRequest에서 "결제수단이 가상계좌인데 환불 계좌가 없다"는 조합은 필드 각각은 유효해도 전체로는 무효입니다. StrictInt는 반대로 필드 하나를 더 엄격하게 만드는 도구입니다 — 보통 Pydantic의 int는 "24"(문자열)·24.0(실수)·True(bool)까지 너그럽게 받아주는데, StrictInt는 이 변환을 끄고 진짜 int만 받습니다. 환불 비율표(RefundPolicyTier)가 이걸 쓰는 이유는, 여기서 느슨하게 받으면 저장은 성공하고 취소 시점에 환불 계산 함수가 같은 값을 거부해서 터지기 때문입니다.

FastAPI 라우터(APIRouter)가 뭔가요?

모든 엔드포인트를 app 객체 하나에 직접 등록하면 파일 하나가 끝없이 길어집니다. APIRouter는 "이 모듈이 담당하는 엔드포인트들"을 하나로 묶어두는 그릇이고(prefix="/reservations" 같은 공통 경로도 여기서 지정합니다), app/main.py가 app.include_router(router)로 이 그릇들을 최종적으로 하나의 앱에 조립합니다. 각 라우터 모듈은 자기 몫의 경로만 신경 쓰면 되고, "전체 API가 어떻게 구성되는지"는 main.py 한 곳만 보면 알 수 있습니다.

예외 → HTTP 상태 코드 매핑 패턴

SCH-05(취소 오케스트레이션 서비스 + deps.py)가 만든 CancellationError는 status_code를 값으로 들고 다닙니다(404/403/409/422). 그래서 라우터에는 예외 타입별 if/elif 사다리가 없습니다 — raise HTTPException(status_code=exc.status_code, detail=exc.message) 한 줄이 전부입니다. 취소 거부 사유가 하나 늘어도(예: 새로운 CancellationError 서브클래스) 이 라우터 코드는 바뀌지 않습니다. 이건 SCH-05가 "예외 자신이 HTTP 지식을 갖게 하자"고 미리 설계해 둔 덕분입니다.

CORS가 뭔가요?

브라우저는 기본적으로 "이 페이지를 내려준 출처(origin)와 다른 출처의 API"로 보낸 요청의 응답을 스크립트가 읽지 못하게 막습니다(보안 기본값). admin-web(Next.js, localhost:3000)이 backend API를 호출하려면, 서버가 "이 출처는 허용한다"고 응답 헤더에 명시적으로 적어줘야 합니다. 그 설정을 담당하는 것이 app/main.py의 CORSMiddleware입니다. 모바일(Expo) 앱은 브라우저가 아니므로 이 규칙 자체와 무관합니다.

OpenAPI 스키마(app.openapi())가 뭔가요?

FastAPI가 등록된 라우트와 스키마를 훑어서 자동으로 만들어내는 API 명세(JSON)입니다. /docs 화면도 이 정보로 그려집니다. app.routes를 직접 읽는 대신 app.openapi()["paths"]를 보면, FastAPI 내부에서 라우터를 감싸는 방식이 버전마다 바뀌어도 "실제로 클라이언트가 호출할 수 있는 경로 목록"을 안정적으로 얻을 수 있습니다 — 이 SCH의 I-1 이슈(아래 4절)가 바로 이 차이 때문에 생겼습니다.

4. 이슈 → 원인 파악 → 해결

SCH-06 작업 중 실제로 발견된 사항입니다. _workspace/05_implementer_TS-06_summary.md의 §4(구현 중 발견한 이슈)를 그대로 옮깁니다 — 지어내지 않습니다.

4.1 완료 기준의 검증 명령이 이 FastAPI 버전에서 깨진다 (I-1)

현상: 계획이 지정한 uv run python -c "from app.main import app; print([r.path for r in app.routes])"는 AttributeError로 죽는다.
원인 파악: FastAPI 0.141.1은 include_router로 붙인 라우터를 _IncludedRouter라는 래퍼로 app.routes에 넣는데, 이 객체에는 .path가 없다. 계획 작성 시점의 구버전 동작을 전제한 명령이었다.
해결: 대신 app.openapi()["paths"]를 본다 — 위 "사전 개념" 절의 OpenAPI 스키마 설명 참고. 결과: ['/admin/academies/{academy_id}/refund-policy', '/health', '/reservations/{reservation_id}/cancel', '/reservations/{reservation_id}/cancellation-preview']. test_all_routes_are_mounted도 같은 이유로 이 방식을 쓴다.

4.2 admin 경로에 인증도 권한 검사도 없다 (I-2)

경고 — 배포 전 반드시 고쳐야 하는 진짜 위험

현상: GET·PUT /admin/academies/{id}/refund-policy는 학원 ID만 알면 누구나 그 학원의 환불 비율표를 바꿀 수 있다. 비율표를 0%로 바꿔 두면 이후 모든 취소가 무환불이 되므로, 영향은 "설정이 틀렸다"가 아니라 회원 돈이 걸린 사고다.

원인 파악: 이번 슬라이스에 "이 사람이 이 학원의 관리자인가"를 판정할 모델 자체가 없다(인증·회원·권한 체계 부재). 예약 취소 쪽은 X-User-Id 헤더라는 임시 인증(F7)이라도 있지만, admin 쪽은 그 헤더를 요구해도 아무 UUID나 넣으면 통과하므로 검증 흉내만 내는 셈이다.

해결(이번 SCH 범위): X-User-Id를 요구하지 않기로 했다 — 있는 척하는 검사보다 없는 게 낫다고 판단했다. 대신 admin_academies.py 모듈 docstring 최상단에 경고와 붙일 자리(dependencies=[Depends(require_academy_admin)])를 명시해 두었다.

지금 상태: 이 경로는 프로덕션에 노출하면 안 된다. TS-08의 admin-web은 userId를 선택값으로 보내므로 지금 구성 그대로 동작은 하지만, 그건 "동작한다"이지 "안전하다"가 아니다.

(2026-09-26 주: 이 API 는 비율표와 함께 폐기돼 새 스택으로 옮기지 않는다. "있는 척하는 검사보다 없는 게 낫다"는 판단 대신, 새 스택에서는 SCH-24(인증·역할)가 먼저 선다 — FR-005(역할별 데이터 범위)가 이후 모든 조회의 전제이기 때문이다. 업주 환불 입력(FR-293(업주 환불 입력)) 같은 돈이 걸린 화면도 그 위에 올라간다.)

4.3 mobile이 preview.cancellable / reason_code를 보지 않는다 (I-3)

현상: mobile/App.tsx의 CancellationPreview 타입에 두 필드가 없고 canSubmit도 확인하지 않는다. 이미 시작한 수업에서도 취소 확정 버튼이 열리고, 눌러야 비로소 409를 받는다.
원인 파악: preview API를 만든 이유의 절반은 "미리 버튼을 막아 회원이 헛수고하지 않게 하는 것"이었는데, mobile 쪽이 아직 그 값을 안 쓴다.
해결(범위 밖): 서버는 올바르게 막는다(금전 사고는 아니다) — 결국 409로 거부되므로 안전은 지켜진다. 다만 사용자 경험이 나쁘므로 mobile 쪽 3줄 수정을 권고했을 뿐, TS-06 범위 밖이라 손대지 않았다.

4.4 cancel 경로의 ValueError 포괄 catch는 메시지가 약간 넓다 (I-4)

현상: cancel_reservation()을 감싼 except ValueError는 비율표 오류 외의 ValueError(예: DB에 들어간 알 수 없는 refunds.status 값을 RefundStatus()로 변환할 때 나는 것)도 같은 422로 접는다.
원인 파악: 두 경우 모두 "데이터가 계약을 어겼다"는 같은 부류라 422 자체는 맞지만, 응답 문구는 항상 비율표를 가리키므로 다소 부정확하다.
해결(범위 밖으로 남김): 원인은 항상 logger.warning에 남으므로 운영 추적은 된다. 더 좁히려면 서비스(SCH-05)가 전용 예외를 던지도록 그 파일을 바꿔야 하는데, 그건 이번 SCH의 실질적 변경 범위를 넘어서 하지 않았다.

4.5 RefundPolicyResponse 생성 실패를 500이 아니라 422로 바꿨다 (I-5)

현상: 이 API가 생기기 전에 들어갔거나 SQL로 직접 넣은 값이 응답 스키마를 위반할 수 있다.
원인 파악: GET이 그대로 500을 내면 관리자는 "화면이 고장났다"만 보고 고칠 방법을 찾지 못한다.
해결: 422 + "다시 저장하면 복구됩니다"로 바꿨다. PUT은 조회 결과에 의존하지 않으므로 실제로 그 방법으로 복구된다.

정리
I-1은 계획과 실제 FastAPI 버전의 불일치, I-2는 이번 슬라이스의 구조적 공백(인증 모델 부재)이 만든 배포 차단 사유, I-3은 다음 계층(mobile)의 미흡한 활용, I-4·I-5는 이번 SCH가 스스로 내린 절충(범위를 넘는 수정 대신 로그·문구로 완화)입니다.

7. 다음 SCH로 이어지는 것

SCH-06이 SCH-07(conftest + DB 통합 테스트 작성, 아직 가이드 없음)과 그 이후 단계에 남긴 인터페이스·주의사항입니다. _workspace/05_implementer_TS-06_summary.md §6(미해결/인계)을 그대로 옮깁니다.

  • 1. 실DB 통합 미검증. localhost:5433 연결 거부(이 환경에 docker CLI 없음)로, 취소 정상 경로·403·409·멱등 재생은 코드상으로만 맞춰져 있다. SCH-07이 테스트를 작성하고 SCH-12가 실행해야 한다. (2026-09-26 주: 2026-09-23 DB 를 켜고 186 passed 를 확인했다. SCH-12(DB 통합 테스트)는 SCH-21(FastAPI→Next.js 전환)에 흡수됐다.) 특히 routers/reservations.py의 예외 매핑과 schemas/academy.py의 JSONB 문지기 역할이 DB 없이 검증 가능했던 지점이자, 실 DB로도 반드시 재확인해야 할 지점이다.
  • 2. (후속 권고 I-2) admin 인증 — 배포 전 필수. dependencies=[Depends(require_academy_admin)]를 붙일 자리는 마련해 두었지만, 그 의존성 자체(인증·회원·권한 모델)는 아직 없다. 이 API를 외부에 노출하기 전에 반드시 채워야 한다. (2026-09-26 주: 이 API 는 옮기지 않는다. 인증·권한은 SCH-24(인증·역할)가 만든다.)
  • 3. (후속 권고 I-3) mobile이 cancellable/reason_code를 무시한다. mobile/App.tsx의 CancellationPreview 타입에 두 필드를 추가하고 취소 버튼을 canSubmit 기준으로 막는 3줄 수정이 필요하다. (2026-09-26 주: 이 화면은 SCH-09(mobile 취소·환불계좌) 데모이고 회원이 누르면 곧바로 환불하던 옛 흐름이다. 새 흐름(정규는 문의, 이벤트형은 예약 상세 취소 신청)으로 다시 만든다.)
  • 4. (후속 권고 I-4) 에러 문구 정밀화. cancel 경로의 except ValueError가 비율표 오류 외의 데이터 오류까지 같은 문구로 접는다. 서비스(SCH-05)가 전용 예외를 던지도록 바뀌면 이 라우터도 그때 함께 좁힐 수 있다. (2026-09-26 주: 비율표 오류 경로가 사라져 이 권고는 새 스택에 해당하지 않는다.)
