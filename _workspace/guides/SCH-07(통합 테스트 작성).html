이 가이드는 끝난 작업의 기록이다. 여기서 설명하는 FastAPI 코드와 테스트는 SCH-21(FastAPI→Next.js 전환)에서 Next.js + Prisma 8 로 교체된다. 1~5절은 2026-09-15 작업 당시 그대로 두었고 지금과 달라진 곳에는 「2026-09-26 주」를 달았다.

그 뒤에 일어난 일: 이 SCH 가 준비한 DB 테스트 27개는 2026-09-23 DB 를 켜고 실제로 돌았다 — 전체 186 passed. 5절이 "아직 실행되지 않았다"고 적은 부분이 그날 풀렸다.

이어지는 것: 이 가이드가 다음 순서로 적은 SCH-11(마이그레이션 검증)·SCH-12(DB 통합 테스트)는 FastAPI 를 대상으로 해서 SCH-21 의 완료 기준으로 흡수됐다. SCH-21 은 Prisma 마이그레이션 적용과 DB 통합 테스트를 완료 기준에 넣는다. 테스트 DB 를 어떻게 돌릴지는 Q7(DB 테스트 전략)로 열려 있다. test_admin_refund_policy.py가 검증하던 비율표 API 는 옮기지 않는다.

지금 환불 규칙: 정규·일반 수업은 회원이 문의하고 업주가 금액을 정해 직접 실행한다(FR-098(업주 처리 환불 방식)·FR-293(업주 환불 입력)). 이벤트·원데이·파티·공연·대회는 회원이 예약 상세에서 취소하면 시스템이 FR-099c(이벤트·원데이·파티·공연·대회 취소 규정) 표대로 환불액을 계산하고 업주가 실행한다. 업주가 공지한 처리 기간(최대 3영업일)이 지나면 시스템이 자동으로 실행한다(FR-295(수단별 환불 실행)). 행사를 통째로 취소하면 결제자 전원에게 PG 로 일괄 전액 환불한다(FR-099e(행사 일괄 취소)).

테스트 실측: 2026-09-26 uv run pytest -q → 159 passed · 27 skipped. Docker Desktop 이 꺼져 있어 DB 테스트 27개가 skip 됐다 — 이 SCH 의 conftest.py가 설계대로 error 없이 건너뛴 것이다. DB 를 켠 2026-09-23 에는 186 passed 였다.

1. 개요

SCH-01(기반 배선)부터 SCH-06(Pydantic 스키마 + 라우터 + main.py)까지, 모든 테스트는 실제 PostgreSQL 연결 없이 통과해 왔습니다. 트랜잭션이 정말 한 덩어리로 커밋되는지, 같은 예약에 취소 요청이 동시에 2건 들어와도 환불이 1번만 나가는지는 진짜 DB가 있어야만 확인할 수 있는데, 이 환경에는 Docker가 없어서 그동안은 "코드상으로는 맞다"까지만 말할 수 있었습니다.

SCH-07은 이 간극을 메우는 테스트 하네스와 테스트 코드를 만듭니다. backend/tests/conftest.py가 "DB가 있으면 실제로 붙고, 없으면 조용히 건너뛴다"는 안전장치를, test_cancel_api.py·test_admin_refund_policy.py가 실제 검증 내용을 담당합니다.

한 줄 요약
"DB가 없는 이 환경에서도 테스트 스위트는 초록이어야 하고(skipped는 되지만 error는 안 된다), DB가 생기는 순간 같은 코드가 실제 검증을 시작해야 한다" — 이게 이 SCH가 푸는 문제입니다.

2. 사전 개념

트랜잭션·행 잠금(SELECT ... FOR UPDATE)·멱등성·SAVEPOINT·Depends()는 SCH-05(취소 오케스트레이션 서비스 + deps.py)에서, JSONB는 SCH-02(도메인 모델 7개)에서, Pydantic 스키마 검증은 SCH-06(Pydantic 스키마 + 라우터 + main.py)에서 이미 설명했으므로 반복하지 않습니다. 이번 SCH에서 처음 나오는 개념 4가지만 설명합니다.

pytest fixture(픽스처)가 뭔가요?

테스트 함수가 필요로 하는 "준비물"(DB 세션, API 클라이언트 등)을 함수 인자 이름으로 자동으로 받는 pytest의 기능입니다. scope="session"이면 테스트 전체에서 딱 한 번만 만들고(예: db_engine — DB 연결 자체는 비싸니까), scope="function"이면 테스트마다 새로 만듭니다(예: db_session — 각 테스트가 서로의 데이터를 보지 못하게 독립된 트랜잭션을 가져야 하니까).

테스트 격리를 SAVEPOINT로 만드는 이유

취소 서비스(SCH-05)는 스스로 session.commit()을 부릅니다. 테스트가 "커밋 안 하는 세션"을 넘겨서 격리를 만들 수는 없다는 뜻입니다. 그래서 한 겹 아래에서 막습니다: 커넥션 하나를 열고, 그 위에 "바깥 트랜잭션"을 걸고, 세션을 join_transaction_mode="create_savepoint"로 만듭니다. 서비스가 평소처럼 커밋해도 실제로는 자기 SAVEPOINT만 정리될 뿐 바깥 트랜잭션은 그대로이고, 테스트가 끝나면 바깥 트랜잭션을 롤백해서 전부 지웁니다. 단, 동시성 테스트는 예외입니다 — 락 경합을 재현하려면 커넥션이 진짜 2개여야 하는데, 위 방식은 커넥션 1개를 공유하므로 이 테스트만 실제로 커밋하고 끝나면 직접 지웁니다(committed_scenario).

DB가 없으면 error가 아니라 skip

pytest_runtest_setup은 pytest가 "각 테스트 실행 직전"에 자동으로 불러주는 후크(hook)입니다. 여기서 DB 연결을 한 번 확인해 안 되면 requires_db 마커가 붙은 테스트를 skip 처리합니다. error로 두면 인프라가 없을 뿐인데 테스트 스위트 전체가 빨갛게 보여서, 그 안에 섞여 들어온 진짜 회귀를 아무도 알아채지 못하게 됩니다. 수집(collection)은 연결을 요구하지 않으므로 uv run pytest -m requires_db --collect-only는 DB 없이도 "이런 테스트들이 있다"를 보여줄 수 있습니다.

동시 요청을 실제로 만드는 도구

threading.Barrier(2)는 두 스레드가 "둘 다 준비될 때까지" 기다렸다가 동시에 출발하게 만드는 장치입니다 — 이게 없으면 한쪽이 먼저 끝나버려서 진짜 동시 요청이 재현되지 않습니다. ThreadPoolExecutor는 여러 스레드를 동시에 돌리고 결과를 모아주는 도구입니다. SET LOCAL lock_timeout은 "이 트랜잭션이 잠금을 얼마나 기다릴지" 상한을 거는 PostgreSQL 설정으로, 락 버그가 있을 때 테스트가 영원히 멈추는 대신 실패로 드러나게 해줍니다.

3. 무엇을, 왜 이렇게 만들었나

파일구분무엇을 왜

참고 — 진행 중 있었던 일
