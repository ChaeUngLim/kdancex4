## 0. 먼저 알아 둘 현황

1. **서버 쪽 소스는 아직 없다.** `admin-web/app/` 에는 `page.tsx`·`refund-policy/` 뿐이고 `app/api/` 가 없다(`find` 로 확인). `admin-web/lib/` 에는 순수 계산(`domain/` 5개)과 포트·가짜 구현(`server/ports`, `server/fakes`)만 있다. mobile 은 화면 10종이 `/api/...` 를 부르도록 짜여 있으나 받는 쪽 API 는 없다. 아래 표의 「소스 일부」는 이 뜻이다.
2. **플랜은 US1 1회차(수업 찾아 결제)** 만 다룬다. 멤버십, 대기, 회차 옮기기, 알림 설정, 내역·영수증, 탈퇴, 신고는 전부 플랜 밖이다(`01_req-analyst_requirements.md` 1-2·1-4 절).
3. **보드 글자 스냅샷 주의.** `board_texts.md` 에는 `gap_summary.md` §3-1 이 「고침」이라 적은 옛 문구가 그대로 남아 있다(M3 「모바일 학생증 또는 학생증 사진」, M18B 보드 이름 「월 멤버십 2개월째」). 이 보고서는 `board_texts.md` 를 보드 기준으로 삼았다.
4. FR 번호 뒤 괄호는 spec 색인 표(`spec:2196~`)의 짧은 이름이다.

## 2. 「없음·부분·어긋남」 항목별 상세

### 어긋남

**⑪ 결제 실패 안내와 재시도 — 어긋남**
- 한쪽: spec:782(공통 오류 카드 X2) 는 「결제가 실패하면 자리를 잡아 두지 않는다(2026-11-03 사용자 결정)」고 정했다. 다시 결제할 때 남은 자리가 있으면 그대로 진행한다.
- 다른쪽: FR-285(결제 기한, spec:1439)·FR-096(결제 대기 자리 잠금, spec:1080)은 결제를 시작하는 순간 자리를 `held` 로 잡고 기한까지 유지한다. 플랜 `03_contracts/03-checkout-payment.md` §1 의 7단계도 주문 생성 때 자리를 잡는다. 「카드 승인이 실패했을 때 `held` 를 즉시 풀고 주문을 어떤 상태로 보내는가」는 어느 문서에도 없다. `FR-298(주문 상태 6종)` 에도 결제 실패 전이가 없다(`pending → paid/expired/cancelled` 뿐).
- 비어 있는 것: 실패 주문의 상태·재시도 횟수·같은 주문 재사용 여부, 가상계좌에는 「실패」가 없다는 점(발급 실패만 있음), 카드사 사유 문구 출처.
- 권장 문구: 「시스템은 카드·간편결제 승인이 실패하면 즉시 그 주문의 `held` 자리를 풀고 주문을 종료 상태로 두며, 회원이 다시 결제하면 새 주문으로 자리를 다시 잡아야 한다.」「시스템은 결제 실패 시 PG 가 알려 준 실패 사유를 회원에게 보여 주고 돈이 청구되지 않았음을 함께 알려야 한다.」

**⑱ 회원 취소(기한·수수료) — 어긋남**
- spec: FR-098(대표 처리 환불 방식, spec:1082)·FR-098b(spec:1086)는 정규·일반 수업의 환불을 「문의 → 대표가 규정대로 결정·실행」으로만 둔다. 24시간 규칙과 비율표 자동 계산은 폐지(spec:37, Q11 ② 「기존 환불 계산 코드 폐기」). 이벤트형만 회원이 예약 상세에서 직접 취소하고 시스템이 FR-099c(spec:1091) 표로 계산한다.
- 소스·플랜: `admin-web/lib/domain/refund-policy.ts:1-14` 가 옛 규칙(24시간 이상 전액, 그 안은 학원 비율표)을 그대로 옮겼고, `mobile/app/reservation/[id]/cancel.tsx` 는 「예상 환불액·환불율」을 보여 주고 회원이 환불 계좌를 입력해 취소를 확정한다. `03_contracts/05-cancellation-migrated.md:5` 가 「동작 보존 이관」을 원칙으로 못박았고, plan `D12`(`03_impl-planner_plan.md:47`)·`U4`(`:204`)가 spec FR-293~295 와의 정렬을 SCH-32(정규 과정 환불)로 미뤘다.

- 있는 것: 자동 갱신 안 되는 수단(일반 계좌이체·가상계좌)은 기간 종료 3일 전 앱 알림(FR-112, spec:1160). 가격 인상·혜택 축소는 앱 알림 개별 안내(약관 제9조 ④). 결제 화면에 자동 갱신 여부 표시.
- 빈 것: **자동 갱신 수단(카드·자동이체)의 갱신 전 고지**가 없다. 갱신일·금액·해지 방법을 며칠 전에 알리는지. 소비자 분쟁이 잦은 영역이라 법무 검토 대상으로 올릴 만하다. 보드는 갱신 완료 알림(M21)만 있다.
- 권장: 「시스템은 자동 갱신 멤버십의 갱신일 [N]일 전에 갱신일·결제 금액·결제 수단·해지 방법을 앱 알림으로 보내야 한다.」

**㉛ 결제 실패 시 처리(재시도·혜택 중단) — 부분**
- 있는 것: FR-113(spec:1192) 한 문장 「재시도 정책에 따라 처리하고 사용자에게 통지」. 약관·정책 문서에도 정책 값 없음.
- 빈 것: **재시도 정책 자체**(횟수·간격), 재시도 중 혜택 유지 여부(유예기간), 최종 실패 시 멤버십 종료 시점·AI 검색·대기·학원 소식 잠금(FR-112d 의 불투명 유리), 쿠폰 처리, 회원에게 보내는 알림과 결제 수단 변경 안내. 보드 없음(`sweep_B.md:18`).
- 권장: 「시스템은 멤버십 자동 결제가 실패하면 [N]일 동안 [M]회 재시도하고 매 실패마다 회원에게 사유와 결제 수단 변경 방법을 알려야 하며, 끝까지 실패하면 멤버십을 종료하고 전용 혜택을 잠가야 한다.」

**㊳ 알림 설정(종류별) — 부분**
- 있는 것: 수업 전 알림 시점 4종 선택(FR-140), 광고성 동의 분리(FR-146), 학원 구독별 소리·무음·끔(spec:790~800), 알림함 종류 칩(FR-144 하위). 거래 알림은 설정과 상관없이 온다(spec:800).
- 빈 것: 설정 화면의 구성과 항목 목록(어떤 알림 종류를 켜고 끄는지, 대기·쿠폰·레벨 알림을 끌 수 있는지), 기기 푸시 권한과 앱 내 설정의 관계. M12·M21 에 `알림 설정 ›` 줄만 있고 화면이 없다(`sweep_C.md:9`).
- 권장: 「시스템은 알림 설정 화면에서 수업 전 알림 시점, 광고성 수신 동의, 대기·쿠폰·학원 소식 알림의 켜고 끔을 보여 주고 거래 알림(결제·환불·변경)은 끌 수 없음을 안내해야 한다.」

**㊵ 신고 — 부분**
- 있는 것: FR-188(신고 처리, spec:1855) 한 줄, FR-255(서비스 밖 거래 신고, spec:1808), FR-254(이용 제한 절차, spec:1807: 사유 통지 → 소명 → 조치).
- 빈 것: 신고 대상(회원·강사·학원·수업·문의 답변?), 신고 사유 분류, 신고하는 진입점, 신고자 통지·결과 알림, 허위 신고 처리, 접수 후 누가 받는지(운영자? 약관 제11조 ① 「신고는 회사가 받는다」). 보드·소스·플랜 없음.
- 권장: 「시스템은 회원이 학원·강사·수업 화면에서 사유를 골라 신고하게 하고, 접수 사실과 처리 결과를 신고자에게 알려야 한다.」

**㊶ 탈퇴·계정 삭제 — 부분**
- 있는 것: 앱 안 탈퇴(약관 제4조 ③), 법정 보관 기록 분리(FR-190, spec:1857 · 처리방침 §1·§5), 재가입 혜택 차단(FR-010), 보호자 탈퇴 때 자녀 정보 삭제(FR-009a).
- 빈 것: **진행 중 예약·환불·정산이 있을 때 탈퇴 허용 조건**(차단할지 자동 취소할지), 입금 대기 주문 자동 취소, 남은 쿠폰·멤버십 기간 소멸 고지, 환불 pending 건 처리, 탈퇴 확인 화면, 유예 기간. 약관은 「이 약관에 따라 처리한 뒤 삭제」 한 줄. 보드에 탈퇴 줄 없음(`sweep_C.md:123`).
- 권장: 「시스템은 회원이 탈퇴를 요청하면 진행 중인 예약·환불·입금 대기를 보여 주고, 처리되지 않은 환불이 있으면 완료 뒤 삭제하며, 남는 쿠폰·멤버십 혜택이 사라진다는 점을 확인받아야 한다.」

**㊷ 개인정보 열람·삭제 — 부분**
- 있는 것: 처리방침 §5 가 열람·정정·삭제·처리정지 권리를 적었고 FR-190 이 삭제 요청을 요구한다.
- 빈 것: **열람·정정·처리정지에 해당하는 FR 이 없다**(FR-190 은 삭제만). 앱 안 열람 화면(내가 낸 정보·제3자 제공 내역), 요청 후 처리 기한, 요청 접수 창구. 처리방침이 앱이 하지 않는 기능을 약속한 상태다.
- 권장: 「시스템은 회원이 앱에서 자신의 개인정보를 열람·수정하게 하고, 처리정지와 삭제 요청을 접수해 [N]일 안에 처리 결과를 알려야 한다.」

## 3. 추가 발견 (J)

1. **푸시 알림 권한 요청과 기기 푸시 연결** — 근거: 「푸시 권한」「알림 권한」 spec 0건, `mobile/package.json` 에 알림 패키지(expo-notifications) 없음. FR-114 등은 「앱 내 알림」을 정하고 FR-146 은 「휴대폰 푸시」(spec:1328)를 전제하지만 OS 권한 요청 시점·거절 시 대체(알림함)·토큰 등록 규칙이 없다. 위치 권한만 보드(M20B)가 있다. 권장: 「시스템은 첫 결제 직후 또는 알림 설정에서 푸시 권한을 요청하고, 거절하면 앱 알림함으로만 알려야 한다.」
2. **정규 과정 일시정지(홀딩)** — 근거: spec:2017 「다음 확장 후보(요구사항 아님)」에만 있다. 기간 단위 신청(FR-052a)이 있으면 부상·출장 요청이 곧바로 생긴다. 환불(㉒)·보강 크레딧 정의와 함께 정하는 게 좋다.
3. **본인확인 번호 변경·계정 복구** — 근거: 「번호 변경」「계정 복구」「계정 찾기」 spec 0건(FR-003 은 CI 로 1인 1계정만 규정). 휴대폰 번호를 바꾸거나 소셜 계정을 잃은 회원이 같은 CI 로 새 계정을 만들 수 없는 상태가 된다. 권장: 「시스템은 본인확인으로 같은 CI 의 기존 계정을 찾아 새 소셜 계정을 연결(계정 복구)하게 해야 한다.」
4. **기기 캘린더 내보내기** — 근거: 「기기 캘린더」「캘린더 연동」 0건, 계획서 Q9 가 「앱 안 캘린더 기록」으로 못박음(`03_contracts/04-me-calendar-notifications.md:3`). ⑮ 「캘린더 등록」을 앱 캘린더로 제한한 결정이 사용자에게 보이는 안내 문구로는 없다. 권장: 확정 화면에 「기기 캘린더에 추가(.ics)」 버튼을 둘지 결정.
5. **환불 요청 철회·문의 취소** — 근거: 「환불 요청 철회」 0건. 요청 후 마음이 바뀐 회원이 취소할 길이 없다(⑲와 한 묶음).
6. **수강 확인서·결제 증빙 발급(수강료 영수 외)** — 근거: 「수강확인서」「수료증」 0건. 현금영수증(FR-138)만 있고 소득공제용 교습비 납입 증명을 요구받는 수업에서 쓸 곳이 없다. 필요성은 학원 등록 형태(FR-085)에 달려 있어 우선순위는 낮다.
7. **점검·강제 업데이트 공지** — 근거: 「점검 공지」「강제 업데이트」 0건. 결제 중 점검으로 끊기는 사고를 막을 장치가 없다(X1 연결 오류 화면은 단순 끊김용).
8. **부분 환불·휴강 환불의 법정 소비자 고지(환불 영수)** — 근거: ⑳·㉒가 기록에는 있으나 회원에게 주는 환불 내역서(환불 사유·계산식·근거 규정 문구)는 FR-293 의 「근거 공지 항목」을 회원에게 보여 준다는 문장이 없다. FR-206(학원 환불 규정 근거)은 AI 답변용이다. 권장: 「시스템은 환불 완료 알림에 환불 금액·계산 근거·근거 공지 항목을 포함해야 한다.」
