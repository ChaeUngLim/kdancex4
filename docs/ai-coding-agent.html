개요 — 스택 전체 그림

인증 — Better Auth 확정, Clerk 보류

Better Auth 로 간다. 직접 통제하는 인증 라이브러리라 스키마와 흐름을 우리가 쥔다. Auth.js 프로젝트가 Better Auth 의 일부가 되었다고 공식 안내에 나와 있어 사실상 이쪽이 후속 라인이다. 미검증

Clerk 은 보류다. 관리형 인증이라 붙이기는 더 간단하지만 유료다. 사용자가 크게 늘어 직접 운영 부담이 커지면 그때 넘어간다 — 지금 미리 넘어갈 이유는 없다.

다만 Better Auth 는 Prisma 8 과 설치 단계에서 충돌한다. package.json 의 overrides 로 설치는 풀었고, 인증은 Prisma 를 거치지 않고 Kysely 로 같은 DB 에 붙는다(2026-09-24 스모크 통과). 자세한 내용은 최신을 고른 값에 있다.

PostgreSQL 18 vs @prisma/orm-postgres — 창고와 직원

이름에 둘 다 "postgres" 가 들어가서 같은 것 같지만 결정적 차이는 "혼자 도느냐" 다.

PostgreSQL 18.6@prisma/orm-postgres
정체독립 실행되는 프로그램앱 안의 파일 덩어리
어디에Docker 컨테이너 kdance-dbadmin-web/node_modules/
혼자 도나돈다. 앱을 꺼도 계속 켜져 있다안 돈다. 앱이 불러야 움직인다
데이터를 갖나갖는다. 디스크에 쌓인다없다. 전달만 한다
크기컨테이너522개 파일 · 5.6MB

PostgreSQL 은 창고다. 물건(데이터)이 실제로 쌓여 있는 별도 건물이다. 우리 사무실이 문을 닫아도 창고는 돌아가고, 창고가 멈추면 아무도 물건을 못 꺼낸다.

@prisma/orm-postgres 는 창고에 주문 넣는 직원이다. 우리 사무실 안에 앉아 있고, 창고 주소를 알고, 우리 말을 창고가 알아듣는 말(SQL)로 번역해 전화를 건다. 이 직원은 물건을 하나도 갖고 있지 않다.

둘을 잇는 끈이 접속 문자열이다.

postgresql://kdance:kdance@localhost:5433/kdance
             └──┬──┘ └──┬──┘ └──────┬─────┘ └──┬──┘
              아이디   비번      창고 주소     구역 이름
왜 직원을 두나

직원 없이 창고에 직접 전화할 수도 있다. 대신 이렇게 된다.

"SELECT * FROM reservatons WHERE id = " + id
                    ↑ 오타. 실행해봐야 안다. 사용자가 먼저 발견할 수도 있다

db.reservation.findMany({ where: { id } })
      ↑ 오타면 빌드가 막는다. 사용자에게 가기 전에 잡힌다
숫자가 헷갈리는 이유

PostgreSQL 의 18 과 Prisma 의 8 은 아무 관계가 없다. 다른 회사가 각자 매기는 번호다. "아이폰 17" 과 "안드로이드 16" 이 서로 상관없는 것과 같다.

prisma vs @prisma/orm-postgres — 연장과 배관

이 둘은 이름이 비슷해서 중복처럼 보이지만 역할이 정반대다.

prisma@prisma/orm-postgres

실행파일bin 있음없음

연장은 공사가 끝나면 갖고 나온다. 배관은 집 안에 남아 실제로 물이 흐른다. Prisma 7 까지는 배관 이름이 @prisma/client 였고, 8 에서 DB 별로 쪼개지며 @prisma/orm-postgres 가 됐다. 연장 이름(prisma)은 안 바뀌었다.

CLI 가 rc.15 인데 런타임이 rc.11 인 것도 정상이다 — 별개 패키지라 각자 센다. 앞의 8 이 같으면 맞는 짝이고, 뒷숫자가 어긋나 보여도 문제가 아니다.

RC 를 쓰는 대가

정식이 아니라서 어느 날 쓰는 법이 바뀔 수 있다. 정식 전에는 그게 허용된다. 그래서 고정표 「11-2. 알려진 위험」에 감수로 적어 두었다 — 알고도 받아들인 위험이라는 뜻이다. Prisma 8 을 고른 이유(AI 코딩 에이전트 지원)가 8 에만 있어서 안정판 7 로는 그 기능을 아예 쓸 수 없기 때문이다.

dist-tags — 초보가 꼭 걸리는 함정

$ npm view prisma version
8.0.0-rc.15        ← "최신이 RC 네?"

보통 latest 는 정식판을 가리키는데, Prisma 는 latest 태그를 RC 에 달아 두었다. 안정판 7.10.0 은 prev 라는 다른 이름표 밑에 있다.

그래서 npm view <패키지> version 만 믿으면 RC 를 정식인 줄 알고 깐다. 이름표 전체를 보려면 npm view <패키지> dist-tags 를 쓴다.

peer · transitive — 누가 누구를 데려오나

말뜻이 프로젝트의 예
dependency내가 직접 쓰려고 선언한 것next, zod
peer dependency"너도 이거 깔아야 나랑 같이 돈다" 고 요구하는 것. 직접 깔아주지는 않는다better-auth 가 요구한 prisma ^5 \|\| ^6 \|\| ^7
transitive내가 선언 안 했는데 남을 타고 딸려 들어온 것vitest · kysely · pg

transitive 가 위험한 이유는 내가 통제하지 못하기 때문이다. 위쪽 패키지가 마음을 바꾸면 조용히 사라진다. 자세한 내용은 지금 어디까지 왔나 의 "표에 없는데 깔려 있는 것" 참고.

계약(contract) — Prisma 8 의 핵심 개념

Prisma 7 까지는 new PrismaClient() 로 만능 객체 하나를 만들어 썼다. 8 은 먼저 "계약서" 를 만들고 그 계약서에 적힌 것만 할 수 있게 바뀌었다.

contract.prisma   ← 사람이 쓰는 설계도 (어떤 테이블, 어떤 컬럼)
      ↓ prisma contract emit
contract.json + contract.d.ts   ← 기계가 읽는 계약서 (자동 생성. 손으로 안 고친다)
      ↓
postgres<Contract>({ contractJson, url })   ← 계약서를 쥔 db 객체

계약서에 없는 테이블을 부르면 코드를 돌리기 전에 타입이 막는다. 이게 8 이 얻은 안전장치이고, 동시에 7 의 코드가 8 에서 그대로 안 도는 이유다.

핵심 규칙

호환되는 선에서 최신을 쓴다.
"최신"과 "의존성 호환"이 충돌하면 호환이 이긴다.

이 규칙은 .claude/rules/core-rules.md 「버전 정책」에도 같은 문장으로 들어 있다. 두 곳이 어긋나면 core-rules.md 가 원본이다.

규칙에 딸린 조건이 하나 더 있다. 버전을 기억으로 쓰지 않는다. 학습 시점 이후에 나온 버전이 항상 있기 때문에, 말하거나 적기 전에 실제 파일이나 레지스트리에서 읽는다. 아래 버전을 확인하는 법에 어디서 읽을지 적어 두었다.

이 문서를 읽는 법

항목마다 실측 또는 미검증 이 붙어 있다. 실측은 2026-09-20 에 실제로 명령을 돌려 출력을 확인한 것이고, 미검증은 공식 문서나 릴리스 노트에만 있고 아직 이 프로젝트에서 돌려보지 않은 것이다. 섞어서 읽으면 나중에 무엇을 믿을지 알 수 없게 된다.

왜 최신을 고르나

기능이 더 많아서가 아니다. AI 코딩 에이전트가 다룰 수 있는 형태로 바뀌었기 때문이다. 같은 일을 하는 도구라도, 사람이 읽는 로그를 뱉느냐 기계가 파싱하는 JSON 을 뱉느냐에 따라 에이전트의 작업 품질이 갈린다.

kdance 는 혼자 개발한다. 사람 팀이면 저절로 나뉘는 역할(DB 담당·프론트 담당·QA 담당)을 에이전트가 대신 맡아야 하고 그러려면 도구가 에이전트에게 말을 걸 수 있어야 한다. 그게 최신을 고른 이유다.

Prisma 8 RC

CLI 가 사람이 아니라 기계에게 말한다 실측

8 의 CLI 는 사람이 읽는 줄글 대신 구조화 JSON 을 뱉는다. 실제 출력이다.

$ npx prisma --version

{"kind":"result",
 "envelope":{"ok":true,
             "commandId":"version",
             "result":{"version":"8.0.0-rc.15"},
             "exitCode":0,
             "diagnostics":[],
             "nextActions":[]},
 "commandId":"version",
 "timestamp":"2026-09-20T09:09:27.389Z"}

ok 로 성공 여부를, diagnostics 로 경고를, nextActions 로 다음에 할 일을 읽는다. 에이전트가 정규식으로 로그를 긁을 필요가 없다. 이 한 가지 때문에 Prisma 8 을 골랐다.

런타임 패키지 이름이 바뀌었다 실측

7 계열까지의 런타임은 @prisma/client 였다. 8 의 런타임은 @prisma/orm-postgres 다. 옛 이름만 조회하고 "8 이 없다"고 결론짓는 일이 실제로 일어난다.

그리고 8 부터 CLI 가 ORM 을 넘어 플랫폼으로 넓어졌다(auth·project·postgres·bucket·branch·git·service·deploy·dev). ORM 은 prisma orm 서브커맨드 아래로 들어갔다.

ESM 이지만 소비자까지 ESM 일 필요는 없다 실측

@prisma/orm-postgres 의 package.json 은 "type": "module" 이다. 그래서 소비하는 쪽도 ESM 이어야 한다고 적어 둔 적이 있는데, 확인해 보니 그렇지 않았다. CommonJS 기본값인 admin-web 에서 그대로 해결된다.

$ node --input-type=module -e "import('@prisma/orm-postgres/runtime')..."

import OK, exports: PostgresRuntimeImpl, buildNamespacedNativeEnums,
                    default, isPgClient, isPgPool

다만 prisma.config.ts 를 Node 가 직접 실행할 때는 다를 수 있다. 스캐폴딩 단계에서 확인한다.

접근 방식 미검증

아래는 공식 문서의 형태다. 이 프로젝트에서 아직 돌려보지 않았다.

prisma orm init --target postgres --authoring psl
  → src/prisma/contract.prisma      (PSL 데이터 계약)
    prisma.config.ts
    src/prisma/db.ts

prisma contract emit
  → contract.json + contract.d.ts
import postgres from '@prisma/orm-postgres/runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
});

pg 가 딸려 온다 실측

Prisma 8 의 Postgres 런타임은 내부적으로 pg 를 쓴다. 따로 설치하지 않아도 의존성 트리에 들어온다.

@prisma/orm-postgres@8.0.0-rc.11
└─ @prisma/orm-target-postgres@8.0.0-rc.11
   ├─ pg-cursor@2.22.0 → pg@8.22.0
   └─ pg@8.22.0

인증을 Postgres 직결로 붙일 계획이라면 이게 이미 깔려 있다는 뜻이다.

AI SDK 7 · LangGraph · MCP

2026-09-24 — 에이전트는 별도 TypeScript 서버에서 돈다

CLAUDE-decisions.md ADR-003. 에이전트 런타임은 Next.js 안이 아니라 별도 Node 프로세스(Hono + LangGraph JS + AI SDK)다. 중간에 Python 안(ADR-002)을 거쳤지만, Qwen 비전이 포스터를 OCR 없이 읽고 그 호출이 AI SDK 로 된다는 실측으로 되돌렸다. 이 절의 @langchain/langgraph·@langchain/core 는 에이전트 서버로 옮긴다. ai(채팅 UI)와 MCP SDK(도구 서버)는 Next.js 에도 남는다. llama-server 를 부를 때는 @ai-sdk/openai-compatible 에 supportsStructuredOutputs: true 를 준다 — 빠뜨리면 스키마 없이 json_object 만 가서 마크다운이 돌아온다. 에이전트에게: Next.js 코드에 LangGraph 그래프를 새로 만들지 않는다. 에이전트 서버는 DB 에 접속하지 않는다 — 데이터는 Next.js 가 여는 도구로만 읽고, 벡터는 계산만 해서 Next.js 에 넘긴다.

세 패키지 모두 라인 자체를 올렸다. ai 6.x 와 @langchain/langgraph 1.2.x 는 구세대 에이전트 API 라, 에이전트 기능을 쓰려면 올려야 한다. 미검증 — 릴리스 노트 기준이고 이 프로젝트에서 아직 코드로 확인하지 않았다.

패키지버전요구 Node
ai7.0.113>=22
@langchain/langgraph1.4.17>=18
@langchain/core1.2.12langgraph 가 ^1.1.48 로 요구
@modelcontextprotocol/sdk1.30.1>=18

@langchain/core 는 직접 쓰지 않더라도 표에 적어 둔다. LangGraph 를 올릴 때 같이 움직이는 값이라, 적어 두지 않으면 다음 사람이 왜 이 버전인지 알 수 없다.

zod 4 — 보이지 않는 공유 층

위 세 패키지가 전부 zod 를 peer 로 요구한다. 각자 범위가 달라서 하나라도 어긋나면 조용히 깨진다.

ai@7.0.113                        ^3.25.76 || ^4.1.8
@langchain/langgraph@1.4.17       ^3.25.32 || ^4.2.0
@modelcontextprotocol/sdk@1.30.1  ^3.25    || ^4.0
                       교집합  →  zod >= 4.2.0

그래서 zod 4.6.5 를 고정표에 명시적으로 올렸다. 설치 후 실제로 하나로 수렴했는지 확인했다. 실측

중첩 zod 개수: 0        ← node_modules 안에 zod 사본이 하나뿐
왜 표에 적어야 하나

zod 는 우리가 직접 설치할 생각을 안 하는 패키지다. 표에 없으면 나중에 누가 다른 이유로 zod 3.x 를 깔고, 셋 중 하나가 런타임에 조용히 어긋난다. 공유되는 전이 의존성은 직접 쓰지 않아도 표에 올린다.

소스에 반영하는 법

여기부터는 코드를 쓸 때 지키는 규약이다.

1. Prisma 는 계약으로 접근한다

new PrismaClient() 를 쓰지 않는다. 8 에는 그 API 가 없다. contract.json + contract.d.ts 를 생성해 타입이 박힌 db 객체를 만들고, 그것만 import 한다. 생성물은 손으로 고치지 않는다 — 고쳐야 하면 contract.prisma 를 고치고 다시 emit 한다.

2. 에이전트가 CLI 를 부를 때는 JSON 을 읽는다

Prisma CLI 출력을 줄글로 파싱하지 않는다. envelope.ok 로 성공을 판정하고, envelope.diagnostics 를 경고로 올리고, envelope.nextActions 가 비어 있지 않으면 그걸 다음 단계 후보로 쓴다.

3. 스키마는 zod 한 곳에서 정의한다

ai 의 tool 정의, LangGraph 의 상태, MCP 도구 스키마가 전부 zod 를 쓴다. 에이전트 서버와 Next.js 가 같은 언어라 이 스키마를 두 서버가 그대로 나눠 쓴다(ADR-003). 같은 개념을 세 번 정의하지 않고 한 번 정의해 세 곳에서 재사용한다. 버전이 하나로 수렴해 있어야 이게 성립한다.

4. 버전을 소스에 하드코딩하지 않는다

런타임에서 버전을 문자열로 비교하는 코드를 쓰지 않는다. RC 라 값이 자주 바뀐다. 필요하면 기능 존재 여부로 분기한다.

5. 프리릴리스는 캐럿 없이 고정한다 실측

npm 은 설치할 때 캐럿을 자동으로 붙인다. ^58.0.0-preview.3 은 58 안정판이 나오면 거기로 넘어가고, ^0.88.0-rc.0 은 0.88 안정판으로 넘어간다. RC 를 쓰기로 한 이상 어느 RC 인지가 재현성의 전부이므로 캐럿을 떼고 정확한 값으로 적는다.

최신을 고른 값

최신을 고르면 대가가 따른다. 숨기지 않고 적어 둔다.

Better Auth 가 Prisma 8 을 받지 않는다 실측

better-auth@1.7.5 와 @better-auth/prisma-adapter@1.7.5 의 peer 가 둘 다 Prisma 8 을 배제한다. 그리고 설치가 실제로 막힌다.

npm error Could not resolve dependency:
npm error peerOptional prisma@"^5.0.0 || ^6.0.0 || ^7.0.0" from better-auth@1.7.5
npm error Found: prisma@8.0.0-rc.15
함정 — optional 은 "아무 버전이나"가 아니다

peerDependenciesMeta 가 optional: true 라 설치가 그냥 통과할 거라고 적어 둔 적이 있는데 틀렸다. optional 은 "없어도 된다"는 뜻이지 "있으면 아무 버전이나 된다"가 아니다. Prisma 8 이 이미 설치돼 있으면 npm 이 범위를 검사해서 거부한다.

두 패키지 모두 최신이 1.7.5 라, 올려서 풀 수 없다. 구조도 안 맞는다 — 어댑터는 new PrismaClient() 를 전제하는데 8 에는 그게 없다.

해결 — overrides 로 이 한 건만 끈다 실측

--legacy-peer-deps 로 뚫을 수도 있지만 그러면 peer 검증을 통째로 포기한다. 방금 이 충돌을 제대로 잡아낸 게 그 검증이다. 대신 package.json 에 override 를 하나 넣는다.

"overrides": {
  "better-auth": { "prisma": "$prisma" }
}

better-auth 가 선언한 prisma peer 범위를 루트의 버전으로 덮어쓴다. 우리는 prisma 어댑터를 쓰지 않으므로 그 제약이 우리 구성에 해당하지 않는다. 플래그 없는 npm install 이 exit 0 으로 통과한다.

--legacy-peer-depsoverrides (채택)
기록없음 — 매번 손으로package.json
다른 PC · CI깨진다동작한다
peer 검증전부 끈다이 한 건만 끈다

어댑터는 막을 수 없고, 막을 필요도 없다 실측

@better-auth/prisma-adapter 는 optional peer 가 아니라 better-auth 의 정식 dependency 다. better-auth 가 백엔드별 어댑터(drizzle·kysely·memory·mongo·prisma)를 전부 번들로 들고 다니므로 설치를 막을 방법이 없다. 설정에서 고르지 않으면 그냥 쓰이지 않는다.

쓸 것은 따로 있다. kysely 가 better-auth 의 직접 의존성이고, 어댑터가 Postgres 용 함수를 내보낸다.

import('@better-auth/kysely-adapter')
→ createKyselyAdapter, kyselyAdapter, getPostgresSchema, ...

Postgres 직결은 임시방편이 아니라 정식 지원 경로다. Prisma 8 이 앱 ORM 을 맡고, 인증은 같은 DB 에 kysely/pg 로 붙어 스키마만 공유한다. 실제 인증 동작도 돌려 봤다. 실측

kdance_test · 임시 스키마 auth_smoke · database: new pg.Pool(...)   (2026-09-24)
PASS  테이블 생성 — account,session,user,verification
PASS  재실행 시 추가 변경 없음
PASS  회원가입 · 비밀번호 해시 저장(평문 아님)
PASS  로그인 + 세션 쿠키 발급 · 쿠키로 세션 조회
PASS  틀린 비밀번호 거부 · 로그아웃 후 세션 무효
PASS  public 스키마 침범 없음

드라이버 pg@8.22.0 은 따로 깐 게 아니라 @prisma/orm-postgres 가 가져온 것이다. Prisma 8 과 Better Auth 가 같은 드라이버를 쓴다. 초기화 때 찍히는 Database schema mismatch 로그는 테이블이 생기기 전이라 나오는 것이고, 마이그레이션 뒤에는 사라진다.

아직 확인하지 않은 것: Prisma 8 계약과 인증 테이블의 관계다. 계약에 없는 user·session 을 Prisma 마이그레이션이 어떻게 다루는지, 예약·결제가 user 를 외래키로 어떻게 참조할지는 Phase 3(구현 계획)에서 정한다. 미검증

TypeScript 는 6.0.3 이다 — 7 로 올리지 않는다 실측

npm latest 는 7.0.2 지만, 설치된 패키지 두 곳이 6 을 요구한다.

peer typescript@">=4.8.4 <6.1.0" from typescript-eslint@8.70.0
$ npx expo install --check   # 7.0.2 일 때
typescript@7.0.2 - expected version: ~6.0.3

반대로 7 을 요구하는 패키지는 하나도 없다. Next.js 16.3.5 는 TypeScript peer 를 선언하지 않고 코드상 최소 5.1.0 만 검사한다. 설치된 16.3 문서(dist/docs/.../02-typescript.md)도 TS 6 을 기본으로 두고, 7 은 JavaScript API 가 없어 tsc CLI 로 돌려 쓰는 방식으로 설명한다. Instant Navigations·개발 서버 메모리 절감·dist/docs/AGENTS.md 는 Next 런타임·번들러 기능이라 TS 버전과 관계없다. 2026-09-23 에 6.0.3(~6.0.3)으로 내렸고 next build 성공, mobile tsc --noEmit exit 0, Expo 의 TS 경고가 사라졌다.

에이전트에게: typescript 를 7 로 "최신화"하지 않는다. typescript-eslint 가 7 을 지원하면 그때 함께 올린다.

admin-web lint 는 설정 파일 문제로 아직 깨져 있다 실측

TS 를 내린 뒤에도 npm run lint 는 Converting circular structure to JSON 으로 죽는다. eslint.config.mjs 가 FlatCompat 으로 next/core-web-vitals 를 감싸는 옛 방식이라서다. 16.3 문서는 eslint-config-next/core-web-vitals 를 직접 import 한다. 그 전까지 타입 검증은 next build 로 한다.

RC 를 두 개 쓰고 있다

Prisma 8 RC 와 Expo 58 preview × RN 0.88 RC 다. 안정판 전까지 breaking change 가 올 수 있다는 걸 받아들인 선택이다. 각각 안정판이 나오면 옮긴다.

올리기 전에

  • 그 패키지를 고정하는 상위 패키지가 있는지 먼저 본다
  • peerDependencies 로 표 안의 다른 항목과 충돌하는지 본다
  • 메이저가 올라가면 패키지 이름과 API 가 재편됐는지 확인한다
  • 깨져 있는 검증선과 겹치지 않게 순서를 나눈다. 한 번에 둘을 건드리면 원인 분리가 안 된다
  • 올린 뒤 실제로 돌려 본다. 레지스트리 조회만으로 "된다"고 하지 않는다
미검증은 미검증이라 적는다

확인하지 못한 항목을 확인한 것처럼 적지 않는다. 이 문서의 미검증 표시가 그 약속이고, 돌려본 뒤에는 실측 으로 바꾸고 근거가 된 출력을 함께 남긴다.
