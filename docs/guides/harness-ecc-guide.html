1. 핵심 질문 두 개

이 프로젝트는 혼자 Claude Code로 개발합니다. 사람 팀이면 "DB 담당·프론트 담당·QA 담당"으로 저절로 역할이 나뉘지만, 혼자 할 때는 그 역할 분담을 Harness가 대신 해주고, 코드 품질 관리는 ECC가 대신 해줍니다. 이 둘은 서로 다른 질문에 답합니다.

🏗

Harness

"이 큰 작업을 누구에게 어떤 순서로 시킬까?"
Agent Orchestration Layer · 프로젝트 레벨
🛡

ECC

"이 코드를 어떻게 하면 제대로 만들 수 있지?"
Software Engineering Quality Layer · 엔지니어링 레벨
최종 중심축
이 프로젝트의 뼈대는 Harness(작업 지휘) + ECC(품질 보증) 둘뿐입니다. Playwright·MindPilot·Visual Guide 같은 나머지는 이 둘과 경쟁하지 않고 그 위에 얹히는 실행 도구·설명 도구입니다.

5. Harness 상세 — 5대 업무

Harness는 코드를 직접 짜지 않습니다. "누구에게 무엇을 어떤 순서로" 시킬지만 결정합니다.

#업무내용연결 단계
①요구사항 → 작업 분해예: 예약 기능 → DB Schema / Backend API / Service / Payment / Notification / Next.js / React Native / Admin / E2E1.요구사항 분석 ~ 3.구현 계획
②Agent Team 구성·배정DB / Backend / Frontend / Payment / Notification / AI / QA Agent 중 누가 뭘 할지4.Task 분리
③작업 의존성 관리DB 완료 → Backend 완료 → Frontend 구현 → Integration → E2E 순서 강제4.Task 분리
④병렬 작업의존성 없는 작업은 동시 진행(예: DB 완료 후 Frontend와 Admin UI를 같이)5.구현 팬아웃
⑤Agent 결과 취합각 Agent 산출물을 하나의 기능으로 통합 + 학습 주석/가이드5.구현 ~ 9.5.학습 주석/가이드

6. ECC 상세 — 6대 업무

Harness가 "Backend Agent야 예약 API 만들어"라고 시키면, ECC는 그 결과물에 "테스트 있나? SQL Injection 가능성은? 권한 체크 했나? 에러 처리는? 타입 안전성은?"을 묻습니다.

#업무내용
①TDD요구사항 → Test → Implementation → Test → Refactor 순환. "테스트부터 제대로 작성했나?"
②Code Review버그 / 중복 / 복잡도 / 유지보수성 / 설계 문제
③Security예약·결제가 있는 이 프로젝트에서 특히 중요. 인증 / 권한 / 입력 검증 / 민감정보 / API 보호 / Webhook 검증 / 결제 위변조
④Refactoring거대 파일(예: 예약 코드 1,000줄)을 Service / Repository / Domain / Validator / DTO 등으로 분리
⑤Coding StandardPython(FastAPI/SQLAlchemy2/Pydantic), TypeScript(Next.js/React Native) 스타일 일관성
⑥테스트 품질Unit / Integration / Security / Regression Test — 실제 브라우저 E2E 실행은 Playwright가 담당

10. 절대 금지 패턴

❌ 나쁜 구조

Harness도 Plan → Implement → Test → Review를 돌고, ECC도 똑같이 Plan → Implement → Test → Review를 따로 돕니다.

→ "Harness가 계획을 세웠는데 ECC가 또 계획을 세우는" 중복·혼란이 생깁니다.

✅ 좋은 구조

Harness는 "무엇을·누구에게·어떤 순서로"만 정하고 두 번 다시 정하지 않습니다.

ECC는 그 결과물의 "품질"만 검사하고 순서·배정을 다시 정하지 않습니다.

11. 프로젝트가 커질 때 — 팀 조직
