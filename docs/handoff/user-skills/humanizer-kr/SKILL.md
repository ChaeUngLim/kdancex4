# Humanizer-KR: 한국어 AI 글쓰기 티 제거

**이 스킬은 어휘·조사·어미 층만 보는 가벼운 1패스 도구다.** 구조적
패턴(단정 대신 무대화 · 강제 3항 나열 · 대시 남발 · 과장된 의미 부여 ·
굵은 글씨 장식 등)은 보지 않는다 — 짧은 글에 매번 무거운 파이프라인을
돌리지 않으려는 의도된 트레이드오프다.

구조 층까지 필요하면 **`humanize-korean` 플러그인**을 쓴다. 어휘·구조를
한 번에 보고 정량 지표와 게이트로 과윤문까지 막는다. 아래 「어느 스킬을
쓸지」 표가 그 갈림을 정한다.

> 이전 버전은 영어권 구조 스킬 `humanizer`(blader)를 선행 단계로 두었으나,
> 그 역할을 `humanize-korean`이 흡수해 2026-09-19 의존을 끊었다.

## 무엇을 쓸지는 **① 언어 ② 장르** 두 축으로 정한다

**① 언어 — 이 스킬 자체를 쓸지.** 한국어면 쓴다. 영어면 이 스킬은 절대
안 쓴다(아래 ②와 무관하게 항상 이렇다).

**② 장르 — 이 스킬로 충분한지, `humanize-korean`을 쓸지.** 한국어라는 게
정해진 뒤에만 묻는 질문이다.

| 장르 | 한국어일 때 | 영어일 때 |
| --- | --- | --- |
| PR 본문 · 설명 문서(explainer) · 기술 문서 | `humanize-korean` (어휘+구조 전체) | 해당 없음 |
| 코드 리뷰 코멘트 · 질문 답변/대화체 · 이력서·자기소개서 | `humanizer-kr` **단독** (가벼운 1패스) | 아무 것도 안 씀 |

**흔들리기 쉬운 지점:** 이력서·자기소개서는 "문서"처럼 느껴지지만 위 표의
둘째 줄이다 — `humanizer-kr` 단독. 커밋 메시지 본문은 squash merge 관례상
PR 본문과 한 몸이라(`docs/WORKFLOW.md`) 첫째 줄로 친다.

## 원칙은 같다

`humanizer` 와 똑같이 **뜻을 안 바꾸고 티만 없앤다.** 없는 사실·숫자·이름·
경력·성과를 지어내지 않는다. 코드·데이터·frontmatter·링크는 손대지 않고
산문만 고친다. 글쓴이의 의견·말투·농담은 살리고, 기술 문서·레퍼런스는
중립적으로 유지한다.

## 쓰임새별 목소리

**이 표는 "무엇을 쓸지"를 정하지 않는다** — 그건 위 두 축이 이미 정했다.
여기서는 한국어 + 이 스킬을 쓴다는 게 정해진 뒤, 같은 K 패턴이라도 자리마다
고치는 방향이 다르다는 것만 본다.

| 자리 | 목소리 | 특히 조심할 것 |
| --- | --- | --- |
| 기술 문서 · 커밋 · PR · explainer | 중립·서술형. 팀 관례(`docs/WORKFLOW.md`)가 있으면 그걸 우선한다 | K1·K2·K4·K10 |
| 코드 리뷰 코멘트 | 직접적이고 구체적. 돌려 말하지 않되 사람에 대한 평가가 아니라 코드에 대한 평가로 쓴다 | K2(애매한 헤징으로 지적을 흐리는 것) · K4(상투적 칭찬 "좋은 접근입니다!") |
| 질문에 대한 답변 · 대화체 응답 | 자연스러운 구어체. 다만 챗봇 특유의 wrapper는 걷어낸다 | K7(챗봇 잔재) · K3(문장마다 접속부사) |
| 이력서 · 자기소개서 | 설득력 있는 개인 목소리. 성과는 구체적 수치·사실로 증명하고, 형용사로 부풀리지 않는다 | K6(근거 없는 자기 평가) · K11(자소서 상투구) · §13(과장된 의미 부여) |

## 왜 한국어 AI 문장은 이렇게 나오나

모델은 학습 데이터에서 가장 흔한 격식체 조합을 고른다. 그 결과가 **번역체
조사, 헤징(hedging) 종결어미, 기계적 접속부사, 상투적 도입·결론구**로 뭉친
"보고서 같은 한국어"다. 사람은 한 독자를 향해 쓰므로 문장 길이와 어미가
들쭉날쭉하고, 접속사를 문장마다 안 붙인다.

## 한국어 전용 패턴

### K1. 번역체 조사 — `~에 대한` · `~를 통해` · `~에 있어서` · `~로 인해`

**감지:** 이 넷이 한 문단에 반복해서 나오면 거의 항상 영어 전치사구를 그대로
옮긴 자리다.

| 전 | 후 |
| --- | --- |
| 이 기능**에 대한** 설명은 다음과 같다 | 이 기능은 이렇게 동작한다 |
| 캐시**를 통해** 응답 속도를 개선했다 | 캐시를 넣어 응답 속도를 개선했다 |
| 사용자 인증**에 있어서** 중요한 것은 | 사용자 인증에서 중요한 것은 |
| 네트워크 지연**으로 인해** 실패했다 | 네트워크가 늦어 실패했다 |

### K2. 헤징 종결어미 — `~것으로 보인다` · `~수 있다고 할 수 있다` · `~라고 판단된다`

**감지:** 확인된 사실을 굳이 완곡하게 낮춰 말하는 어미. 실제로 확인했으면
단정하고, 확인 못 했으면 "미검증"이라고 그 이유를 적는다 — 애매하게 눙치지
않는다 (`docs/WORKFLOW.md` 의 "미검증으로 남는 것을 반드시 적는다"와 같은
정신이다).

| 전 | 후 |
| --- | --- |
| 테스트가 통과한 것으로 보인다 | 테스트가 통과했다 |
| 성능이 개선되었다고 할 수 있다 | 성능이 개선됐다 (측정값을 붙인다) |
| 원인은 캐시 미스로 판단된다 | 원인은 캐시 미스다 / 캐시 미스로 추정되나 미검증이다 |

### K3. 기계적 접속부사 — 문장마다 `또한` · `그리고` · `하지만` · `따라서`를 붙이는 습관

**감지:** 문단의 문장 절반 이상이 접속부사로 시작하면 대개 필요 없다. 접속사
없이도 앞뒤 문장이 붙으면 지운다. 진짜 역접·인과일 때만 남긴다.

### K4. 상투적 도입·결론구 — `다음과 같습니다` · `아래와 같이 정리하면` · `결론적으로` · `요약하자면`

**감지:** 섹션마다 기계적으로 붙는 여닫이 문구. 한 문서에 "결론적으로"나
"정리하자면"이 두 번 이상 나오면 최소 하나는 지운다 — 내용이 이미 정리돼
있으면 그 말이 필요 없다.

### K5. 존댓말 격식 과잉 — 모든 문장을 `~습니다`체로 통일하며 리듬을 죽이는 것

**감지:** `humanizer` 의 §7(반복되는 문장 시작)과 같은 문제의 한국어판이다.
어미가 전부 `-습니다/-됩니다`로 끝나면 사람 글의 굴곡이 사라진다. 개조식
설명문(README·explainer)은 평서형(`-다`체)과 섞어 문장 길이를 들쭉날쭉하게
만든다. 다만 **커밋 메시지·PR 본문처럼 팀 관례가 이미 정해진 자리**는 그
관례(예: `docs/WORKFLOW.md` 의 서술형 어미)를 따르고 억지로 안 섞는다.

### K6. 근거 없는 권위 — `여러 연구에 따르면` · `전문가들은 ~라고 말한다` · `일반적으로 알려진 바와 같이`

**감지:** 출처를 못 대는 권위 인용. `humanizer` §17과 같은 문제다. 실제
출처(코드·문서·커밋)를 대거나, 못 대면 문장을 지운다.

### K7. 챗봇 잔재 한국어판 — `도움이 되셨길 바랍니다!` · `좋은 질문이네요!` · `궁금한 점 있으면 말씀해주세요`

**감지:** 대화형 도우미의 말투가 문서·커밋에 새어든 자리. 전부 지운다.

### K8. 장식용 이모지·화살표 헤딩 — `## 🚀 시작하기` · `### ✅ 완료`

**감지:** `humanizer` §20과 같지만 한국어 문서에서 특히 흔하다. 제목은
평서형 명사구로 정리하고 이모지·화살표를 뗀다. (`docs/` 프로젝트라면 그
문서 자체의 기존 헤딩 관례를 우선한다.)

### K9. 대칭 강박 — `~뿐만 아니라 ~도` 남발

**감지:** `humanizer` §1(Not X but Y)의 사촌. 모든 문장을 "A뿐 아니라 B도"
꼴로 맞추면 리듬이 단조로워진다. 뜻이 대칭이 아니면 그냥 따로 쓴다.

### K10. 코드 설명에서 — 이름이 이미 말해주는 것을 다시 서술하는 버릇

**감지:** `getUserById(id)` 를 "id를 받아 사용자를 반환하는 함수입니다"로
다시 풀어 쓰는 것. 이미 아는 사람에게는 잡음이다. 왜(WHY)·숨은 제약·부작용만
남기고 나머지는 지운다 — 이 저장소(mobydick)의 CLAUDE.md 원칙과도 같다.

### K11. 자소서·이력서 상투구 — `저는 ~한 사람입니다` · `이러한 경험을 통해 성장할 수 있었습니다` · `열정을 가지고 임했습니다`

**감지:** 자기소개서·이력서에서 가장 흔한 빈 문장. 자기 규정("저는 ~한
사람입니다")이나 뻔한 성장 서사("~를 통해 성장했습니다")는 아무 사실도
안 준다. `humanizer` §13(과장된 의미 부여)의 자소서판이다.

| 전 | 후 |
| --- | --- |
| 저는 책임감 있는 사람입니다 | (구체적 사례로 대체) 마감 하루 전 장애를 발견해 팀장에게 먼저 보고하고 원인을 고쳤다 |
| 이 프로젝트를 통해 많은 것을 배우고 성장할 수 있었습니다 | (배운 것을 구체적으로 — 무엇을 몰랐고, 무엇을 알게 됐는지) |
| 열정을 가지고 최선을 다했습니다 | (열정의 증거가 되는 행동 하나로 대체하거나 삭제) |

**의도:** 채용 담당자는 형용사가 아니라 사실을 본다. 형용사를 지우고 그
자리를 채울 사실이 없으면, 그 문장은 원래 필요 없었던 것이다.

## 점수 채점기는 한국어에서 못 믿는다 — 그래서 플러그인으로도 안 둔다

Aboudjem/humanizer-skill(0~100 AI-tell 점수를 주는 도구, 로컬에서는
`humanizer-check`로 이름 바꿔 한때 별도 플러그인으로 등록했었다)는
**영어 전용**이다. 토크나이저가 공백 기준 영단어 경계를 쓰고 AI-어휘
목록도 영어 단어라, 한국어 문장을 넣으면 `words: 1`처럼 단어 수 자체가
잘못 세어지고 `AI-vocab tells` 는 항상 0이 나온다 — 점수가 낮게 나와도
그건 "사람 같다"가 아니라 "이 도구가 한국어를 못 읽는다"는 뜻이다
(2026-09-07 실측: 4문단짜리 한국어 예문이 `words: 1`로 잡혔다).

이 한계 때문에, 그리고 한국어 산문은 어차피 이 스킬(K1~K11)로 사람이
점검하는 편이 정확해서, **`humanizer-check` 플러그인 등록은 제거했다**
(2026-09-07). 코드 자체는 `~/.claude/external/humanizer-aboudjem` 에
남아 있어 영문 텍스트(영어 커밋 메시지·영문 README 등)를 채점할 일이
생기면 `node cli/index.js score <file>` 로 수동 실행할 수 있다 — 플러그인
재등록 없이도 된다.

## 작업 순서

1. **어느 자리인지부터 정한다** — 위 「무엇을 쓸지」 표에서 PR 본문·문서
   장르인지(→ 이 스킬 대신 `humanize-korean`), 코드리뷰·Q&A·자소서인지
   (→ 2번부터 바로)를 가른다. 「쓰임새별 목소리」 표에서 목소리와 특히
   조심할 K 번호도 같이 확인한다.
2. **위 K1~K11 을 이 문서로 훑는다** — 한국어 조사·어미·접속부사·
   자소서 상투구 층을 본다. 구조적 티(무대화·3항 나열·대시·과장·굵은 글씨)는
   이 스킬의 범위가 아니다 — 필요하면 `humanize-korean`으로 간다.
3. 고친 결과를 소리 내어 읽듯 확인한다 — 문장 길이가 들쭉날쭉한가, 접속사
   없이도 흐름이 이어지는가, 헤징 어미가 실제로 필요한 자리인가.
4. 사실·숫자·이름·경력이 안 바뀌었는지 원문과 대조한다.

## 무엇을 돌려주나

**붙여넣은 텍스트:** 무엇을 고쳤는지(K 번호로) 짧게 나열하고, 최종본을
낸다.

**파일 지정:** 산문만 고치고 코드·데이터·frontmatter·링크는 그대로 둔다.
고친 뒤 무엇을 K 몇 번으로 고쳤는지 요약 한 줄을 남긴다.

**커밋·PR·explainer 안에서 쓰일 때:** 최종 텍스트만 돌려준다 — 이 스킬
이름이나 과정을 커밋 메시지 본문에 남기지 않는다.
