노트북 베타에서
운영 서버로

지금까지의 스택·무료 API 판단은 개인 개발자 노트북 기준이었다. 규모 목표가 "베타 1~10명 → 3년 이후 1천~1만 명"으로 바뀌었다(2026-09-24). 베타는 노트북 1대로 감당된다 — AI 동시 사용자 10명을 이 노트북에서 실측했다. 갭이 생기는 건 3년 이후 운영 단계(1천~1만 명)이고, 특히 AI 모델 서빙과 DB가 그렇다. 이 문서는 그 갭을 숨기지 않고 짚는다.

전환 · 01

노트북 → 운영 서버, 뭐가 바뀌어야 하나

같은 이름의 도구를 계속 쓰더라도, "어디서 도느냐"가 바뀐다. 노트북에서 멀쩡히 돌던 게 실 서비스에서 문제가 되는 지점만 골랐다. 베타(1~10명)는 노트북 그대로 간다 — 아래 표의 "이전 필수"는 운영 단계 (1천~1만 명) 기준이다. 서버 이전은 운영 단계로 넘어가기 전에 정한다.

컴포넌트지금(노트북)운영(1천~1만)바뀌는 이유
API 서버(FastAPI → Next.js) 내 PC, uvicorn --reload — Next.js 로 교체 예정(기술 스택 문서 11-3) 이전 필수 클라우드 VPS 2~4대 + 로드밸런서 내 PC가 꺼지면 서비스가 통째로 죽는다. 운영 서비스는 24시간 떠 있어야 한다. 베타는 시험 시간대에만 켜 두는 것으로 감수한다
DB(PostgreSQL+pgvector) Docker 컨테이너, 로컬 디스크 이전 필수 관리형 DB(백업·복제 자동) 또는 전용 서버 노트북 디스크가 죽으면 회원·결제 데이터가 통째로 사라진다. 운영부터는 매일 백업이 있어야 한다
채팅 AI(Qwen3.5 9B) llama-server(kdance-llm), 이 노트북 GPU 이전 필수 별도 GPU 서버 — 아래 02절 노트북 GPU 하나로는 동시 사용자 몇 명 이상에서 응답이 밀린다. 가장 큰 갭이라 따로 다룬다
AI 에이전트 서버(TypeScript) 내 PC, 아직 없음 — 새로 만든다(ADR-003) 검토 필요 GPU 서버 옆 또는 API 서버와 같은 VPS 에이전트는 LLM 을 여러 번 부르는 긴 작업이라 제품 API 와 떼어 둔다. DB 에는 접속하지 않고 API 서버의 도구(MCP)로만 데이터를 읽는다. 모델을 부르는 곳도 이 서버 하나다. 계산만 하므로 GPU 는 필요 없다
임베딩(로컬 소형 모델) Ollama, 채팅 AI와 같은 GPU 검토 필요 채팅 AI와 자리 다툼 — 별도 CPU 서빙 고려 검색·추천 요청이 늘면 채팅 응답과 GPU를 다투게 된다. 임베딩은 비교적 가벼워 CPU로 돌려도 되는 경우가 많다
Redis·APScheduler Docker, 로컬 그대로 서버로 옮기기만 하면 됨 도구 자체는 안 바뀐다. API 서버와 같은 곳으로 이사만 간다
오브젝트 스토리지(MinIO) 로컬 디스크 검토 필요 디스크 용량 실측 후 결정 포스터 원본이 쌓이는 속도를 먼저 재야 한다 — 학원 수 × 업로드 빈도로 추정 가능. 감당되면 셀프호스팅 유지, 넘으면 Cloudflare R2
카카오 Local·PG·Expo Push 클라우드 API 그대로 호출 그대로 이미 클라우드라 노트북 여부와 무관 애초에 내 PC 자원을 안 쓰는 것들이라 전환 대상이 아니다
병목 · 02

AI 모델 서빙 — 가장 먼저 막힐 자리

Qwen3.5 9B 자체를 바꾸자는 게 아니다. "어디서 돌리느냐"가 이 규모에서 갈리는 지점이다.

⚠ 노트북 GPU 1대는 베타까지다 — 숫자로 보면

실측(2026-09-24) — Ollama 0.33.3은 Qwen3.5를 병렬로 돌리지 않는다 (OLLAMA_NUM_PARALLEL을 줘도 한 번에 1건). 같은 모델 파일을 llama-server로 직접 띄워 슬롯 10개로 돌리니, 동시 10명 답 완료 p95가 55.4초 → 15~18초로 줄었다. 예전 이 자리의 "체감상 1~4건"은 추정이었다. 근거: specs/001-ai-dance-class-platform/local-ai-capacity.md

베타(최대 10명)는 이 수치 안에 들어온다. 운영(1만 명)에서 채팅을 쓰는 비율을 5%로 잡으면 500명이고, 저녁 피크에 수십 명이 동시에 몰리면 노트북 1대의 동시 10건을 넘어 대기열이 분 단위로 밀린다. 이 계산은 추정이다 — 실제 비율은 베타에서 잰다.

옵션 A

저가 GPU 클라우드 1대

RunPod·JarvisLabs 등에서 RTX 4090급 인스턴스를 시간당 $0.34~0.59에 빌려 Qwen3.5 9B를 그 위에서 돌린다. 노트북의 llama-server 구성(infra/docker-compose.yml)을 거의 그대로 옮긴다.

트레이드오프: "완전 무료"가 깨진다 — 24시간 기준 월 약 $250~430. 대신 동시 처리가 8GB 노트북보다 훨씬 나아진다
옵션 B

사용량 제한 + 대기열

채팅 AI 요청에 사용자당 일일 횟수 제한을 걸고, 초과 대기는 "순서대로 답변 중입니다" 큐 화면으로 보여준다.

트레이드오프: 비용은 0에 가깝지만, 베타 체감 품질이 떨어진다 — AI 챗봇이 "핵심"이라던 원래 방향과 부딪힌다
옵션 C

AI 챗봇 범위를 좁힌다

"추천·가격·경로"처럼 매번 LLM이 필요 없는 질문은 규칙 기반(필터+정렬)으로 먼저 처리하고, LLM은 자유 대화형 질문에만 쓴다.

트레이드오프: 개발 공수가 늘지만, 같은 GPU로 훨씬 많은 사용자를 감당한다 — LLM 호출 자체가 줄어드니까

추천 — B+C를 먼저, A는 베타 반응과 운영 전환 시점을 보고 결정. 처음부터 월 $300을 쓰기보다, LLM 호출을 줄이는 설계(C)와 사용량 제한(B)으로 시작해서 실제 병목이 확인되면 그때 GPU 서버(A)를 붙이는 순서가 "모두 무료로 시작한다"는 원래 방향과 맞는다.

아키텍처 · 03

권장 배포 구조 (운영 기준 — 베타는 노트북)

회색 상자는 이미 무료/저비용으로 유지되는 것, 굵은 테두리는 위 02절에서 비용이 생기는 지점이다.

2026-09-24 에 에이전트 서버를 분리했다(CLAUDE-decisions.md ADR-003 — 언어는 API 서버와 같은 TypeScript). DB 에 쓰는 곳은 API 서버 하나이고, 에이전트 서버는 도구 호출로만 데이터를 읽는다. 벡터도 에이전트 서버가 계산하고 API 서버가 기록한다.

비용 · 04

이 규모에서 무료가 유지되는 것 / 안 되는 것

개발 가이드의 무료 우선순위 가이드를 운영 규모(1천~1만 명)로 다시 채점했다.

항목노트북·베타 기준운영(1천~1만) 기준
카카오 Local API무료 한도 확인 필요 일 10만 건을 넘으면 건당 10~50원. 1만 명 규모에서는 한도 안일 가능성이 높다(추정)
OCR(Tesseract 1차)무료 무료 유지 볼륨이 학원 수 기준이라 사용자 수와 무관하게 완만함
임베딩(로컬 소형 모델)무료 서버 자원 필요 무료지만 별도 CPU 서버 자리가 필요해짐
채팅 AI(Qwen3.5 9B)무료 비용 발생 02절 — 유일하게 구조적으로 돈이 드는 지점
DB·API 서버무료(내 PC) 비용 발생 VPS·관리형 DB — 다만 GPU보다 훨씬 저렴
PG(결제대행)해당 없음 거래수수료 매출 연동이라 고정비는 아님
추정 · 05

월 예상 비용 (거친 범위)

PG 거래수수료(매출 비례)는 뺀, 고정 인프라비만의 추정이다. 실측 전 숫자라 ±50% 오차를 감안한다.

베타(1~10명) — 노트북 1대
전기료 제외
₩0 ~ 5만원
운영 — 옵션 B+C만 적용 (GPU 서버 없이 시작)
VPS 소규모 1~2대 정도
₩40만 ~ 60만원
운영 — GPU 서버(옵션 A) 추가 시
RTX 4090급 24시간 인스턴스 기준

클라우드 GPU 시세는 자주 바뀐다. 실제 도입 직전에 RunPod· JarvisLabs 등에서 최신 시간당 단가를 다시 확인할 것.
