# 결제수단 정책

- 날짜: 2026-09-14

## 구현 규칙 — 무료 API 우선 원칙

**결제(PG) 자체를 제외한 모든 주변 기능은 무료 API/오픈소스만으로 구현한다.** PG는 거래 수수료로 수익을 내는 업종이라 완전 무료가 구조적으로 불가능하지만(`kdance-beta-infra.html`), 결제를 둘러싼 알림·락 등 나머지 구성 요소에서 유료 API를 새로 들이는 것은 이 원칙 위반이다.

- 결제 확인 알림: SMS(유료 API) 금지, Expo Push(무료, 기존 스택) 사용
- 슬롯 중복예약 방지: 별도 유료 서비스 없이 기존 Redis(오픈소스, 셀프호스팅)로 락 구현
- 새 유료 API 도입이 필요해 보이면, 착수 전 이 문서에 사유를 남기고 예외로 명시할 것

## 결정 사항

**단건 예약 결제는 가상계좌(무통장입금)를 기본 결제수단으로 하고, 월 구독(정기결제)은 카드만 지원한다.**

- 가상계좌: PG(포트원/토스페이먼츠 등)가 주문마다 1회용 계좌번호를 발급하는 방식. 카드망(VAN·카드사)이 아니라 은행 간 실시간 입금통보망을 쓰기 때문에 수수료가 결제 금액에 비례하는 %가 아니라 **건당 정액**이다. 강습료(4~15만원대) 기준으로 환산하면 카드(2.5~3.5%대)보다 실질 수수료율이 크게 낮다. 단, 정확한 건당 금액은 PG사·계약 조건마다 달라 실제 계약 전 PG사 요율표로 확인 필요.
- 카드: 정기결제(빌링키) 자동 청구가 되는 유일한 수단이라 구독에는 그대로 유지.
- 카카오페이/네이버페이 등 간편결제는 수수료가 카드와 비슷하거나 더 높을 수 있어 "저비용 대안"으로 채택하지 않는다.
- 학원 계좌를 앱에 직접 노출하고 PG 없이 수동으로 입금 확인하는 방식은 채택하지 않는다 — 입금자명 불일치 등 운영 부담, 전자금융거래법·통신판매중개 관련 리스크, 이중예약 문제 때문 (`social-dance-app-dev-guide.html`의 정산 분배형 PG 전제와도 배치됨).

## 결제 확인 알림 방식 (구현 규칙)

**결제 확인은 SMS 문자가 아니라 앱 내 팝업(인앱 알림/푸시)으로 구현한다.**

- PG 웹훅(`payment.completed` 등)이 백엔드에 도착하면, 백엔드는 그 즉시 **구매자와 학원 관리자 양쪽에** 앱 내 알림을 발송한다 — 카드 결제 시 오는 "카드사 문자"의 대체재 역할.
  - 구매자: "입금이 확인되어 예약이 확정되었습니다" 팝업/푸시
  - 학원 관리자(웹 콘솔 또는 관리자 웹 알림): "새 결제가 확인되었습니다" 알림
- 전달 수단은 이미 스택에 있는 Expo Push(FR-90, `social-dance-app-dev-guide.html`)를 그대로 재사용한다 — 별도 SMS 발송 API(알리고·쿨SMS 등) 연동은 **무료 API 우선 원칙 위반이라 채택하지 않는다.**
- 관리자 웹(React+Next.js)에도 동일한 확인 알림을 실시간으로 띄워야 하므로, 웹 쪽에는 폴링 또는 WebSocket/SSE 중 하나로 별도 알림 채널이 필요하다 — 구체 구현 방식은 아직 미정, 개발 착수 시 결정.

## 가상계좌 결제의 구조적 차이 — 슬롯 홀드 필요 (구현 규칙)

카드는 체크아웃 안에서 결제가 즉시 승인되지만, 가상계좌는 사용자가 앱을 벗어나 본인 은행 앱에서 이체해야 하므로 **입금 대기 상태가 생긴다.** 이 대기 시간 동안 같은 수업 슬롯이 중복 예약되지 않도록 아래 규칙을 따른다.

- 가상계좌 발급 시점에 해당 수업 슬롯을 짧게 잠근다(Redis 락 — 기존에 쿠폰 중복사용 방지용으로 예정된 Redis를 재사용).
- 가상계좌 유효시간(발급 시 PG가 정하는 입금 기한) 내에 입금이 확인되면 슬롯을 확정, 기한이 지나면 슬롯 잠금을 풀어 다시 예약 가능하게 한다.
- 같은 슬롯에 여러 명이 동시에 가상계좌를 발급받았다가 한 명만 입금한 경우, **먼저 입금 확인된 주문이 슬롯을 확정**하고 나머지는 자동 취소 처리한다.

## 결제수단 라우팅 규칙 — 방식 A / 방식 B (핵심 기능, 구현 규칙)

- 날짜: 2026-09-14 결정

상품 유형·금액 기준으로 결제 흐름을 두 경로로 분리한다.

| 구분 | 방식 A (딥링크 Scheme URL) | 방식 B (포트원/PG 간편 계좌이체 URL) |
|---|---|---|
| 적용 대상 | 체험형·원데이 클래스 등 **1~9만원 이하**, 이벤트·파티·대회 등 **간헐적 비용** | **일반 수강** 및 **10만원 이상** 수업 |
| 구현 방식 | 계좌이체 딥링크(Scheme URL)를 생성해 알림톡 버튼 등에 삽입 | 포트원 등 PG의 간편 계좌이체 URL로 결제 진행, 완료 시 웹훅 수신 |
| 장점 | 구현 난이도 매우 낮음, PG 가입·계약·API 키 발급 절차 거의 없음, 개발 기간 짧음 | 웹훅으로 결제 성공/실패 상태를 신뢰성 있게 처리, 통합 PG(포트원 등) 문서·예제 풍부 |
| 단점 | 송금 완료 자동 확인 불가 — 오픈뱅킹(팝빌·아임포트 등) API + 폴링을 직접 구현해야 하고, 입금자명 매칭·중복입금·금액 불일치·타임아웃 예외처리를 직접 챙겨야 함 | PG사 가입·사업자 심사·테스트 계정 세팅 등 초기 공수 큼, 웹훅 서명 검증·중복 웹훅 방지·실패 재처리 로직 필요 |

**결정: 이 라우팅을 핵심 기능으로 채택한다.**
- 저비용·간헐성 상품(방식 A)은 구현 속도를 우선해 딥링크 + 오픈뱅킹 폴링으로 처리.
- 고비용·정기성 상품(방식 B)은 안정성을 우선해 포트원 PG 간편 계좌이체 + 웹훅으로 처리.
- 방식 B를 쓰는 이상 **"PG사 미선정"은 더 이상 유효한 전제가 아니다** — 포트원이 방식 B의 PG로 확정됐다. 예약 취소/환불 등 방식 B 결제건을 다루는 기능은 포트원 실제 API 인터페이스를 전제로 설계해야 한다(가짜 어댑터를 쓰더라도 포트원 응답 스키마를 흉내 낼 것).

**✅ 확정 (2026-09-14, 사용자 재확인):** 이후 대화에서 "카드 정기결제 + 딥링크만 쓰는 2가지 세팅"을 권장하는 외부 자료가 인용되며 혼선이 있었으나, 사용자가 **가격 기준 방식 A/B 라우팅(위 표)을 그대로 유지**하기로 명시적으로 재확인했다. 방식 B/포트원 PG 연동은 계획대로 진행한다.

**✅ 추가 확정 (2026-09-14):** "일반 수강"은 별도 카테고리가 아니라 **"10만원 이상"과 동일한 조건**이다 — 즉 일반 수강 = 방식 B(포트원 PG). 가격이 10만원 미만인 상품은 정의상 체험형·원데이·이벤트 등(방식 A) 범주에 속한다. 9만원 초과~10만원 미만 구간의 처리만 여전히 미정으로 남는다(위 오픈 이슈 참조).

> ⚠️ 편집 노트: 위 "결정 사항"의 "학원 계좌를 앱에 직접 노출하고 PG 없이 수동으로 입금 확인하는 방식은 채택하지 않는다"는 기존 결정과 방식 A의 경계를 한 번 더 확인할 필요가 있다. 방식 A도 오픈뱅킹 API(팝빌·아임포트 등)를 통한 입금 확인이라는 점에서 완전 수동 방식과는 다르지만, 자동 확정이 아니라 폴링 기반이라는 점에서 기존에 우려했던 운영 부담(입금자명 불일치, 이중예약, 전자금융거래법 리스크)이 저비용 상품군에서 재발할 수 있다.

### 방식 A 상세 — 원클릭 송금 딥링크 (구현 규칙)

방식 A의 "딥링크 Scheme URL"은 학원 계좌번호를 사용자가 직접 복사·붙여넣기 하는 방식이 아니라, **토스(Toss)/카카오페이 등 송금 앱의 딥링크를 사용해 받는 계좌·금액을 미리 채운 송금 화면을 여는 방식**이다.

**플로우:**
1. 예약/신청 — 사용자가 앱에서 "OO 서비스 예약/신청" 버튼을 누른다.
2. 알림 수신 — 알림톡 또는 문자로 `[원클릭 계좌이체 하기]` 링크가 도착한다.
3. 앱 간 이동(Deep Link) — 링크를 누르면 토스 또는 카카오페이 송금 화면이 즉시 열리며, **받는 사람 계좌번호 + 결제 금액이 이미 입력된 상태**다.
4. 결제 완료 — 사용자는 지문/FaceID 인증만으로 송금을 완료한다.

**장점:** 가상계좌의 번거로움(계좌번호 복사 → 은행 앱 실행 → 붙여넣기 → 금액 입력)을 없애고, 버튼 하나로 입금 정보가 자동 세팅된 송금 화면까지 도달한다 — 수수료를 거의 들이지 않으면서 입금 경험을 크게 간소화하는 방식.

**구현 시 유의:** 송금 자체는 토스/카카오페이 앱 내부에서 완결되므로 백엔드는 그 결과를 알 수 없다 — 위 "단점"에 적힌 대로 **오픈뱅킹 API + 폴링으로 별도 확인**해야 한다. 딥링크가 여는 것은 결제 실행 UI일 뿐 결제 확인 채널이 아니라는 점을 구현 시 혼동하지 말 것.

**딥링크 URL 스킴 (토스 규격):**
```
supertoss://send?bank=기업은행&accountNo=1234567890&amount=100000&msg=주문번호102
```
```python
# FastAPI 백엔드 예시
def generate_toss_deeplink(order_id: str, amount: int) -> str:
    my_bank = "신한"
    my_account = "110123456789"
    return f"supertoss://send?bank={my_bank}&accountNo={my_account}&amount={amount}&msg={order_id}"
```

**연동 컴포넌트 2가지 (둘 다 유료 API — 아래 "무료 API 우선 원칙 예외" 참조):**
1. **알림톡/문자 발송** — solapi(쿨SMS), Popbill 알림톡, NCP(네이버클라우드 Sens) 중 택1. 건당 약 8~15원. 딥링크 버튼을 사용자에게 전달하는 채널(예약 확정 후 결제 요청용 — 결제 완료 확인 알림은 기존대로 Expo Push 유지).
2. **오픈뱅킹 계좌입금조회** — Popbill 계좌입금조회 API. 건당 수십 원. 1~5분 간격 폴링으로 입금 내역을 탐지해 예약 상태를 `PAID`로 갱신.

**비용 비교:** 방식 A는 PG 결제수수료가 0원(대신 위 알림톡+조회 API 건당 비용만 발생). 방식 B는 PG 계좌이체 수수료 약 1.5% 내외 또는 건당 약 150원.

### ⚠️ 무료 API 우선 원칙 예외 — 알림톡/오픈뱅킹 조회 API (미확정, 사용자 확인 필요)

이 문서 최상단 "무료 API 우선 원칙"은 "새 유료 API 도입이 필요해 보이면, 착수 전 이 문서에 사유를 남기고 예외로 명시할 것"을 요구한다. 방식 A는 **두 개의 새로운 유료 API**(알림톡/문자 발송, Popbill 계좌입금조회)를 도입한다 — 결제(PG) 자체는 아니지만 결제를 둘러싼 주변 기능이라 원칙 적용 대상이다. 예외로 채택할지 아직 명시적으로 확정되지 않았으므로, 방식 A(원클릭 송금 딥링크) 구현 계획에 반영하기 전에 사용자 확인이 필요하다(아래 질문 참조).

## 예약 취소 환불 정책 (핵심 기능, 구현 규칙)

- 날짜: 2026-09-14 결정 (요구사항 분석 Q1~Q5 확정 반영)

### 적용 범위

이번에 확정한 규칙은 **방식 B(포트원 PG) 가상계좌로 결제된 단건 예약을, 회원이 직접 요청해 전체 취소하는 경우**를 대상으로 한다. 카드 승인취소, 부분 취소, 학원 귀책 취소는 범위 밖이며 아래 "범위에서 제외한 것"에 따로 적었다.

환불 실행은 **자동 즉시 환불**이다. 학원 관리자 승인 단계를 두지 않는다 — 대신 학원별 환불 비율표가 취소 시점에 이미 설정돼 있어야 하므로 관리자 웹의 비율표 설정 화면은 필요하다(승인 워크플로우와는 별개).

### 1. 24시간 경계 — 정각 24:00:00은 전액 환불

수업 시작까지 남은 시간을 `h`라 할 때:

| 조건 | 환불률 |
|---|---|
| `h >= 24시간` | **100% (전액)** — 학원 설정과 무관한 플랫폼 고정값 |
| `h < 24시간` | 학원별 환불 비율표를 적용 (아래 2항) |

**정확히 24시간 00분 00초 남은 시점의 취소는 전액 환불**이다. 경계를 전액 환불 쪽에 포함시킨다.

근거: 약관 문구가 "수업 시작 24시간 **전** 취소 — 전액 환불"이다. 정확히 24시간 전은 "24시간 전"에 포함된다고 읽는 쪽이 자연스럽고, 애매한 경계는 소비자에게 유리하게 해석하는 편이 분쟁 리스크가 낮다.

모든 시각은 timezone-aware UTC로 저장·비교한다(`TIMESTAMP WITH TIME ZONE`). 산정 함수는 "현재 시각"을 내부에서 읽지 않고 **파라미터로 주입**받는다 — 함수 안에서 현재 시각을 읽으면 이 경계를 테스트로 못 박을 수 없다. 23:59:59 / 24:00:00 / 24:00:01 세 지점을 단위 테스트로 고정한다.

### 2. 학원별 환불 비율표 (Q3 — 학원별 설정 방식 채택)

"24시간 이내 취소는 학원 정책에 따름"(FR-22)의 실체를 **학원별 설정 필드**로 확정했다. 플랫폼 고정 기본값으로 단순화하지 않는다.

비율표는 학원 레코드에 JSONB로 저장하고, 관리자 웹에서 학원이 직접 편집한다. 형태는 다음과 같다.

```json
[{"hours_before_start": 24, "refund_rate_bp": 5000},
 {"hours_before_start": 12, "refund_rate_bp": 0}]
```

- `refund_rate_bp`는 **basis point 정수(0~10000)** 다. 10000 = 100%, 5000 = 50%. 퍼센트 실수나 소수점 비율을 쓰지 않는다 — 부동소수를 금지한 이상 비율도 정수여야 한다.
- `hours_before_start`는 1~720시간 범위의 정수다.
- JSONB는 DB가 구조를 검증해주지 않으므로, 범위·정렬·중복 검증은 **쓰기 경로(API 스키마 계층)에서 전부 막는다.**

**티어 해석 규칙:**

1. `h >= 24시간`이면 비율표를 보지 않고 무조건 100% 환불이다. 학원이 24시간 이상 구간에 낮은 비율을 넣어두더라도 플랫폼 고정 규칙이 이긴다.
2. `h < 24시간`이면, `hours_before_start`가 `h` **이상**인 티어들만 추린 뒤 그중 `hours_before_start`가 **가장 작은** 티어의 비율을 적용한다. `h`를 담는 가장 좁은 구간을 고른다는 뜻이다.
3. 조건을 만족하는 티어가 하나도 없으면 **0% 환불**이다.

위 예시 비율표 기준 동작:

| 남은 시간 `h` | 적용 | 환불률 |
|---|---|---|
| 30시간 | 플랫폼 고정 | 100% |
| 24시간 정각 | 플랫폼 고정 | 100% |
| 20시간 | 24h 티어 | 50% |
| 12시간 | 12h 티어 | 0% |
| 3시간 | 12h 티어 | 0% |

### 3. 금액 계산 — 정수(원), 올림(ceil), 부동소수 금지

- 모든 금액은 **정수(원)** 로 다룬다. 저장·계산·전송 어디에도 부동소수를 쓰지 않는다.
- 환불액 = `결제액 × 비율bp / 10000`, 나머지가 생기면 **올림(ceil)** 한다. 정수 연산으로만 계산한다.
- 근거: 1원 단위 차이지만 내림은 "회원에게 덜 준" 방향이라 분쟁 시 불리하다. 올림이 안전하다.
- 산정 결과는 **결제액으로 clamp** 한다. 환불액이 원결제액을 넘는 상황은 구조적으로 불가능해야 하며, 계산 단계의 clamp와 DB CHECK 제약으로 이중 방어한다.

### 4. 가상계좌 환불은 원거래 취소가 아니라 별도 송금

카드 결제는 승인취소로 원거래 자체를 되돌리지만, **가상계좌는 이미 입금된 돈을 되돌릴 수 있는 원거래 취소 수단이 없다.** 환불은 플랫폼이 회원 계좌로 새로 송금하는 별건 이체다. 여기서 두 가지가 따라온다.

1. **환불계좌를 수집해야 한다.** 취소 요청 시 회원에게 은행/계좌번호/예금주를 입력받는다. 결제수단이 가상계좌면 이 정보는 **필수**이고, 누락 시 요청을 거부한다. 이 검증은 PG 어댑터가 아니라 **API 스키마 계층**에 둔다 — PG사를 갈아끼워도 검증이 살아남아야 한다.
2. **환불의 `pending`은 오류가 아니라 정상 상태다.** 송금은 즉시 완결되지 않는다. 환불 상태는 `succeeded` / `pending` / `failed` 세 가지이며, `pending`을 1급 상태로 취급한다. 성공/실패 2값(불리언)으로 모델링하면 안 된다.

환불 상태 변경은 전부 감사 로그로 남기고, 실패 시 상태와 사유를 기록한다. 취소 완료 시 회원과 학원 관리자 양쪽에 앱 내 알림을 보낸다 — 기존 규칙대로 Expo Push를 재사용하고 SMS는 쓰지 않는다.

### 5. 수수료·정산·쿠폰 처리 (Q4 확정)

네 건 모두 **정책으로는 확정**됐다. 다만 이번 슬라이스에서 실제로 코드에 반영되는 것과, 결정만 해두고 구현을 미룬 것이 섞여 있다. 혼동하지 않도록 구분해 적는다.

| 항목 | 결정 | 이번 슬라이스 구현 상태 |
|---|---|---|
| 반환되지 않는 **PG 건당 수수료** 손실 | **플랫폼이 부담**한다. 회원에게 전가하지 않고 학원 정산에서 떼지도 않는다 | **반영 없음(의도된 것).** 회원 환불액은 이 손실과 무관하게 산정되므로 계산식에 들어갈 자리가 없다. 결정값은 수수료 정책 상수로 코드에 남긴다 |
| 이미 나간 **정산 이후의 환불** 회수 | **다음 달 정산에서 차감**한다 | **⚠️ 결정만 완료, 이번 미구현.** 정산 모듈 자체가 아직 없다. 차감 로직은 정산 기능 착수 시 별건으로 구현한다. 지금은 결정값을 상수와 주석으로만 남겨 둔다 |
| **1+1 쿠폰(FR-33)** 사용 예약의 취소 | **쿠폰을 복원한다.** 복원된 쿠폰에는 기존 분기말 소멸 규칙이 그대로 적용된다 (소멸 기한이 연장되지 않는다) | **⚠️ 결정만 완료, 이번 미구현.** 쿠폰 모델이 이번 슬라이스 범위에 없다. 취소 서비스에 복원 훅 위치만 주석으로 고정해 두고, 쿠폰 모델 도입 시 그 자리에 구현한다 |
| **플랫폼 수수료 8%**(FR-38) 환급 | **환급 대상이 아니다.** 베타 6개월 면제 기간이라 애초에 징수하지 않으므로 되돌릴 것이 없다 | **반영 없음(의도된 것).** 면제가 끝나는 시점에 환급 규칙을 별도로 재검토한다 |

즉 이 절에서 **환불액 산정에 실제로 영향을 주는 항목은 하나도 없다.** 회원이 돌려받는 금액은 결제액과 취소 시점, 학원 비율표만으로 결정된다. 나머지는 플랫폼과 학원 사이의 정산 문제이며 회원 환불과 분리한다.

### 6. 이번 범위에서 제외한 것 (Q5 확정)

| 제외 항목 | 사유 / 후속 |
|---|---|
| **부분 취소**(한 주문의 여러 수업 중 일부만 환불) | 이번엔 주문 단위 전체 취소만 지원한다. 스키마는 주문:예약을 이미 1:N으로 잡아둬서 나중에 서비스 로직만 추가하면 된다 — 마이그레이션은 필요 없다 |
| **학원 귀책 취소**(폐강·일정 변경) | 통상 시점과 무관하게 전액 환불로 보지만 문서에 정의가 없다. 이번엔 회원 요청 취소만 다루며, 취소 사유 값 집합에 학원 귀책을 넣지 않는다. 나중에 추가할 땐 CHECK 제약 변경 마이그레이션 1건이면 된다 |

### 7. `pricing-policy.md`와의 정합성 확인

`pricing-policy.md`는 "쿠폰/할인 차액은 **업주 부담**"을 정하면서 "상세 정산 로직(쿠폰 종류별 부담 비율, 정산 주기 등)은 추후 논의 필요"라고 명시적으로 열어뒀다. 위 결정들과 **직접적인 모순은 없다.** 다만 두 지점을 짚어 둔다.

1. **부담 주체 원칙이 항목별로 갈린다.** 쿠폰 차액은 업주, PG 건당 수수료 손실은 플랫폼이다. 어느 한쪽으로 통일된 원칙이 있는 게 아니라 비용 항목마다 따로 정해진 것이므로, 앞으로 새 비용 항목이 생길 때마다 개별 결정이 필요하다.
2. **할인 결제건을 취소했을 때 업주가 이미 부담한 차액을 되돌리는지는 여전히 공백이다.** 회원에게 돌려주는 금액은 "회원이 실제 결제한 금액(할인가)" 기준이라 회원 쪽은 문제가 없다. 문제는 정산 쪽이다 — 취소되면 업주가 부담한 차액도 함께 소멸해야 논리적으로 맞지만, `pricing-policy.md`가 열어둔 "추후 논의" 영역이라 규칙이 없다. 여기에 "1+1 쿠폰은 복원한다"가 겹치면, **업주는 차액을 부담한 채로 회원에게는 쿠폰이 돌아가는** 구간이 생길 수 있다. 정산 모듈과 쿠폰 모델을 실제로 구현할 때 반드시 함께 정해야 한다. 아래 오픈 이슈에 올린다.

### 환불 관련 오픈 이슈

- 할인·쿠폰 적용 결제건을 취소했을 때, 업주가 부담한 차액의 정산 처리 규칙 — 위 7항 2번. `pricing-policy.md`의 "추후 논의" 영역과 함께 확정 필요.
- 쿠폰 복원의 구체 규칙 — 복원 시 소멸 기한 재계산 여부는 "기존 분기말 소멸 규칙 그대로"로 확정됐으나, 소멸 직전에 취소해 사실상 쓸 수 없는 쿠폰이 복원되는 경우의 처리는 미정.
- 정산 후 환불의 다음 달 차감에서, 해당 학원의 다음 달 정산액이 차감액보다 적을 때의 처리 미정.
- PG 건당 수수료 손실을 플랫폼이 부담할 때의 상한·모니터링 기준 미정 (악의적 반복 예약·취소 대응).

## 오픈 이슈 (별도 확인 필요)
