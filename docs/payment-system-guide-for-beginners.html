1. 큰 그림 — 우리 앱은 결제를 어떻게 처리하나

kdance는 돈이 오가는 방식을 상품 가격에 따라 2갈래로 나눕니다. 비싸고 중요한 결제는 안전하고 검증된 방식(PG사)으로, 싸고 가끔 발생하는 결제는 개발자가 직접 구현하기 쉬운 방식(딥링크)으로 처리합니다. 이렇게 하면 개발 초기 비용은 줄이면서도, 큰돈이 걸린 결제는 신뢰도를 지킬 수 있습니다.

2. 시작 전에 — 꼭 알아야 할 용어 5개

PG (Payment Gateway, 결제대행사)
온라인 결제를 대신 처리해주는 회사(예: 포트원, 토스페이먼츠). 카드사·은행과 직접 계약하지 않아도, PG사 하나와만 계약하면 다양한 결제수단을 받을 수 있게 해줍니다. 대신 결제 금액의 일부를 수수료로 가져갑니다.
가상계좌
주문 1건마다 PG사가 임시로 발급해주는 1회용 계좌번호. 사용자가 그 계좌로 돈을 보내면 PG사가 "입금됐다"고 우리 시스템에 알려줍니다. 카드보다 수수료가 훨씬 저렴하지만, 사용자가 직접 계좌번호를 복사해서 이체해야 하는 번거로움이 있습니다.
딥링크(Deep Link)
클릭하면 특정 앱의 특정 화면을 바로 열어주는 특수한 링크. 예를 들어 supertoss://send?...를 누르면 토스 앱이 실행되면서 "송금하기" 화면이 계좌번호·금액까지 미리 채워진 채로 열립니다. 웹페이지 링크(https://...)와 달리 스마트폰에 설치된 앱을 직접 실행합니다.
웹훅(Webhook)
"어떤 일이 일어나면 자동으로 알려주는 전화" 같은 것입니다. PG사가 "결제가 완료됐어요"라는 신호를 우리 서버로 즉시 보내주는 방식이 웹훅입니다. 반대로 우리가 "결제됐나요?"라고 계속 물어봐야 하는 방식은 폴링(Polling)이라고 합니다.
오픈뱅킹 API
은행 계좌의 입출금 내역을 조회할 수 있게 해주는 서비스(예: 팝빌). PG사를 거치지 않고 "이 계좌에 얼마가 들어왔는지"를 직접 확인할 때 씁니다. 방식 A(딥링크)는 웹훅이 없기 때문에 이 오픈뱅킹 API로 입금 여부를 직접 조회(폴링)해야 합니다.

3. 방식 A vs 방식 B — 왜 2가지로 나눴나

한 가지 결제 방식만 쓰면 개발은 단순해지지만, 그러면 손해를 봅니다. 딥링크는 거의 공짜지만 결제 확인이 번거롭고, PG 결제는 확인이 간편하지만 결제마다 수수료가 나갑니다. 그래서 1인 개발 초기 단계에 맞게 금액 기준으로 갈라서 각자의 장점만 취하기로 했습니다.

구분 방식 A딥링크 송금 방식 B포트원 PG
적용 대상 체험형·원데이 클래스, 이벤트·파티·대회 등
1~9만원 이하 · 간헐적 비용		 일반 수강 및 10만원 이상 수업
결제 수수료 거의 0원 (대신 알림 발송·조회 API 건당 비용) 약 1.5% 내외 또는 건당 약 150원
결제 완료 확인 직접 주기적으로 조회(폴링) — 느리고 손이 감 PG사가 자동으로 알려줌(웹훅) — 빠르고 신뢰도 높음
개발 난이도 낮음 (PG 계약 불필요, 2~3시간이면 뼈대 완성) 높음 (PG 가입·심사·연동 테스트 필요)
왜 이 가격 기준? 금액이 작을수록 "확인이 좀 느려도 되는" 리스크가 작음 금액이 클수록 "확실하게 확인해야 하는" 필요성이 큼
솔직한 트레이드오프
방식 A는 "돈은 아끼지만 확인은 불완전한" 방식입니다. 입금자명이 다르거나, 금액을 잘못 보내거나, 확인 전에 사용자가 문의하는 등 예외 상황을 개발자가 직접 챙겨야 합니다. 그래서 상대적으로 금액이 작고 발생 빈도가 낮은 상품에만 쓰기로 했습니다 — 만에 하나 문제가 생겨도 피해 규모가 작기 때문입니다.

4. 방식 A 완전분석 — 딥링크 송금

사용자 입장에서는 버튼 하나만 누르면 되는 가장 쉬운 결제입니다. 개발자 입장에서 복잡한 건 "그 버튼 뒤에서" 벌어지는 일입니다.

5. 방식 B 완전분석 — 포트원 PG

일반 수강료나 10만원 이상 결제처럼 실수가 용납되기 어려운 금액은, 검증된 결제대행사(포트원)를 통해 처리합니다.

1. 결제 요청포트원 API로 결제 URL 생성
→
2. 결제 진행사용자가 PG 결제창에서 계좌이체 진행
→
3. 웹훅 수신결제 완료 즉시 포트원이 우리 서버에 자동 통보
→
4. 예약 확정웹훅 받는 즉시 바로 확정 (폴링 불필요)
방식 A와 가장 다른 점
방식 A는 "확인했나 안 했나 계속 물어봐야" 하지만(폴링), 방식 B는 "결제되면 PG사가 먼저 전화를 걸어줍니다"(웹훅). 그만큼 신뢰도와 처리 속도가 좋아지는 대신, PG사에 수수료를 지불합니다.

단점은 가입 절차입니다. PG사와 계약하려면 사업자 심사, API 키 발급, 테스트 계정 세팅 등을 거쳐야 하고, 결제 성공/실패 판정 로직도 보안(서명 검증)까지 챙겨야 합니다. 그래서 "이 정도 수고를 들일 가치가 있는" 고가·정기 상품에만 적용합니다.

더 깊이: 왜 PG사를 코드에서 직접 안 부르고 한 단계 거치나 (개발자용)

코드는 포트원(PortOne) 같은 구체적인 PG사 이름을 직접 알지 않습니다. 대신 포트(Port)라는 "약속된 창구"(파이썬에서는 Protocol)만 알고, 실제로 그 창구 뒤에 무엇을 연결할지는 딱 한 곳(deps.py)에서만 정합니다. 그래서 테스트할 때는 가짜(Fake) 구현체를 끼우고, 나중에 진짜 포트원 연동을 붙일 때도 이 파일 하나만 바꾸면 됩니다 — 서비스 로직(cancellation.py)은 건드리지 않습니다.

6. 월 구독 결제 — 카드 정기결제

매달 자동으로 결제되는 구독 상품은 위 방식 A/B와는 또 다른 이야기입니다. 자동 청구(빌링)가 가능한 유일한 수단이 카드이기 때문에, 구독은 항상 카드 정기결제로 처리합니다. 계좌이체(딥링크)나 가상계좌는 "매달 자동으로" 빠져나가게 만들 수 없어서 구독에는 쓸 수 없습니다.

7. 예약 취소·환불은 어떻게 되나

이 부분은 백엔드 코드까지 완료됐습니다(SCH-01~10: 기반 배선부터 환불 정책 문서까지, pytest 159개 통과 — Docker로 띄우는 실 DB 통합 테스트 2건만 대기 중). 아래는 실제로 동작하는 규칙입니다.

상황환불 규칙
수업 시작 24시간 초과 전 취소전액 환불 (플랫폼 고정 규칙)
수업 시작 24시간 이내 취소학원마다 직접 설정한 환불 비율표를 따름
환불 승인사람이 승인하지 않고 시스템이 자동으로 즉시 처리
가상계좌로 결제한 건의 환불원래 계좌로 자동 취소가 안 돼서, 사용자의 환불받을 계좌를 새로 입력받아 별도로 송금

처리 순서를 그대로 보면 (11단계)

실제로 구현된 backend/app/services/cancellation.py의 처리 순서입니다. "커밋(commit) 이후"에야 알림·락 해제를 하는 이유는, 아직 확정 안 된 트랜잭션을 근거로 "취소됐습니다"를 먼저 알려버리면 안 되기 때문입니다.

8. 솔직히 말하는 리스크·미해결 사항

초보자를 위한 가이드라고 좋은 말만 하면 나중에 발등을 찍습니다. 지금 시점에 알려진 위험 요소를 그대로 적습니다.

  • 방식 A는 완전 자동이 아닙니다. 입금자명이 다르거나, 폴링 주기(1~5분) 동안 사용자가 "왜 확정이 안 되냐"고 문의할 수 있습니다.
  • 알림톡·오픈뱅킹 조회 API는 무료가 아닙니다. 이 프로젝트는 원래 "무료 API 우선 원칙"을 갖고 있었는데, 방식 A를 위해 새로 유료 API 2개(SOLAPI 알림톡, Popbill 계좌조회)를 도입하기로 했습니다 — 이 부분은 원칙에 대한 명시적 예외로 기록돼 있습니다.
  • 외부 승인 절차가 남아있습니다. SOLAPI 가입, 카카오 비즈니스 채널 개설, 알림톡 템플릿 심사(수 영업일 소요), Popbill 가입 — 전부 아직 시작 전입니다.
  • 가격 경계값이 애매합니다. "1~9만원"과 "10만원 이상" 사이, 정확히 9만원 초과 10만원 미만인 상품을 어느 방식으로 보낼지 아직 정하지 않았습니다.
  • 개발 환경 자체가 아직 안 갖춰져 있습니다. 로컬 데이터베이스(kdance-db)가 꺼져 있어서, Docker 설정을 먼저 켜야 실제 결제 코드를 테스트할 수 있습니다.

9. 자주 묻는 질문

Q. 사용자가 토스나 카카오페이 앱이 없으면 어떻게 되나요?

딥링크가 실행되지 않으므로, 대신 계좌번호를 직접 보여주는 화면으로 안내하도록 설계돼 있습니다(2초 안에 앱이 안 열리면 대체 화면 표시).

Q. 방식 A로 결제했는데 다른 사람이 대신 입금하면 어떻게 확인하나요?

입금자명이 시스템이 기대한 이름과 다르면 자동 매칭에 실패합니다. 이런 예외 케이스를 처리하는 구체적인 로직은 아직 설계 중입니다.

Q. 왜 처음부터 포트원(PG) 하나로 통일하지 않았나요?

PG 결제는 건당 수수료가 계속 나갑니다. 1인 개발·초기 베타 단계에서는 수수료 부담을 줄이는 것이 중요해서, 저가·간헐적 상품은 수수료가 거의 없는 딥링크 방식을 쓰기로 했습니다.

Q. "왕초보 가이드"인데 왜 이렇게 자세한가요?

결제는 실수하면 실제 돈 문제로 이어지는 영역이라, 겉핥기 설명보다 "왜 이렇게 만들었는지"까지 이해하는 편이 나중에 버그를 마주쳤을 때 훨씬 도움이 됩니다.
