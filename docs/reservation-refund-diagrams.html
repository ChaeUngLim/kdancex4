4. 서브3. 방식 A/B 라우팅 분기

금액 기준으로 결제 흐름이 두 갈래로 갈라집니다. 아직 안 정해진 가격 구간(O1)도 표시했습니다.

flowchart TD
  START(["주문 생성 Order Created"]) --> CHECK{"금액 얼마? 가격 기준 라우팅, SCH-19 예정"}
  CHECK -->|"1~9만원 이하 · 체험,이벤트,파티"| A["방식 A: 딥링크 Deep Link · 구현 빠름, PG 계약 불필요"]
  CHECK -->|"10만원 이상 · 일반 수강"| B["방식 B: 포트원 PG · 간편 계좌이체, 완료"]
  CHECK -->|"9만원 초과~10만원 미만 · O1 아직 미확정"| OPEN["열린 결정 O1 · 아직 못 정함"]
  A --> ADEEP["딥링크 생성 SCH-14 · 토스,카카오,네이버"]
  ADEEP --> ANOTI["알림톡 발송 SCH-16 SOLAPI · 원클릭 송금하기 버튼"]

  B --> BWEBHOOK["포트원 웹훅 수신 · payment.completed"]
  BWEBHOOK --> BCONFIRM["예약 확정 PAID"]

5. 서브4. 방식 A 딥링크 전체 플로우

아직 구현 전인 SCH-13~20(외부 계정·승인 절차부터 테스트까지)의 목표 흐름 — 예약부터 오픈뱅킹 폴링까지.

sequenceDiagram
  participant U as 회원(모바일 앱)
  participant BE as 백엔드(FastAPI)
  participant SOLAPI as SOLAPI(알림톡)
  participant TOSS as 토스/카카오/네이버(송금앱)
  participant POPBILL as Popbill(오픈뱅킹조회)
  participant DB as PostgreSQL

  U->>BE: 예약/신청 버튼
  BE->>DB: 주문 Order 생성 status=pending
  BE->>SOLAPI: 알림톡 발송 요청 SCH-16, 브릿지 URL 포함
  SOLAPI-->>U: 알림톡 도착, 원클릭 송금하기 버튼
  U->>BE: 브릿지 페이지 진입 SCH-15
  BE-->>U: provider 화이트리스트 검증 후 딥링크로 리다이렉트 SCH-14
  U->>TOSS: 딥링크로 송금 앱 진입, 계좌 금액 자동 입력
  TOSS-->>U: 지문/FaceID 인증 후 송금 완료
  Note over BE,POPBILL: 백엔드는 송금 완료를 직접 모른다, 반드시 폴링으로 확인
  loop 1~5분 간격 SCH-17
    BE->>POPBILL: 계좌입금조회 요청
    POPBILL-->>BE: 입금 내역 응답
  end
  BE->>DB: 입금자명 매칭 성공, 주문 status=paid, 슬롯 확정
  BE-->>U: 예약 확정 알림 Expo Push

6. 파이프라인. 예약취소·환불 11단계

실제로 구현된 backend/app/services/cancellation.py의 처리 순서입니다.

sequenceDiagram
  participant M as 모바일 앱
  participant R as 라우터(reservations.py)
  participant S as 서비스(cancellation.py)
  participant DB as PostgreSQL
  participant PG as 포트원(PG 어댑터)
  participant RD as Redis(슬롯락)
  participant N as 알림(Expo Push)

  M->>R: POST /reservations/id/cancel
  R->>S: cancel_reservation 호출
  S->>DB: 1.행 잠금 SELECT FOR UPDATE
  S->>S: 2.소유권 검증 본인 예약인가
  S->>DB: 3.멱등 재생 검사 이미 처리됐나
  alt 이미 처리된 요청
    S-->>R: 기존 결과 그대로 반환 200 replayed true
  else 새 요청
    S->>S: 4.상태 전이 검증 취소 가능한가
    S->>S: 5.환불액 산정 calculate_refund 순수함수
    S->>DB: 6.Refund INSERT SAVEPOINT로 멱등 보호
    S->>PG: 7.PG 환불 호출
    alt 실패
      PG-->>S: failed
      S->>DB: 실패 사유 기록, 예약은 그대로 유지
    else 성공 또는 대기
      PG-->>S: succeeded 또는 pending
      S->>DB: 8.예약 취소 확정 + 정원 -1 + 주문 상태 변경
    end
    S->>DB: 9.refund_events INSERT 감사 로그
    S->>DB: 10.COMMIT 여기서 확정
    S->>RD: 11a.슬롯 락 해제 커밋 이후 best-effort
    S->>N: 11b.회원+학원관리자 알림 커밋 이후
  end
  S-->>R: CancellationOutcome
  R-->>M: 200 응답 성공/대기/실패 전부 200
