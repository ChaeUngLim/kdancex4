# SCH — 결제수단 방식 A(원클릭 송금 딥링크) 구현 스케줄

- 날짜: 2026-09-14
- 관련 문서: `docs/payment-method-policy.md`(정책 결정), `docs/payment-deeplink-reference.md`(코드 레퍼런스)
- 성격: 핵심 구현 태스크 스케줄. `kdance-dev-harness`의 Phase 4(Task 분리)가 그대로 가져다 쓸 수 있는 형태로 작성했다 — 아직 Phase 5(구현) 착수 전이다.

## 목표

체험형·원데이 클래스, 이벤트·파티·대회 등 1~9만원 이하 상품(방식 A)에 대해, 예약/신청 → 알림톡(토스/카카오페이/네이버페이 선택 버튼) 발송 → 딥링크 브릿지 페이지 → 간편송금 앱에서 결제 → 오픈뱅킹 폴링으로 입금 확인 → 예약 확정까지의 전체 흐름을 구현한다.

## Task 목록

### T1. 외부 계정·승인 절차 (최우선, 외부 소요시간 있음 — 개발과 병행 가능)
- SOLAPI 가입 + API 키/시크릿 발급
- 카카오톡 비즈니스 채널(PF) 개설
- 알림톡 템플릿 작성 + 카카오 심사 제출(승인까지 통상 수 영업일 — 일정 리스크)
- Popbill 가입 + 계좌입금조회 API 신청
- **의존:** 없음. 다른 태스크와 병행 시작 가능. T4(알림톡 발송 어댑터)·T5(입금 확인 폴링)의 실제 연동은 이게 끝나야 하지만, 코드 자체는 Fake(가짜 구현)로 먼저 짤 수 있다.

### T2. backend: 딥링크 생성 모듈 (`app/adapters/deeplink.py`)
- `generate_toss_deeplink` / `generate_kakaopay_deeplink` / `generate_naverpay_deeplink` (레퍼런스 §1 기반, 계좌 하드코딩 제거)
- 단위 테스트: URL 인코딩, 계좌번호 정규화(하이픈 제거), 빈 memo 처리
- **의존:** 없음

### T3. backend: 리다이렉트 브릿지 엔드포인트 (`GET /pay/redirect/{order_id}`)
- 레퍼런스 §2 기반, `provider` 쿼리 화이트리스트 검증(`toss`/`kakao`/`naver` 외 값 거부 — 예시 코드의 무검증 else 폴백 제거)
- 계좌/금액을 하드코딩이 아니라 `order_id`로 DB 조회
- 모바일 웹뷰 대응(alert() 대신 실제 UI 안내 페이지)
- **의존:** T2(딥링크 생성 모듈)

### T4. backend: 알림톡 발송 어댑터 (`app/adapters/alimtalk.py`, SOLAPI)
- 레퍼런스 §3 기반, HMAC(해시 기반 메시지 인증) 서명 — API 키/시크릿은 T6(설정/환경변수 추가)에서 로드, 하드코딩 금지
- 3버튼(토스/카카오/네이버) 템플릿 변수 구성, T3(리다이렉트 브릿지 엔드포인트)의 URL 연결
- T1(외부 계정·승인 절차) 중 SOLAPI 계정·템플릿 승인이 끝나기 전까지는 Fake 발송 어댑터로 대체
- **의존:** T1(외부 계정·승인 절차 — 실연동 시점), T3(리다이렉트 브릿지 엔드포인트)

### T5. backend: 입금 확인 폴링 (`app/adapters/deposit_polling.py`, Popbill)
- 1~5분 간격 스케줄러(APScheduler) 잡으로 계좌입금조회
- 입금자명 매칭 실패·중복입금·타임아웃 처리
- 확인되면 예약 상태 `PAID` 갱신 + 슬롯 확정(Redis 락 해제)
- T1(외부 계정·승인 절차) 중 Popbill 승인이 끝나기 전까지는 Fake 어댑터로 대체
- **의존:** T1(외부 계정·승인 절차 — 실연동 시점)

### T6. 설정/환경변수 추가
- `SOLAPI_API_KEY`, `SOLAPI_API_SECRET`, `KAKAO_PF_ID`, `KAKAO_TEMPLATE_ID`, `POPBILL_*` — `backend/.env`, `backend/.env.example` 양쪽에 추가(값은 `.env`에만, `.example`은 플레이스홀더)
- **의존:** 없음. T4(알림톡 발송 어댑터)·T5(입금 확인 폴링)보다 먼저 끝내두면 편하다

### T7. 가격/상품유형 기준 방식 A·B 라우팅 로직
- 주문 생성 시 금액·상품유형에 따라 방식 A(딥링크)/방식 B(포트원 PG) 분기 (`payment-method-policy.md` 라우팅 규칙)
- **의존:** 없음(독립적으로 먼저 착수 가능) — 단, 아래 "미해결" 항목 확정 필요

### T8. 테스트
- 딥링크 생성 단위 테스트 — T2(딥링크 생성 모듈)
- 브릿지 엔드포인트 통합 테스트 — provider(결제 제공사)별 정상/화이트리스트 거부 케이스. T3(리다이렉트 브릿지 엔드포인트)
- 알림톡·폴링 어댑터는 Fake로 목 테스트 — T4(알림톡 발송 어댑터), T5(입금 확인 폴링)
- **의존:** T2~T5(딥링크 생성 ~ 입금 확인 폴링)
