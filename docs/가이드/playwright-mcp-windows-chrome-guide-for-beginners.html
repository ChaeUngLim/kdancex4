1. 개요 — 우리가 풀려고 한 문제

kdance 개발 환경은 WSL(Windows 안에 설치된 리눅스) 위에서 Claude Code가 돌아갑니다. 그런데 화면을 실제로 보면서 브라우저를 테스트하거나(mindpilot MCP의 구조도 뷰어, playwright MCP의 E2E 테스트), 로그인이 필요한 사이트에 접속하려면 진짜로 화면에 보이는 브라우저가 필요합니다. 문제는 리눅스(WSL) 안에서 브라우저 창을 직접 띄우면 화면 표시(WSLg)가 불안정해서 로그인 같은 상호작용이 제대로 안 됐다는 점입니다.

그래서 "브라우저는 Windows에서 진짜로 띄우고, 그걸 리눅스 쪽에서 원격으로 조종한다"는 방식을 택했습니다. 이 문서는 그 방식을 실제로 연결하는 과정에서 만난 문제 10가지와, 최종적으로 "매번 포트를 열고 닫을 필요 없는" 편한 구조로 정리하기까지의 전체 과정을 담습니다.

① 문제리눅스(WSL) 안에서는 브라우저 창이 제대로 안 뜨고 로그인이 안 됨
→
② 시도Windows Chrome을 원격 디버깅 모드로 띄우고, 리눅스에서 그걸 조종
→
③ 걸림돌포트 충돌, 관리자 권한, IPv6/IPv4 불일치 등 10가지 문제
→
④ 정착로그인은 1회만, 그 상태를 저장해서 평소엔 리눅스가 혼자 재사용
한 줄 요약
"브라우저를 어디서 실행할지"와 "그 브라우저에 어떻게 로그인 상태를 유지할지"는 서로 다른 문제입니다. 이 가이드는 이 둘을 계속 구분해서 설명합니다.

2. 시작 전에 — 꼭 알아야 할 용어

MCP (Model Context Protocol)
Claude Code가 "브라우저를 조종해라", "DB를 조회해라" 같은 외부 도구를 쓸 수 있게 해주는 연결 규격입니다. playwright와 chrome-devtools(mindpilot과는 별개)는 모두 "브라우저를 조종하는 MCP"입니다.
CDP (Chrome DevTools Protocol)
Chrome을 외부 프로그램이 원격으로 조종할 수 있게 해주는 통로입니다. Chrome을 --remote-debugging-port=9223 옵션으로 켜면, 그 포트로 "새 탭 열어줘", "이 주소로 가줘" 같은 명령을 보낼 수 있습니다. playwright도, 크롬 개발자 도구도, mindpilot도 결국 이 CDP를 통해 브라우저와 대화합니다.
WSL2 네트워킹 (NAT 모드)
이 컴퓨터의 WSL(리눅스)은 기본적으로 Windows와 분리된 가상의 네트워크 위에 있습니다. 그래서 Windows에서 127.0.0.1(자기 자신)에만 열어둔 포트는 WSL에서 바로 안 보입니다 — 마치 옆집 컴퓨터처럼 취급됩니다. 이 문제를 푸는 방법이 아래 portproxy입니다. (참고로 "mirrored 모드"라는 대안도 있지만, 다른 네트워킹 작업과 충돌할 수 있어 이번에는 쓰지 않기로 했습니다.)
portproxy / 방화벽 인바운드 규칙
netsh interface portproxy는 Windows에게 "이 포트로 오는 요청을 저 포트로 그대로 전달해줘"라고 시키는 명령입니다. 방화벽 인바운드 규칙은 "그 포트로 들어오는 연결을 막지 말고 허용해줘"라는 허가증입니다. 이 컴퓨터 설정 두 가지가 각각 관리자 권한이 필요합니다.
관리자 권한(UAC)
Windows에서 시스템 설정을 바꾸려면 "이 작업을 허용하시겠습니까?" 팝업(UAC)에 사람이 직접 클릭해야 합니다. Claude Code는 WSL 안에서 powershell.exe를 원격으로 실행할 수는 있지만, 이 팝업은 절대 대신 클릭할 수 없습니다 — 그래서 이 종류의 명령은 항상 사용자가 직접 관리자 PowerShell을 열어서 실행해야 했습니다.
헤드리스(headless)
화면(창)을 아예 띄우지 않고 브라우저를 백그라운드에서만 실행하는 방식입니다. 사람이 볼 필요 없는 자동화 작업(테스트 등)에는 헤드리스가 더 빠르고, 관리자 권한이나 포트 작업도 필요 없습니다.
storageState (로그인 상태 저장 파일)
브라우저의 쿠키·로그인 정보를 파일 하나로 통째로 저장해두는 Playwright의 기능입니다. 한 번 로그인해서 이 파일을 만들어두면, 다음부터는 로그인 화면을 다시 띄우지 않고 이 파일을 불러오는 것만으로 "이미 로그인된 상태"로 시작할 수 있습니다. 이 파일 자체가 로그인 비밀번호와 동급으로 민감한 정보라는 점이 중요합니다(8장 참고).

3. 최종 아키텍처 — 왜 이렇게 만들었나

핵심 아이디어는 "귀찮고 위험한 부분(포트를 열어서 Windows Chrome에 접속하는 것)은 딱 한 번만 하고, 그 결과(로그인 상태)만 저장해서 평소에는 그 흔적조차 필요 없게 만든다"는 것입니다.

이렇게 바꾼 이유
처음엔 "매번 Windows Chrome을 켜고, portproxy·방화벽을 열고, 다 쓰면 다시 지우는" 방식으로 시작했습니다. 그런데 이 방식은 ① 매번 번거롭고 ② 관리자 권한 승인을 사람이 직접 해야 하고 ③ 포트를 열어둔 채 와이파이에 연결돼 있으면 보안 위험까지 있었습니다(4장의 이슈 3 참고). storageState로 로그인 상태만 저장해두면 이 세 가지 문제가 전부 한 번에 없어집니다.

4. 이슈 → 원인 파악 → 해결 (10개, 순서대로)

실제로 겪은 순서 그대로 적었습니다. 지어내지 않았습니다 — 이 프로젝트가 처음이신 분도 "아, 이래서 이렇게 됐구나"를 그대로 따라올 수 있게 하기 위함입니다.

1포트 9222가 이미 다른 프로그램이 쓰고 있었다

무슨 일이 있었나: Chrome을 --remote-debugging-port=9222로 켜고 접속했더니, Chrome이 아니라 "Lenovo Vantage"라는 전혀 다른 프로그램(내장된 Edge WebView)이 응답했습니다.

왜 그랬나: 노트북 제조사 유틸리티(Lenovo Vantage)가 이미 9222 포트를 선점하고 있었습니다. Chrome은 원하는 포트가 이미 사용 중이면 에러를 내지 않고 그냥 조용히 그 옵션을 무시하기 때문에, 겉보기엔 정상적으로 켜진 것처럼 보여서 눈치채기 어려웠습니다.

어떻게 해결했나: 포트를 9223으로 바꿨습니다.

2포트포워딩·방화벽 설정에 관리자 권한이 필요했다

무슨 일이 있었나: netsh interface portproxy add, New-NetFirewallRule 명령을 WSL에서 원격으로 실행하면 "액세스가 거부되었습니다"라는 에러가 났습니다.

왜 그랬나: 두 명령 모두 Windows 시스템 설정을 바꾸는 작업이라 관리자 권한이 필요합니다. WSL에서 powershell.exe를 실행할 수는 있지만, 관리자 권한 승인 팝업(UAC)은 사람이 직접 클릭해야만 넘어갈 수 있고 원격으로는 그 클릭을 대신할 수 없습니다.

어떻게 해결했나: 이 두 명령만 사용자가 직접 "관리자 권한으로 실행"한 PowerShell 창에서 입력했습니다. (참고: 이후 일부 정리 명령은 재시도 시 권한 없이도 통과된 경우가 있었는데, 이는 해당 규칙이 이미 삭제되어 있었기 때문으로 보입니다.)

3와이파이에 연결된 채로 포트를 열어둬서 보안 위험이 있었다

무슨 일이 있었나: 포트 9223을 0.0.0.0(모든 네트워크 인터페이스)에 열어둔 상태로 한동안 와이파이에 연결돼 있었습니다.

왜 위험했나: Chrome 디버깅 포트는 그 Chrome을 통째로 조종할 수 있는 매우 강력한 권한입니다. 같은 와이파이에 있는 다른 사람이 이 포트에 접속하면 로그인 세션·쿠키까지 전부 들여다보고 조작할 수 있었습니다.

어떻게 해결했나: 즉시 portproxy·방화벽 규칙을 전부 삭제해서 원상복구했고(WSL에서 조회해 규칙이 실제로 비어있는 것까지 확인), 이후 작업은 유선(LAN)으로 전환한 뒤 재개했습니다.

4리눅스(WSL) 안에서는 Chrome 로그인이 안 됐다

무슨 일이 있었나: WSL 안에서 직접 Chrome을 띄우면 창이 제대로 표시되지 않거나 상호작용이 안 돼서 로그인을 진행할 수 없었습니다.

왜 그랬나: WSL의 리눅스 화면을 Windows 데스크톱에 보여주는 WSLg 기능이 이 환경에서 불안정했습니다.

어떻게 해결했나: 리눅스 Chrome을 고치려 하지 않고, 대신 Windows에 진짜로 떠 있는 Chrome을 리눅스가 원격으로 조종하는 방식(CDP)으로 방향을 바꿨습니다 — 이게 이 가이드 전체의 핵심 방향입니다.

5이미 켜진 Chrome 창이 있으면 디버그 포트 옵션이 무시됐다

무슨 일이 있었나: 이미 다른 작업 탭들이 열려있는 평소 Chrome이 켜진 상태에서 --remote-debugging-port 옵션으로 새로 Chrome을 실행해도, 그냥 기존 Chrome에 새 탭 하나만 추가로 열렸습니다.

왜 그랬나: Chrome은 같은 프로필로 이미 실행 중이면, 새로 내린 실행 명령을 "새 창 열어줘" 정도로만 이미 떠 있는 프로세스에 전달하고 커맨드라인 옵션(디버그 포트 등)은 무시합니다.

어떻게 해결했나: --user-data-dir=C:\Temp\kdance-debug-profile로 완전히 별개의 전용 프로필을 지정해서 새 Chrome 프로세스를 띄웠습니다. 기존에 열려있던 작업 탭은 전혀 건드리지 않으면서, 별도의 Chrome 창 하나가 새로 뜨는 방식입니다.

6Chrome이 IPv6로만 열려서 portproxy(IPv4)와 안 맞았다

무슨 일이 있었나: 전용 프로필로 Chrome을 다시 켰더니, 이번엔 127.0.0.1(IPv4)이 아니라 [::1](IPv6)에서만 디버그 포트가 열렸습니다. --remote-debugging-address=127.0.0.1 옵션을 명시해도 마찬가지였습니다.

왜 그랬나: 이 Chrome 버전이 로컬 환경에서 IPv6 루프백을 우선으로 바인딩하는 것으로 보였습니다 (정확한 내부 동작은 Chrome마다 다를 수 있습니다). portproxy는 connectaddress=127.0.0.1(IPv4)로 설정돼 있어서, Chrome이 IPv4로 응답하지 않으니 연결이 안 됐습니다.

어떻게 해결했나: Chrome과 싸우지 않고 portproxy 쪽을 바꿨습니다 — v4tov4 대신 v4tov6 모드로 바꿔서 connectaddress=::1(IPv6)을 가리키게 했습니다. netsh는 이렇게 IPv4↔IPv6를 서로 연결해주는 기능도 지원합니다.

7테스트 탭을 닫았더니 Chrome 전체가 꺼져버렸다

무슨 일이 있었나: 연결 테스트용으로 새 탭을 열어 페이지를 확인한 뒤 그 탭을 닫았는데, Chrome 프로세스 자체가 통째로 종료됐습니다.

왜 그랬나: 그 탭이 전용 디버그 프로필의 유일한 창이었습니다. 남은 창이 하나도 없어지면 Chrome이 프로세스를 종료하는 것으로 보였습니다.

어떻게 해결했나: Chrome을 다시 켜고, 이후로는 테스트용 탭을 열어도 닫지 않고 그대로 두는 방식으로 바꿨습니다(연결(커넥션)만 끊고 탭은 유지).

8로그인 세션 저장이 보안 장치에 의해 자동으로 막혔다

무슨 일이 있었나: 이미 로그인돼 있는 상태에서 그 로그인 정보(storageState)를 파일로 저장하는 명령을 실행하려 하자, Claude Code의 자동 보안 분류기가 이 작업을 차단했습니다.

왜 그랬나: 로그인 쿠키를 그대로 디스크에 저장하는 작업은 사실상 "비밀번호급 정보를 파일로 빼내는" 것과 같은 민감한 동작이라, 자동화 도구가 스스로 판단해서 실행하도록 두지 않고 사람의 명시적 승인을 요구한 것입니다. 이는 정상적으로 작동한 안전 장치입니다.

어떻게 해결했나: 왜 이 작업이 필요한지(포트 여닫는 번거로움 없이 평소엔 리눅스가 저장된 상태를 재사용하기 위함), 어디에 저장할지(~/.cache/kdance-playwright-auth/state.json, git과 무관, 권한 600)를 사용자에게 그대로 설명하고, 명시적 승인을 받은 뒤에 진행했습니다.

9playwright MCP가 시스템에 없는 'chrome' 채널을 찾으려 했다

무슨 일이 있었나: 새로 설정한 playwright MCP(헤드리스 모드)를 재연결한 뒤 첫 테스트를 하자 Chromium distribution 'chrome' is not found at /opt/google/chrome/chrome 에러가 났습니다.

왜 그랬나: playwright MCP는 옵션을 따로 지정하지 않으면 기본값으로 "시스템에 설치된 정식 Chrome"(chrome 채널)을 쓰려고 합니다. 그런데 이 리눅스 환경에는 정식 Chrome이 아니라 Playwright가 자체적으로 내려받은 번들 Chromium만 설치돼 있었습니다.

어떻게 해결했나: 설정에 --browser chromium을 추가해서, 이미 설치돼 있는 번들 Chromium을 쓰도록 명시했습니다.

10그마저도 브라우저 버전이 한 끗 안 맞았다

무슨 일이 있었나: --browser chromium으로 고친 뒤에도 Browser "chrome-for-testing" is not installed; expected ... chromium-1244 에러가 났습니다.

왜 그랬나: 예전에 다른 작업(연결 테스트)을 할 때 내려받았던 번들 Chromium은 chromium-1243 버전이었는데, @playwright/mcp@latest가 그사이 더 최신 버전으로 올라가면서 chromium-1244를 요구하게 됐습니다.

어떻게 해결했나: 에러 메시지가 안내해준 명령(npx @playwright/mcp@latest install-browser chrome-for-testing)을 그대로 실행해서 필요한 버전을 새로 내려받았습니다.

5. 테스트로 확인한 것

설정을 다 바꾼 뒤 "정말 되는지"를 실제로 두 가지 방식으로 확인했습니다. 둘 다 MCP 재연결(/mcp) 이후에 진행한 테스트입니다.

테스트방법결과이게 증명하는 것
저장된 로그인 상태 재사용 헤드리스 리눅스 Chromium으로 구글 계정 페이지(myaccount.google.com) 접속 로그인 화면 없이 바로 계정 정보 표시됨 storageState 파일이 실제로 로그인 상태를 온전히 담고 있고, playwright MCP가 그걸 정상적으로 불러온다는 것
실제 프로젝트 앱 구동 kdance admin-web(Next.js) 개발 서버를 실행하고, 같은 헤드리스 Chromium으로 접속·스크린샷 페이지 정상 렌더링, 스크린샷 확인됨 이 설정이 "구글 로그인 확인용 장난감"이 아니라 실제 개발 작업(E2E 확인 등)에 바로 쓸 수 있다는 것
알려진 제한 — 과장하지 않고 그대로 적음
admin-web 테스트 화면에서 콘솔 에러 2건이 났는데, 이는 백엔드 서버(localhost:8000)를 같이 켜지 않아서 난 헬스체크 실패였습니다(설정 문제 아님). 또한 스크린샷에서 한글 텍스트가 네모(□)로 깨져 보였는데, 이는 헤드리스 리눅스 환경에 한글 폰트가 설치돼 있지 않아서이고 실제 서비스 동작과는 무관합니다 — 필요하면 fonts-nanum 등을 추가로 설치하면 해결됩니다(이번 작업 범위 밖이라 설치하지 않음).

6. 로그인이 다시 만료되면 — 재현 절차

구글 로그인 세션은 언젠가 만료될 수 있습니다. 그때 처음부터 다시 겪지 않도록, 최종적으로 성립한 절차만 순서대로 적습니다(4장의 시행착오는 이미 반영된 상태입니다).

  1. Windows에서 전용 프로필로 Chrome 실행: chrome.exe --remote-debugging-port=9223 --user-data-dir=C:\Temp\kdance-debug-profile
  2. 관리자 PowerShell에서 포트 연결(IPv6로 뜨면 v4tov6, IPv4로 뜨면 v4tov4 — 실제 뜬 주소를 netstat -ano | findstr 9223으로 먼저 확인):
    netsh interface portproxy add v4tov6 listenaddress=0.0.0.0 listenport=9223 connectaddress=::1 connectport=9223
    New-NetFirewallRule -DisplayName "WSL Chrome CDP 9223" -Direction Inbound -LocalPort 9223 -Protocol TCP -Action Allow
  3. 그 Chrome 창에서 직접 로그인
  4. WSL에서 storageState 다시 저장 (탭은 닫지 않기 — 이슈 7 참고): 
    NODE_PATH=<playwright-core 설치 경로> node -e "
const { chromium } = require('playwright-core');
const fs = require('fs');
(async () => {
  const browser = await chromium.connectOverCDP('http://<Windows 게이트웨이 IP>:9223');
  const context = browser.contexts()[0] ?? await browser.newContext();
  await context.storageState({ path: '/home/user/.cache/kdance-playwright-auth/state.json' });
  fs.chmodSync('/home/user/.cache/kdance-playwright-auth/state.json', 0o600);
})();
"
  5. Windows Chrome 종료 + portproxy·방화벽 규칙 삭제(정리)
  6. 평소처럼 /mcp로 playwright MCP 재연결 — 별도 설정 변경 불필요(저장 위치가 그대로라면)

8. 솔직히 말하는 리스크·주의사항

  • storageState 파일은 로그인 비밀번호와 동급입니다. 이 파일을 다른 사람에게 보내거나, 실수로 git에 커밋하거나, 권한 설정을 풀면 그 계정에 누구나 로그인할 수 있게 됩니다. 이번 설정은 파일 권한(600)과 저장 위치(git 추적 밖)로 최소한의 방어만 해둔 상태입니다.
  • 로그인 세션은 시간이 지나면 만료됩니다. 구글 등 서비스가 세션을 강제로 끊으면(비밀번호 변경, 장기 미사용 등) 6장의 절차를 다시 밟아야 합니다.
  • 디버그 포트를 다시 열 때는 항상 유선(또는 신뢰된 네트워크)에서, 작업이 끝나면 반드시 정리해야 합니다. 이슈 3에서 실제로 와이파이에 포트가 열린 채 방치된 적이 있었습니다 — 같은 실수를 반복하지 않도록 6장 절차 마지막에 정리 단계를 명시해뒀습니다.
  • Claude Code는 Windows 관리자 권한(UAC) 승인을 대신 클릭할 수 없습니다. 포트포워딩·방화벽 설정은 앞으로도 매번 사용자가 직접 관리자 PowerShell을 열어야 하는 부분으로 남아있습니다.

9. 자주 묻는 질문

Q. WSL2의 "mirrored 네트워킹 모드"를 쓰면 더 간단하지 않나요?

네, portproxy·방화벽 설정 자체가 필요 없어지는 더 근본적인 방법입니다. 다만 다른 네트워킹 작업(Docker 포트 바인딩 등)과 충돌할 수 있어서, 이번 작업 범위에서는 쓰지 않기로 했습니다. 지금 방식(storageState 재사용)으로도 "매번 포트를 열어야 하는" 번거로움 자체는 이미 없어졌기 때문에, mirrored 모드의 장점 상당 부분을 이미 얻은 상태입니다.

Q. 이제 Windows Chrome을 계속 켜둬야 하나요?

아니요. storageState 저장이 끝난 뒤에는 Windows Chrome, portproxy, 방화벽 규칙 전부 정리(삭제)했습니다. 평소에는 리눅스 헤드리스 Chromium만 혼자 동작합니다.

Q. mindpilot MCP도 같은 방식으로 Windows Chrome이 필요한가요?

mindpilot MCP는 구조도(다이어그램) 뷰어를 여는 용도라 이번에 정리한 playwright MCP와는 별개의 MCP 서버입니다. 다만 "리눅스 WSLg 창 표시가 불안정하다"는 근본 원인은 같아서, mindpilot 쪽은 core-rules.md에 별도로 기록된 자체 재연결 절차(/mcp 재연결 + 필요한 호출 한 번에 몰아서 실행)를 따릅니다. 로그인이 필요 없는 도구라 이 문서의 storageState 방식은 적용 대상이 아닙니다.

Q. "왕초보 가이드"인데 왜 이렇게 자세한가요?

여기 나온 문제들(포트 충돌, 관리자 권한, IPv6/IPv4 불일치, 프로필 문제)은 겉보기엔 사소해 보여도 원인을 모르면 몇 시간씩 헤매기 쉬운 것들입니다. "무엇을 했는지"보다 "왜 안 됐고 왜 이렇게 고쳤는지"를 알아야 다음에 비슷한 문제가 나와도 스스로 해결할 수 있습니다.
