Core · 02

관리자 스케줄 등록 → 예약 오픈 — 이 앱의 핵심

검색·예약·지도는 "회원을 학원까지 데려오는" 절반이고, 이 기능은 "학원이 등록하면 바로 예약·결제가 열리게 만드는" 나머지 절반이다. 학원 쪽 진입장벽이 곧 이 서비스의 공급(=등록된 학원 수)을 결정하므로, 검색·추천이 아무리 좋아도 이 등록 흐름이 번거로우면 학원이 안 들어온다.

화면 목업(입점 설명회 문서)은 실제 운영 중인 mobydick 앱의 탭바·카드·여백 패턴 중 참고할 만한 부분만 가져왔다 — 아이콘 기반 4탭(배경 강조 없이 색·굵기로만 활성 표시), 리스트 카드 반경 18px, 강조 카드 반경 24px. 색 체계는 그대로 가져오지 않았다 — mobydick은 무채색 하나로 절제하는 편집 톤이고, 이 앱은 장르 5색이 곧 제품 정체성이라 다른 선택이 맞다.

입력 한 번이 예약 가능한 수업이 되기까지

1

업로드

관리자 웹에서 포스터·전단지·스크린샷(형식 무관)을 업로드하면 OCR이 장르 · 요일 · 시간 · 가격 · 정원 등 필드를 자동으로 추출한다.

2

추출 결과 검토

OCR이 추출한 필드가 실제 앱 카드·캘린더 화면 그대로 미리 보이고, 신뢰도가 낮은 항목(특히 시간·가격)은 "확인필요"로 표시된다. 가격·정원처럼 되돌리기 어려운 필드를 게시 전 마지막으로 확인하는 단계다. 이 단계를 건너뛰고 바로 게시하지 않는다.

3

게시 — 검색·예약·결제에 동시 반영

확정된 스케줄이 검색 인덱스 (pgvector 임베딩 포함)에 들어가고, 같은 트랜잭션에서 예약 가능 슬롯과 결제 상품이 함께 생성된다. 셋이 따로 놀면 "검색에는 뜨는데 예약은 안 되는" 결함이 생긴다 — 그래서 하나로 묶는다.

⚠ 가격·정원은 검토 단계에서 반드시 확인

가격·정원처럼 되돌리기 어려운 필드를 OCR이 잘못 추출한 채 그대로 게시하면 실제 예약·결제가 잘못된 조건으로 열린다 — 버그가 아니라 돈 사고다. 검토 단계를 건너뛰고 바로 게시하는 경로는 만들지 않는다.

확장 — 같은 입력 폼이 콘텐츠 3종을 나눠 처리한다

"실시간 뉴스피드(파티·공연·대회)"와 "학원별 공지"도 핵심 기능인데, 전부 새로 만들 필요는 없다. 업로드→검토→게시 흐름은 그대로 두고, 콘텐츠 종류에 따라 뒤에서 갈라지는 것으로 설계하면 같은 폼을 세 번 만들지 않는다.

종류입력예약·결제노출 위치
수업 스케줄 포스터 업로드 → OCR 자동추출 → 검토 있음 — 정원·가격 검토 필수 검색 결과, 캘린더
파티 · 공연 · 대회 같은 업로드 폼 재사용 (OCR 자동추출) 선택 — 참가신청만 있거나, 아예 없을 수 있음 뉴스피드(전 학원 통합)
공지 관리자가 텍스트 직접 작성 (사진은 선택 첨부) 없음 학원별 공지 게시판

세 콘텐츠 모두 같은 입력 폼 컴포넌트를 재사용하고, 예약 연결 여부만 다르게 처리한다. 뉴스피드 쪽은 예약 연결이 선택이라, 데이터 모델에 bookable: bool 플래그 하나로 수업과 같은 테이블을 쓸지, 별도 Event 모델을 둘지는 구현 단계에서 후보 둘 다 가능 — SCH 단위로 착수할 때 정한다.

Stack · 04

결제 대행 구조 — 설계 전에 반드시 확인

"학원 대신 결제를 받고 수수료를 뗀다"는 이 앱의 핵심 기능이, 동시에 가장 위험이 큰 지점이다. 기술 스택보다 먼저 이 부분의 답을 갖고 들어가야 한다.

💳 정산 분배(하위 가맹점) 결제란

고객이 앱에서 결제하면 돈이 먼저 개발자(운영자) 명의 PG 가맹점으로 들어오고, 거기서 수수료를 뗀 나머지를 학원 계좌로 보내는 구조. 학원이 직접 카드 가맹점을 갖고 앱은 예약만 중개하는 구조보다 개발자가 지는 책임이 훨씬 크다.

  • PG 선정 시 확인 — "하위 가맹점 정산", "에스크로", "분배결제" 같은 키워드로 지원 여부를 먼저 물어볼 것. 일반 결제 연동 API로는 안 된다.
  • 전자금융거래법 관련 등록 — 타인의 자금을 잠시 보관했다가 이체하는 구조는 선불전자지급수단·전자지급결제대행 관련 신고·등록 대상이 될 수 있다.
  • 통신판매중개 표시 — 앱이 "학원과 고객을 중개"하는 입장임을 이용약관에 명확히 표시해야 분쟁 시 책임 소재가 갈린다.

법률 자문이 아니다. 실제 진행 전 PG사 기술영업·세무사와 반드시 1회 이상 확인할 것 — 여기서는 "무엇을 물어봐야 하는지"만 짚는다.

🎟 할인·구독 혜택 구조 (2026-09-13 확정)
  • 대학생 전용 3개월 램프 — 1개월차 무료, 2개월차 반값, 3개월차부터 정상가. 차액은 학원(업주)이 부담한다(2026-09-13 정책 결정, pricing-policy.md) — 학원 정산은 실제 결제된 금액 기준이다: 1개월차는 결제 자체가 없어 정산 0원, 2개월차는 반값 결제액에서 수수료 8%를 뗀 금액이 지급된다.
  • 월 구독 1+1 수강권 — 매달 구독 결제 중인 회원에게 분기마다(연 4회) 쿠폰 1장을 지급한다. 기존 수업 결제 1건 이상에 포함해서만 쓸 수 있고, 같은 수준·비슷한 장르 수업 1개를 추가로 무료 수강한다 — 단독으로 공짜 수업을 받는 게 아니다. 비용은 학원이 부담한다(좌석 1개를 무료로 내주는 것) — 결제된 1건에는 정상 수수료 8%가 그대로 붙는다. 분기가 끝나면 미사용 쿠폰은 소멸하고 다음 분기에 1장이 새로 나온다.
  • 일반 결제 수수료는 학원 부담 8%, 92% 지급 — 변동 없음.

모두 기기당 1회가 아니라 사람당 1회/분기 기준으로 막아야 한다. 앱 재설치로 우회되지 않게 서버에서 전화번호(본인인증) 기준으로 검증하고, 대학생 인증은 학교 이메일(.ac.kr) 도메인 확인 정도가 개인 개발자 단계에서 현실적인 선이다.

🔁 구독형 결제가 PG 선정 기준에 하나 추가된다

"매달 구독형"이 생기면서 PG는 하위 가맹점 정산 분배 지원뿐 아니라 정기결제(빌링키) 지원도 확인해야 한다 — 매달 카드 정보를 다시 받지 않고 자동 청구하려면 빌링키 발급·재시도(실패 시 카드 만료 등) 정책이 있는 PG여야 한다.

쿠폰은 별도 Coupon 테이블이 필요하다 — 발급 시각, 유효기간(분기 말 소멸), 사용 여부, 사용된 예약 ID를 갖는다. 분기마다(연 4회) 지급은 APScheduler 배치가 구독 결제 성공 이력을 보고 발급하는 쪽이, 실시간 트리거보다 검증하기 쉽다.

체크아웃 검증이 핵심이다. "결제 항목에 유료 수업이 1건 이상 포함되는가"와 "쿠폰의 +1 수업이 결제한 수업과 같은 장르·비슷한 레벨인가"를 서버에서 같이 막아야 한다 — 안 막으면 쿠폰 단독으로 공짜 수업을 받는 구멍이 생긴다.

Harness · 05

Claude Code MCP · Skill 조합

harness 플러그인이 중심이다. 이 프로젝트 전용 파이프라인(계획→구현→검증→문서화)이 아직 없기 때문에, 제일 먼저 할 일은 harness를 불러 그 파이프라인부터 만드는 것. 나머지 도구는 범용이라 그대로 가져다 쓴다.

도구역할이 프로젝트에서
harness플러그인 에이전트·스킬 구성 자체를 만들어 주는 메타 도구 가장 먼저 호출. planner·implementer·reviewer·explainer 에이전트와, 이 앱 전용 파이프라인 스킬을 새로 생성하는 진입점.
context7MCP 라이브러리 최신 문서를 실시간 조회 그대로 재사용. PG SDK·react-native-calendars처럼 버전에 민감한 라이브러리가 많아 오히려 비중이 커진다.
githubMCP 브랜치·PR·이슈를 다루는 저장소 연결 그대로 재사용. GitHub Flow·squash merge 같은 워크플로 규칙도 그대로 옮겨온다.
serenaMCP · 로컬 코드를 심볼 단위로 찾고 고치는 탐색 도구 그대로 재사용. 프로젝트 규모와 무관하게 유용.
memoryMCP 대화 사이에 지식을 기억해 두는 저장소 그대로 재사용 — 단, mobydick 메모리와 섞이지 않게 새 프로젝트 디렉터리에서 시작해야 자동으로 분리된다.
agent-reachMCP 웹·SNS 등 외부 자료를 조사하는 라우터 그대로 재사용. PG·지도 API 약관·요금제 비교 조사에 그대로 쓴다.
mindpilotMCP mermaid 다이어그램을 그려 주는 도구 그대로 재사용. 정산 분배 흐름(고객→PG→운영자→학원)처럼 돈의 흐름을 그림으로 남겨야 하는 지점이 새로 생겨 오히려 더 자주 쓰게 된다.
humanizer / humanizer-kr플러그인 · 스킬 AI 티 나는 문장을 사람 글처럼 다듬음 그대로 재사용. 커밋·PR·이용약관 초안 다듬기에 동일하게 적용.
strix스킬 보안 점검(펜테스트) 도구 선택 → 필수로 격상. 결제·개인정보(전화번호·위치)를 다루는 앱이라 정기 실행을 개발 루틴에 못 박아야 한다.
{project}-pipeline스킬 · 신규 계획→구현→검증→문서화를 잇는 오케스트레이터 harness로 새로 생성. mobydick-pipeline의 자리를 대신하지만, 내용은 이 프로젝트의 백로그 규칙에 맞게 새로 써야 한다.
implementation-guide스킬 · 신규 레이어 구조·마이그레이션 절차 같은 코딩 규칙 모음 harness로 새로 생성. PG 연동 절차·정산 배치 작성 규칙· 스토어 심사 체크리스트를 이 문서에 담는다.
review-qa스킬 · 신규 서버·API 명세·앱 타입 교차 검증 체크리스트 harness로 새로 생성. mobydick의 "스키마↔OpenAPI↔TS" 패턴은 그대로 두되, "결제 요청 금액 = PG 응답 금액 = DB 기록 금액" 대조 항목을 새로 추가해야 한다.
Screens · 06

화면 12개 ↔ 구현 매핑

kdance 화면 명세서에서 확정한 12화면을, 만들어야 하는 API·데이터 모델·우선순위로 옮겼다. 화면 번호는 명세서와 그대로 맞춘다 — 번호가 갈라지면 "그 화면 얘기하는 거 맞나"부터 다시 확인해야 한다.

#화면API · 데이터 모델우선순위
01회원가입 · 대학생 인증 POST /auth/verify-phone · POST /auth/verify-student — User.student_verified_atMVP
02홈 — 카테고리 검색 GET /academies?genre®ion&day — 카카오 Local + pgvector 유사도 2단계
03학원 상세 GET /academies/{id} — Academy·ClassSchedule MVP
04체크아웃 · 결제 POST /orders (정가-대학생할인-쿠폰 계산 → PG 호출) — Order MVP
05캘린더 · 알람 GET /me/schedule — expo-notifications + APScheduler 발송 2단계
06길찾기 카카오 Local 경로 API 그대로 프록시3단계
07뉴스피드 GET /events?type=party|performance|competition — Event(bookable:bool) 2단계
08학원 공지 GET·POST /academies/{id}/notices — Notice 2단계
09마이 · 구독 관리 GET /me/subscription · GET /me/coupons — Subscription·Coupon4단계
10관리자 · 스케줄 입력 POST /admin/schedules — ClassSchedule 직접 생성, 이미지는 오브젝트 스토리지에 선택 첨부MVP
11관리자 · 미리보기 GET /admin/schedules/{id}/preview — 게시 전 카드·캘린더 렌더링 확인 MVP
12관리자 · 정산 대시보드 GET /admin/settlements — 쿠폰 사용 건수는 4단계에서 컬럼 추가 MVP (기본) / 4단계 (쿠폰 표기)

MVP가 6개 화면(01·03·04·10·11·12)뿐인 이유 — "업로드→검토→게시→예약→결제→정산" 한 바퀴가 실제로 도는지가 이 앱 전체의 전제 조건이다. 검색·캘린더·피드·구독은 그 위에 얹는 것들이라, 먼저 확인 안 하면 나머지를 만들 근거가 없다.

Roadmap · 07

베타 → 안정화 → 출시 순서

정산 분배형 결제는 검토·계약에 시간이 걸리므로, 그 결정이 끝나기 전에 나머지 기능부터 검증하는 순서로 짰다 — WORKFLOW 원칙과 같다: 선행이 걸린 항목은 그 결정이 닫히기 전에 착수하지 않는다.

1

MVP — 관리자 스케줄 입력 + 예약·결제, 단일 학원 (화면 01·03·04·10·11·12)

이 앱의 핵심 흐름(입력→미리보기→게시)부터 먼저 검증한다. 결제는 정산 분배 없이 학원이 직접 PG 가맹점을 갖는 단순 구조로 시작 — "스케줄 등록"과 "정산 분배"는 서로 다른 위험이라 한 번에 두 개를 안 건다.

완료 기준: 실제 스케줄 1건으로 입력→미리보기→게시→예약→결제까지 1회 성공
2

검색 플래너 + 캘린더·알람·피드·공지 (화면 02·05·07·08)

장르·지역·시간대 기반 추천과 일정 캘린더, 수업 전 알람을 붙인다. 이 시점부터 pgvector 기반 선호 추천이 들어간다.

완료 기준: 알람이 실제 수신 시각에 도착하는지 실기기 확인
3

경로 내비게이션 지도 (화면 06)

카카오 Local API로 학원 위치를 좌표화하고 경로를 그린다.

완료 기준: 실기기에서 도보·대중교통 경로 표시 확인
4

정산 분배형 결제 + 구독·쿠폰으로 전환 (화면 09, 12 쿠폰 표기)

PG 계약·법적 검토가 끝난 뒤에만 착수. 여기서부터 진짜 "학원 대신 결제 + 수수료" 모델이 시작된다 — 3단계까지의 검증된 앱 위에 결제 구조만 교체한다.

선행 조건: PG 하위가맹점 계약 완료 + 컴플라이언스 확인
5

베타테스트 → 스토어 정식 출시

갤럭시 스토어 베타 트랙(또는 사내 테스트)으로 먼저 열고, strix 보안 점검을 통과한 뒤 갤럭시 스토어에 정식 제출한다.

완료 기준: strix 리포트 Critical 0건
Free · 08

무료 우선순위 가이드

원칙 — 이미 정한 것이 우선이다. 아래 표는 기존 선택을 뒤집는 게 아니라, "모두 무료로" 라는 조건 위에서 더 나은 무료 대안이 있으면 그 이유와 같이 보여주는 참고표다. 바꿀지는 각 항목의 이유를 보고 판단한다.

분류기존 선택 (우선)더 나은 무료 대안추천 이유
채팅 AI Qwen3.5 9B (Ollama, 로컬) — 완전 무료·무제한, 이 노트북(8GB) 기준으로 이미 검증됨. 바꿀 이유 없음
지도·위치 카카오 Local API — 일 10만 건·월 300만 건 무료. 개인 개발자 단계에서 쓸 일 없는 수준으로 넉넉함
임베딩 NVIDIA 원격 API 로컬 소형 임베딩 모델 (예: nomic-embed-text, Ollama) NVIDIA는 "평생 무료"가 아니라 가입 크레딧 최대 5,000개 한정이라 언젠가 끊긴다. nomic-embed-text는 ~280MB로 아주 작아서 qwen3.5:9b와 8GB에서 같이 상주해도 여유가 있다 — 완전 무료·무제한이 된다. 단, mobydick과 달리 kdance는 벡터 차원 제약이 없으니 자유롭게 고를 수 있다
오브젝트 스토리지 S3 호환 (업체 미정이었음) MinIO(오픈소스, 셀프호스팅) 1순위 내 디스크만 쓰니 용량 제한도 요금도 없음. 포스터 원본을 인터넷에 직접 노출해야 할 때만(예: 인스타 공유) Cloudflare R2 무료 티어로 승격 — 그 전까진 MinIO로 충분
결제대행(PG) 포트원 / 토스페이먼츠 — (무료 대안 구조적으로 없음) PG는 거래 수수료로 돈을 버는 업종이라 "무료 API" 자체가 존재하지 않는다. 다만 월정액 없이 거래당 수수료만 받는 요금제는 있어 — 매출이 없으면 비용도 0이다. "완전 무료"는 아니지만 "고정비 0"은 달성 가능
배치·캐시 APScheduler · Redis — 둘 다 오픈소스, Docker 셀프호스팅. 완전 무료
푸시 알림 Expo Push / FCM — 완전 무료. "1일 전 점심 1회·1시간 전 선택 알람"은 APScheduler가 발송 트리거를 만들고 Expo Push가 무료로 전달 — 추가 비용 없음
배포 자동화 Fastlane — 오픈소스 무료. 갤럭시 스토어(Samsung Seller Portal)는 등록비도 무료라 이 항목은 고정비 없음 — distribution-policy.md 참고

진짜로 바꿀 가치가 있는 건 하나뿐이다 — 임베딩(NVIDIA 원격 → 로컬 소형 모델). 나머지는 이미 최선이거나, 구조적으로 무료가 안 되는 항목(PG)이라 그대로 둔다.
