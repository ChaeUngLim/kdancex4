**Q1 확정이 요구사항을 늘렸다.** 이메일 도메인 인증은 재학 여부를 보장하지 않는다 —
졸업생 계정이 살아 있으면 통과한다. 인증이 약해진 만큼 사후 통제를 보강했다.

- FR-006b — 같은 학교 이메일로 여러 계정이 혜택 받는 것 차단
- FR-006c — 인증의 한계를 명시하고 FR-007(혜택 회수)이 실제로 동작하도록 요구
- FR-006d — 차액을 부담하는 학원이 혜택 사용 현황을 조회

**Q2 확정은 정의서까지 손댔다.** 「남/녀 정원」 표기 4곳을 `Lead/Follow` 로 바꿨고,
표기 잔존이 없음을 검사로 확인했다. 저장 값은 역할이고 화면 표기만 학원별로
바꿀 수 있게 했다(FR-092d). → 2026-09-26 정원을 남·여 성별로 바꾸면서 FR-092d 는 삭제됐다.

**해결된 항목 — Q3(강사 급여 정산 범위, 2026-09-21).** 강사는 프리랜서라
급여 개념이 없고, 온라인 수강 신청과 개인 레슨의 **수강 완료분**에 대해서만
정산이 일어난다. FR-127~FR-135 를 신설하고 US9(정산)·경계 상황·성공 기준
(SC-010a·SC-010b·SC-022a·SC-022b)·범위 경계·전제(5a·5b·5c)에 반영했다.

이 답변이 spec 을 구조적으로 바꾼 지점은 셋이다.

1. **정산 트리거가 결제에서 시각으로 옮겨졌다.** 수업 시작 → `정산 완료 예정`,
   기간 종료 → `정산 완료`. 결제와 정산 사이가 한 칸이 아니라 두 칸이다.
2. **지급 경로가 강사 전용 계좌로 고정됐다.** 강사 1인당 하나이고 정산 이력이
   그 계좌에 묶인다.
3. **조회 권한이 비대칭이다.** 강사는 본인 것만, 업주는 학원 전체 수업과 소속
   강사 전원. 단방향이라 강사는 옆을 보지 못한다.

**초안에서 한 번 잘못 잡았던 것** — 처음에는 출석을 정산 단계 전이의 트리거로
적었다. 사용자 확인 결과 전이는 **시각**으로 일어나고, 출석은 노쇼·분쟁을 가릴 때
꺼내 보는 근거다(FR-135b). 바로잡았다.

**새로 생긴 미정 2건** (질문으로 올리지 않고 전제로 기록했다. 둘 다 결제 경로
구현 전까지 답이 나오면 된다):

- 전제 5b — 개인 레슨의 플랫폼 수수료율. 학원 수수료 8%는 학원 경유 거래의
  값이라 개인 레슨에 그대로 쓸 근거가 없다
- 전제 5c — 프리랜서 지급에 따르는 사업소득 원천징수. 세율과 처리 주체는
  세무 확인 대상이며, spec 은 내역 구분 표기만 정한다(FR-134)

**검증 중 확인한 예외 하나.** 「현재 구현 상태」와 「Dependencies」 두 표는
기술 이름을 쓴다. 이 둘은 요구사항이 아니라 **실측 근거**이고, 사용자 요청이
"전체 소스를 분석해서" 였으므로 근거를 지우면 확인이 불가능해진다.
요구사항 절(FR)과 성공 기준 절(SC)은 기술 중립을 지켰다.

**US11(사용자 문의·AI 응답) 추가 시 내린 판단 3가지.** 사용자가 "너의 판단으로
아이디어를 내서" 라고 했으므로, 무엇을 왜 그렇게 정했는지 남긴다.

1. **P1 의 범위를 좁게 잡았다.** 출시 게이트인 것은 `T3(사람)` 경로뿐이고, AI 층은
   그 위에 얹는 개선이다. AI 를 전부 꺼도 US11 이 성립하게 만들어 슬라이스의
   독립성을 지켰다.
2. **모델을 쓰지 않는 경로를 기본으로 뒀다.** `docs/kdance-beta-infra.html` 의 실측
   (GPU 1대 동시 1~4건)이 근거다. 같은 문서가 이미 "옵션 B+C 를 먼저" 라고
   권고하고 있어, 그 권고를 4단계 분류로 구체화했다.
3. **금액을 모델이 만들지 못하게 막았다**(FR-210·FR-211). 환불 예상액은 취소
   미리보기와 같은 로직이 낸 값을 그대로 쓴다. 두 경로가 각자 계산하면 언젠가
   어긋나고, 그 어긋남이 분쟁이 된다.

**문의 배정을 한 번 고쳤다.** 초안에서는 결제·환불 분쟁을 운영자에게 보냈는데,
사용자 확인 결과 **결제·환불 정책이 학원마다 다르므로 그 학원(개인 레슨은 강사)이
1차로 답한다.** 운영자는 2차 조정자다. 이건 이미 코드에 반영된 구조와도 맞는다 —
`Academy.refund_policy_tiers` 가 학원별 값이다.

다만 **수업 시작 24시간 이상 전 전액 환불은 학원과 무관한 플랫폼 고정 규칙**이라
(`backend/app/services/refund_policy.py` 실측) 답변에서 두 층을 구분하게 했다
(FR-205·FR-206).

> **2026-09-25 대체** — 위 두 단락은 당시 판단이다. 지금은 운영자가 2차 조정자가 아니고(FR-204(운영자 역할 한정)), 24시간 전액 규칙과 학원 비율표는 폐기했다(Q11(환불 방식 변경의 뒤처리) ②). 환불은 업주가 정하고 실행한다(FR-098b(환불 요청 경로)).

**약관은 spec 밖에 두었다.** `docs/terms-of-service.md` 에 초안을 만들고, spec 에는
**시스템이 갖춰야 할 기능**만 FR-240~FR-249 로 넣었다. 약관 문구의 법적 타당성은
이 spec 이 보증하지 않으며, 변호사 검토가 필요한 지점 5가지를 약관 문서 말미에
남겼다(전제 5e).

**반복 횟수** — 5회(초안 · 정산 확정 · 문의 기능 · 배정 정정 · 약관). 번호 중복·잔존
표현은 매회 검사로 확인했다.

## 2026-09-24 재검증 — S0 로컬 운영 재구성

**무엇이 바뀌었나** — US12 · FR-260~FR-279(20개) · SC-040~SC-048(9개) · 엣지 케이스 「AI 동시 사용」 · 엔티티 3종 추가. 규모 단계 S0, AI 켜는 시점, SC-017, FR-200 묶음 전제 문장, 구현 상태·선행 조건 표 수정. 기존 번호는 지우거나 재사용하지 않았다.

|---|---|---|
| 기술 중립(FR·SC·US 절) | 통과 | 새 절 3곳에 제품·기술 이름 검색 — "프롬프트" 1건을 "AI 지시문" 으로 고쳐 0건 |
| [NEEDS CLARIFICATION] | 0건 | 검색 |

| 수용 시나리오 | 통과 | US12 시나리오 10개가 FR-260~FR-273 을 덮는다. FR-274~FR-279(측정·운영)는 SC-043·SC-048 로 판정 |

**판단 3가지 — 사용자가 "너가 판단했을 때" 라고 했으므로 남긴다.**

1. **추정을 실측으로 바꿨다.** 기존 spec 은 "GPU 1대 동시 1~4건" 을 실측으로 인용했지만 원문(`docs/kdance-beta-infra.html`)은 "체감상" 추정이었다. 이 노트북에서 직접 재 보니 구성에 따라 동시 10명 완료 p95 가 55.4초와 18.0초로 갈렸다. 그래서 SC-041 에 **한 건씩 처리하는 구성은 통과하지 못하는 값(25초)** 을 넣었다 — 요구사항이 구성을 강제하게 했다.
2. **AI 를 S0 에서 먼저 켠다.** 기존 spec 은 T2·AI 추천을 S2 이후로 미뤘다. 실사용자 노출 시점은 그대로 두고, 시험 데이터로 S0 에서 먼저 켜서 판정하도록 바꿨다. 지어내기(F3)·언어 섞임(F4)을 실측에서 이미 봤기 때문에, 데이터가 쌓인 뒤에 발견하면 늦다.
3. **SC-017 을 고쳤다.** "동시 사용자 10만 명" 은 사용자 요청의 "베타 1명~최대 10만 명" 을 동시 접속으로 옮긴 표현이었다. 가입자 규모로 고치고 S4(서버 이전 후) 판정 대상임을 밝혔다. 노트북 단계에서 이 목표를 재는 것은 의미가 없다.

**남은 미검증** — 임베딩·재정렬 모델(미설치), 평가 세트(없음), 권장 구성 적용 여부(사람이 정함). 세 가지 모두 spec 의 「선행 조건이 미충족인 것」 표에 있다.

## 2026-09-24 재검증 2 — 규모 목표 변경

사용자 요청으로 규모 목표를 **"베타 1명~최대 10만 명 → 3년 이후 1천~10만 명"** 에서
**"베타 1명~최대 10명 → 3년 이후 1천~1만 명"** 으로 바꿨다. 위 재검증의 판단 3번이 인용한
"10만 명" 은 바뀌기 전 요청 원문이다.

| 바뀐 곳 | 내용 |
|---|---|
| Input | 요청 원문 교체, 원래 문구를 괄호로 보존 |
| 규모 단계 | S0~S4 다섯 → S0~S3 넷. S1 을 "베타 1~10명" 으로, S2·S3 를 3년 이후 목표의 하한·상한으로. S4(10만 명) 삭제, 그 통과 조건(SC-018·SC-023)은 S3 로 이동 |
| SC-017 | 10만 명 → 1만 명(S3) |
| AI·T2 개방 시점 | "S2 이후" → "S1 에서 게시 수업 데이터가 쌓인 뒤". 인원 기준을 그대로 두면 베타가 10명이라 핵심 기능이 3년 뒤로 밀린다 — **이 항목은 판단이 들어간 변경이라 사용자 확인 대상** |

검증: 번호 변경 없음, [NEEDS CLARIFICATION] 0건, 규모 관련 "10만" 잔존은 변경 이력·삭제 기록·금액(10만원)뿐이다.
