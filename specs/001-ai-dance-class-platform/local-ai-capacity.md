## 4. 발견 — 요구사항으로 옮긴 것

| # | 발견 | 근거 | spec 반영 |
|---|---|---|---|
| F1 | **Ollama 0.33.3 은 이 모델을 병렬로 돌리지 않는다.** 병렬 값을 4·10 으로 줘도 한 번에 1건만 처리한다 | 로그 `model architecture does not currently support parallel requests architecture=qwen35`, 실행 인자 `-np 1` | SC-041 을 달성하려면 병렬 처리가 되는 서빙 경로가 필요하다 → 6절 |
| F2 | 같은 모델 파일을 llama-server 로 직접 띄우면 슬롯 10개가 동작한다. 동시 10명 완료 p95 가 **55.4초 → 18.0초** | 3-1 표 | SC-041 수치의 근거 |
| F3 | **모델이 입력에 없는 사실을 지어냈다.** 후보에 거리 정보가 없는데 "이동 시간이 30분 이내", "강남역에서 도보로 이동" 을 썼다 | 단일 호출 응답 표본 | FR-267 |

## 5. 동시 10명의 실제 의미 — 계산

에이전트 1회 완료 p95 18.0초는 **10명이 같은 순간에 질문 버튼을 누른** 최악의 경우다.
10명이 평균 30초에 한 번 묻는다면 순간 동시 요청은 대개 10보다 훨씬 적다. 반대로
Planner·Writer 외에 Reviewer 도 모델을 부르면 호출이 3회로 늘어 약 1.5배가 된다.
그래서 **Reviewer 검증은 모델이 아니라 규칙(시간 충돌·정원·존재 여부)으로 한다**
(FR-038 · FR-267). 모델 호출을 질문당 최대 2회로 묶는 것이 FR-268 이다.

## 6. 권장 구성 (S0) — **2026-09-24 적용함**

> **적용했다(2026-09-24, 사용자 요청).** `infra/docker-compose.yml` 의 `llm` 서비스
> (`kdance-llm`, 포트 **11436**). 기존 `ollama` 컨테이너는 GPU 를 다투지 않도록 **멈추고
> 자동 재시작을 껐다**(`restart=no`). 모델을 새로 받을 때만 `docker start ollama` 로 켜고,
> 받은 뒤에는 다시 멈춘다. OmniRoute 가 Ollama 를 부르면 그때는 응답하지 않는다.
>
> 적용 후 재측정(AC 전원, GPU P0 59°C) — 에이전트 1회·동시 10명, 3회:
>
> | 회차 | 첫 글자 p95 | 완료 p95 | 비고 |
> |---|---|---|---|
> | 1 | 14.99초 | 21.82초 | 컨테이너 기동 직후 첫 부하 |
> | 2 | 9.23초 | 16.63초 | |
> | 3 | 8.50초 | 14.98초 | |
>
> 기동 직후 첫 부하가 가장 느리다. SC-041(15초·25초) 판정은 **예열 뒤** 측정으로 한다.

| 항목 | 권장 | 이유 |
|---|---|---|
| 대화 생성 서빙 | llama-server 직접 실행, 슬롯 10, 전체 컨텍스트 40,960 (슬롯당 4,096) | F1·F2. 3-1 표의 최선값 |
| KV 캐시 | `q8_0` (K·V 모두), Flash Attention on | 메모리 절반, context7 로 확인한 Ollama 문서도 품질 손실이 거의 없다고 한다 |
| GPU 적재 | 전 레이어 GPU (`-ngl 999`) | VRAM 7.4GB 안에 들어간다 |
| 사고(thinking) 모드 | 기본 끔(`--reasoning off`). 서버 기본값이 켜짐이라, 끄지 않으면 옵션을 빠뜨린 요청이 토큰을 사고에 다 쓰고 **본문이 비어서** 온다(적용 중 실측) | F5 |
| CUDA 백엔드 | `cuda_v12` | 드라이버 566.26 은 CUDA 12 계열이라 `cuda_v13` 이 GPU 를 못 잡았다(실측: `no usable GPU found`) |
| Ollama | 모델 저장소·관리용으로만 남긴다 | 같은 모델 파일(blob)을 llama-server 가 읽는다 |

측정에 쓴 실행 명령:

```bash
docker run -d --name llama-bench --gpus all -p 11436:8080 -v ollama:/root/.ollama \
  -e CUDA_VISIBLE_DEVICES=0 -e LD_LIBRARY_PATH=/usr/lib/ollama/cuda_v12:/usr/lib/ollama \
  --entrypoint sh ollama/ollama -c \
  "cp /usr/lib/ollama/cuda_v12/libggml-cuda.so /usr/lib/ollama/ && exec /usr/lib/ollama/llama-server \
   --model /root/.ollama/models/blobs/sha256-dec52a44… --host 0.0.0.0 --port 8080 \
   -c 40960 -np 10 --cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on -ngl 999 --jinja"
```

`cp` 로 백엔드를 옮기는 것은 측정용 우회였다. 상시 운영 구성에서는 환경 변수
`GGML_BACKEND_PATH=/usr/lib/ollama/cuda_v12/libggml-cuda.so` 로 대신했다(VRAM 6,372MiB 적재 확인).

## 7. 임베딩·재정렬 — 미측정, 방향만 정한다

- GPU 에 자리가 없으므로(F7) **CPU 에서 돌린다.** 20 스레드가 있다
- 대화 응답이 먼저다. 수업 설명 색인처럼 급하지 않은 임베딩은 **대화가 없을 때 몰아서** 한다(FR-264)
- 질문 1건의 임베딩은 문장 1개라 CPU 로도 짧다고 **예상하지만 재지 않았다.** 모델을 정하면 `infra/ai-bench/` 에 같은 방식으로 추가해 잰다
- 정의서의 `Nemotron-3-Embed-1B-BF8` · `llama-Nemotron-Rerank-1B-v2` 는 이번에도 실체를 확인하지 않았다 — 「11-2. 알려진 위험」의 **미검증** 그대로다

- 표본이 요청 10건 단위라 p95 는 사실상 최댓값이다. 수치는 **자릿수와 구성 간 비교**로 읽는다
