| 2026-09-25 | **환불 방식 변경** — 플랫폼 공통 "24시간 전 전액 + 비율표 자동 적용" 폐지. 모든 환불은 문의로 요청하고 학원이 자기 규정대로 처리(FR-098b(환불 요청 경로)). 같은 날 넣었던 결제 당일 셀프 환불(FR-098a(당일 셀프 환불·삭제됨))은 계좌이체 방식이라 어렵다는 판단으로 삭제. 이어서 환불 요청은 업주만 받고 처리하도록 바꿨다 — 개인 레슨 포함, 운영자 이관·분쟁 조정(FR-189(운영자 환불 조정·삭제됨)·US10(운영자 시스템 관리) 2번·US11(문의 응답·사람 이관) 6c) 삭제. 이어서 업주가 정해진 양식으로 쓴 환불·취소 공지가 강사의 수업 등록 페이지에 자동으로 들어가게 했다(FR-099a(환불·취소 공지 양식)·FR-099b(공지 자동 입력)). 학원 환불 규정은 모든 수업 공지에 표시 필수, 미등록 시 게시 불가(FR-099(환불 규정 등록·표시)·FR-246(규정 없는 학원 게시 차단)). FR-205(환불 문의 안내)·FR-206(학원 환불 규정 근거)·US11 6a·6b 수정, Q11(환불 방식 변경의 뒤처리) 추가 | 사용자 요청 — 환불 규정이 업주마다 다르고, 학원이 자기 규정대로 처리해야 한다 |
| 2026-09-25 | **문의 받는 사람 재정의(핵심)** — 운영자는 앱·웹 시스템만 관리한다(계정·오류·개인정보 삭제·신고·결제 시스템 장애). 사람에게 가는 문의는 전부 문의자가 검색해서 고른 업주에게 알림으로 간다(개인 레슨 포함). AI 응답(T0~T2)은 유지하고 AI 가 못 답하면 업주 선택 화면으로 넘긴다. **수정** US10(운영자 시스템 관리) · US11(문의 응답·사람 이관) 10번 · FR-200(질문 4등급 분류) T3 · FR-203(업주 선택 문의) · FR-204(운영자 역할 한정) · FR-209a(강사·업주 운영 문의) · FR-226(지식 승인) · SC-029c(업주 건너뛴 배정 0건) · 엣지 케이스 5건 · **추가** FR-203a(AI 이관 경로) | 사용자 요청 — "운영자는 앱(웹) 시스템만, 모든 문의는 검색 후 업주 선택" 이 핵심 |
| 2026-09-25 | **정규 과정 카드 결제 허용** — 정기 수업만 계좌이체 외에 카드(PG, 일시불)도 받는다(FR-111a(모든 결제 카드 허용)). 다른 상품은 계좌이체 그대로. Q12(카드 수수료 부담) 추가 | 사용자 요청 |
| 2026-09-25 | **결제 상세 구성** — 확정된 결제 규칙을 한곳에 모으고 빠진 흐름을 채웠다(FR-280~FR-299(결제수단 결정 ~ 결제 정보 보안), 20건): 결제수단 결정표, 결제 화면 필수 표시, 할인 계산 순서, 주문 시점 값 고정, 수단별 결제 기한, 입금 전 셀프 취소, 웹훅 판정, 딥링크 입금 확인, 확정 후 일괄 처리, 금액 불일치·중복·지연 입금, 업주 환불 입력 항목, 정규 과정 중도 환불 보조, 수단별 환불 실행, 쿠폰 복구, 구독 해지, 주문 상태 6종, 카드·환불계좌 보안. 전제 18(결제 기한) 추가 | 사용자 요청 — "결제 로직은 이걸로 확정으로 예상해서 결제 요구사항을 구체적으로" |

| 2026-09-25 | **Q12(정규 과정 카드 수수료 부담) 확정** — 카드 결제 수수료는 업주(판매자)가 부담한다. 학원 정산에서 플랫폼 수수료와 따로 실비 공제, 베타 면제 기간에도 공제, 수강생 전가 금지. FR-111a(모든 결제 카드 허용) 수정, FR-125a(정산 내역 항목)·FR-125b(입점 시 고지·동의) 추가 | 사용자 결정 |
| 2026-09-25 | **Q11(환불 방식 변경의 뒤처리) ② 확정 — 기존 환불 계산 코드 폐기.** 24시간 규칙·비율표 자동 계산과 비율표 설정 화면을 버리고, 환불 실행 쪽(잠금·멱등키·감사 로그·PG 어댑터·환불계좌 검증)만 살려 쓴다. 코드 삭제는 아직 하지 않았다 | 사용자 결정 |
| 2026-09-25 | **구독 쿠폰 생성 조건** — 1+1 쿠폰은 **구독을 연속 3개월 유지할 때마다 1장.** 발급 뒤 개월 수를 0 으로 되돌려 다음 3개월을 다시 센다. 결제가 끊기면 0 부터. 쿠폰은 발급 후 3개월에 소멸. 같은 날 먼저 넣었던 "달력 분기 기준" 안을 이 방식으로 바꿨다. FR-120(구독 1+1 쿠폰)·FR-122(1+1 쿠폰 소멸) 변경, FR-120a(쿠폰 생성 조건) 추가 | 사용자 요청 — "다음 쿠폰도 월 구독 3개월씩 유지되어야만 한 개씩 생성" |

| 2026-09-25 | **Q13(구독 판매 주체·요금) 판매 주체 확정** — 구독은 플랫폼 상품. 구독료는 플랫폼 수입(학원 정산 대상 아님), 연 구독 할인은 플랫폼 부담, 구독 환불은 플랫폼(운영자)이 받는다. 1+1 쿠폰 좌석은 여전히 학원 부담. FR-112b(구독은 플랫폼 상품) 추가, FR-112a(연 구독 10% 할인)·FR-297(구독 해지) 수정 | 사용자 결정 — "플랫폼의 몫" |

US13(관리자 결산·수수료) · FR-300~FR-319(역할별 로그인 분기 ~ 기준 시각·월 마감) · SC-050~SC-054(콘솔 합계 원장 일치 ~ 학원 결산 도달 3번) 추가 | 사용자 요청 — 업주 수수료를 정할 근거 |

## User Scenarios & Testing *(mandatory)*

이 서비스는 **양면 시장(two-sided market)** 이다. 수요(사용자)와 공급(강사·업주) 중 한쪽만 있으면 거래가 0건이므로, US1(수업 찾아 결제) 과 US2(강사 수업·자리 관리) 를 둘 다 P1 으로 둔다. 둘이 한 쌍으로 완성될 때 비로소 "수업 하나가 실제로 팔린다".

---

### User Story 1 - 취향·일정에 맞는 수업을 찾아 결제까지 끝낸다 (Priority: P1)

댄스를 배우고 싶은 사람이 앱을 깔고, 관심 장르와 활동 가능한 시간·지역을 입력한다. 그 조건에 맞는 수업 목록을 받아 하나를 고르고, 정원이 남아 있는지 확인한 뒤 결제한다. 결제가 확인되면 예약이 확정되고 내 캘린더에 자동으로 올라간다.

**Why this priority**: 이 흐름이 돌지 않으면 나머지 전부가 의미 없다. 매출이 발생하는 유일한 경로이고, 이미 만들어 둔 취소·환불 코드가 붙을 대상이기도 하다.

**Independent Test**: 수업 1건과 사용자 1명만 있으면 끝까지 검증된다 — 가입 → 취향 입력 → 검색 결과에 그 수업이 나옴 → 결제 → 예약 확정 → 캘린더 등록 확인. 추천 알고리즘 없이 단순 필터 검색만으로도 이 슬라이스는 성립한다.

**Acceptance Scenarios**:

1. **Given** 관심 장르 "살사/바차타", 활동 가능 시간 "평일 저녁", 지역 "강남"을 입력한 신규 회원이, **When** 홈 화면을 열면, **Then** 그 조건에 맞는 수업만 목록에 나오고 각 수업에 정원 대비 신청 인원(예: 8/12)이 표시된다.
2. **Given** 정원 12명 중 8명이 찬 수업을 선택한 회원이, **When** 결제를 완료하면, **Then** 예약 상태가 확정(confirmed)으로 바뀌고 신청 인원이 9/12 로 증가하며 내 캘린더에 해당 일시가 등록된다.
3. **Given** 가상계좌를 발급받고 아직 입금하지 않은 회원이, **When** 입금 기한이 지나면, **Then** 예약이 자동 취소되고 잡아 둔 자리가 다시 신청 가능해진다.
4. **Given** 이미 다른 수업이 잡혀 있는 시간대의 수업을 고른 회원이, **When** 결제 화면에 진입하면, **Then** 일정이 겹친다는 경고와 겹치는 수업의 이름·시각이 함께 표시된다.
5. **Given** 정원이 가득 찬 수업을 보고 있는 구독자(또는 가입 3개월 안의 회원)가, **When** 수업 시작 24시간 전까지의 시점에 신청을 누르면, **Then** 결제는 진행되지 않고 대기 순번이 부여되며 그 순번이 화면에 표시된다. 구독하지 않은 회원에게는 대기 신청 대신 구독 안내가 보인다 (2026-09-25 변경).
6. **Given** 리드 6명 / 팔로우 6명 정원인 수업에서 팔로우만 마감된 상태일 때, **When** 회원이 예약 화면을 열면, **Then** 리드는 신청 가능하고 팔로우는 대기 신청만 가능한 것으로 각각 표시된다.
7. **Given** 프로필에 팔로우를 선호로 등록한 회원이, **When** 예약 화면에 들어가면, **Then** 역할이 팔로우로 미리 선택되어 있고 리드로 바꿀 수 있다.

### User Story 2 - 강사가 수업을 열고 자리와 대기자를 관리한다 (Priority: P1)

강사가 프로필(장르·세부장르·경력·활동 학원)을 등록하고, 자신이 가능한 시간을 표시한 뒤 수업을 만든다. 수업에는 일시·장소·정원·역할별 정원·수강료가 붙는다. 공개하면 사용자 검색 대상이 되고, 신청이 들어오면 명단과 남은 자리를 실시간으로 본다.

**Why this priority**: 공급이 없으면 US1(수업 발견·결제)이 빈 화면이 된다. 수업 데이터의 최초 생산자가 강사다.

**Independent Test**: 강사 계정 하나로 수업을 만들고 공개한 뒤, 검색 결과에 노출되는지와 신청이 들어왔을 때 명단·잔여 자리가 맞게 바뀌는지로 검증된다.

**Acceptance Scenarios**:

1. **Given** 승인된 강사가, **When** 장르·레벨·수업구분·일시·장소·정원·수강료를 채워 수업을 공개하면, **Then** 그 수업이 사용자 검색 결과에 즉시 나타난다.
2. **Given** 같은 시간대에 이미 자신의 다른 수업이 있는 강사가, **When** 새 수업을 그 시간에 만들려 하면, **Then** 저장이 거부되고 충돌하는 수업이 함께 표시된다. 소속 학원이 다르더라도 동일하게 막힌다.
3. **Given** 수강 신청이 9건 들어온 정원 12명 수업의 강사가, **When** 대시보드를 열면, **Then** 확정 인원·역할별 잔여 자리·대기자 수·취소 인원이 한 화면에 보인다.
4. **Given** 사정이 생긴 강사가, **When** 수업을 휴강 처리하면, **Then** 결제한 모든 수강생에게 알림이 가고 각자에게 환불 또는 보강 중 선택지가 제시된다.
5. **Given** 수강생 5명이 결제했고 그중 3명이 출석을 마친 수업의 강사가, **When** 정산 화면을 열면, **Then** 완료 3건은 정산 대상으로, 미완료 2건은 정산 보류분으로 나뉘어 표시된다.
6. **Given** 개인 레슨을 진행하는 강사가, **When** 정산 내역을 보면, **Then** 학원 수업분과 개인 레슨분이 구분되어 표시되고 개인 레슨분에는 학원 수수료가 붙지 않는다.

### User Story 3 - 업주가 포스터 한 장으로 수업을 등록하고 공간 충돌을 막는다 (Priority: P2)

학원 업주가 수업 포스터·전단지·스크린샷을 올리면 시스템이 장르·요일·시간·가격·정원을 자동으로 읽어낸다. 업주는 읽어낸 값을 검토·수정한 뒤 게시한다. 같은 강의실·같은 시간에 두 수업이 잡히는 일은 시스템이 막는다.

**Why this priority**: 입점 영업의 핵심 설득 논리("포스터 한 장만 올리면 나머지는 저희가 합니다")이자, 학원 수를 늘리는 속도를 결정한다. 다만 US1(수업 발견·결제)·US2(수업 개설·정원 관리)가 돌아야 의미가 생긴다.

**Independent Test**: 포스터 이미지 1장을 올려 추출 → 검토 → 게시까지 하고, 게시된 수업이 검색에 나오는지로 검증된다. 자동 추출 정확도가 낮아도 검토 화면에서 고칠 수 있으므로 슬라이스는 독립적으로 성립한다.

**Acceptance Scenarios**:

1. **Given** 수업 정보가 적힌 포스터를 가진 업주가, **When** 이미지를 업로드하면, **Then** 장르·요일·시간·가격·정원이 채워진 검토 화면이 뜨고, 신뢰도가 낮은 항목에는 "확인필요" 표시가 붙는다.
2. **Given** 검토 화면을 보고 있는 업주가, **When** 검토를 건너뛰고 바로 게시하려 하면, **Then** 그 경로 자체가 존재하지 않아 반드시 검토 단계를 거친다.
3. **Given** A 강의실 화요일 20:00–21:00 수업이 이미 있는 학원이, **When** 같은 강의실·같은 시간대에 다른 수업을 게시하려 하면, **Then** 게시가 거부되고 충돌한 수업이 표시된다.
4. **Given** 게시가 완료된 수업이, **When** 사용자 앱에서 조회되면, **Then** 검색 노출·예약 슬롯·결제 상품이 모두 함께 준비되어 있어 바로 결제할 수 있다.

### User Story 4 - 일정 충돌 없이 제때 알림을 받는다 (Priority: P2)

사용자가 신청한 수업·파티·공연이 하나의 캘린더에 모인다. 새 수업을 고를 때 이미 잡힌 일정과 겹치면 미리 알려 준다. 수업 전에는 본인이 고른 시점에 알림이 오고, 시간·장소가 바뀌면 즉시 알려 준다.

**Why this priority**: 소셜 댄스는 여러 학원·여러 강사의 수업을 동시에 다니는 사람이 많아, 일정 충돌이 가장 흔한 불만이다. 다만 US1(수업 발견·결제) 뒤에 얹히는 기능이다.

**Independent Test**: 서로 겹치는 수업 2건을 만들어 두고 두 번째 신청 시 경고가 뜨는지, 알림 시점(하루 전·2시간 전·1시간 전·30분 전) 설정대로 알림이 도착하는지로 검증된다.

**Acceptance Scenarios**:

1. **Given** 토요일 19:00 수업을 이미 예약한 회원이, **When** 토요일 19:30 수업을 신청하려 하면, **Then** 충돌 경고와 함께 겹치는 일정이 표시되고, 그래도 진행할지 명시적으로 묻는다.
2. **Given** 알림 시점을 "1시간 전"으로 설정한 회원이, **When** 수업 시작 1시간 전이 되면, **Then** 수업명·시각·장소가 담긴 알림을 받는다.
3. **Given** 예약한 수업의 장소가 변경되면, **When** 강사 또는 업주가 변경을 저장하는 즉시, **Then** 해당 수업의 모든 예약자에게 변경 전후 값이 담긴 알림이 간다.
4. **Given** 이동 시간이 30분 걸리는 두 장소의 연속 수업을 신청하려는 회원이, **When** 두 수업 사이 간격이 이동 시간보다 짧으면, **Then** 시각이 겹치지 않더라도 "이동 시간 부족" 경고가 표시된다. **[신규 제안]**

### User Story 5 - 대학생 인증으로 첫 결제 50% 할인을 받는다 (Priority: P2)

대학생이 재학을 인증하면 **최초 첫 결제 1회**가 자동으로 50% 할인된다. 그다음 결제부터는 정상가다 (2026-09-25 변경). 고객 유치 이벤트라 할인 차액과 그 결제의 환불 비용은 플랫폼이 아니라 학원이 부담한다.

**Why this priority**: 초기 사용자 확보의 핵심 유인이며 입점 학원에 제시하는 고객 유치 논리다. 그러나 결제(US1(수업 찾아 결제))가 돌지 않으면 적용할 대상이 없다.

**Independent Test**: 인증된 계정과 미인증 계정으로 같은 수업을 결제해 결제 금액 차이와 혜택 소진 카운트로 검증된다.

**Acceptance Scenarios**:

1. **Given** 대학생 인증을 마친 회원이, **When** 첫 번째 수업을 결제하면, **Then** 결제 금액이 자동으로 50% 할인되고 "대학생 첫 수강 50% 할인 적용" 안내 팝업이 뜨며 혜택이 1회 소진된 것으로 기록된다 (2026-09-25 변경).
2. **Given** 첫 결제 할인을 받은 회원이, **When** 다음 수업을 결제하면, **Then** 대학생 할인 없이 정상가로 결제된다 (2026-09-25 변경).
3. **Given** 허위 인증이 확인된 회원이, **When** 운영자가 인증을 취소하면, **Then** 남은 혜택이 회수되고 이미 사용한 혜택분은 정상가로 재청구 대상으로 기록된다.
3a. **Given** 이미 혜택을 받은 학교 이메일이, **When** 다른 계정에서 같은 주소로 인증을 시도하면, **Then** 인증이 거부된다.
3b. **Given** 학원 관리자가, **When** 정산 화면을 열면, **Then** 자기 학원에서 대학생 혜택으로 발생한 차액과 건수를 확인할 수 있다.
4. **Given** 탈퇴 후 같은 본인확인 정보로 재가입한 사람이, **When** 대학생 혜택을 다시 받으려 하면, **Then** 이미 소진한 것으로 판정되어 혜택이 부여되지 않는다.

### User Story 6 - AI 에이전트가 조건을 이해하고 근거와 함께 추천한다 (Priority: P3)

사용자가 "이번 주말 강남에서 초급 살사 듣고 끝나고 파티도 가고 싶어"처럼 문장으로 말하면, 시스템이 조건을 분해해 수업을 찾고, 이동 시간과 일정 충돌을 검사한 뒤, 실현 가능한 조합만 골라 이유와 함께 제시한다.

**Why this priority**: 차별점의 핵심이지만 US1~US3(수업 찾아 결제 ~ 포스터 등록·공간 충돌) 의 데이터가 쌓여야 추천할 대상이 생긴다. 데이터 없는 추천은 빈 결과만 낸다.

**Independent Test**: 수업·파티가 각각 몇 건 등록된 상태에서 자연어 요청 10건을 넣고, 결과에 존재하지 않는 수업이 섞이지 않는지와 시간·거리 제약을 지키는지로 검증된다.

**Acceptance Scenarios**:

1. **Given** 수업과 파티가 등록된 상태에서, **When** 회원이 자연어로 조건을 말하면, **Then** 시간 충돌·이동 거리·정원·운영 여부를 모두 통과한 조합만 제시된다.
2. **Given** 추천 결과를 받은 회원이, **When** 항목을 펼치면, **Then** 왜 추천됐는지(선호 장르 일치·거리·시간대·과거 수강 이력 중 무엇이 근거인지)가 문장으로 표시된다. **[신규 제안]**
3. **Given** 조건에 맞는 수업이 하나도 없을 때, **When** 추천을 요청하면, **Then** 없다고 명확히 답하고 어떤 조건을 완화하면 결과가 생기는지 제시한다. 존재하지 않는 수업을 지어내지 않는다.
4. **Given** 추천된 수업이, **When** 결과 표시 직전에 정원이 마감되면, **Then** 그 항목은 결과에서 제외되거나 "마감"으로 표시된다.

### User Story 7 - 강사가 수강 이력으로 레벨을 관리하고 개강 인원을 뽑는다 (Priority: P3)

강사가 자기 수업을 결제한 수강생에 한해 세부 장르별 레벨(0~10)을 부여한다. 출석률과 수강 이력이 쌓이면 개인·단체 레벨 분포를 그래프로 본다. 새 반을 열 때 "토요일 아침 고급 룸바 6명"처럼 조건을 주면 적합한 수강생 후보를 추천받는다.

**Why this priority**: 강사 유지율을 크게 올리는 기능이지만, 수강 이력 데이터가 최소 몇 달치 쌓여야 의미 있는 결과가 나온다.

**Independent Test**: 수강 이력이 있는 수강생 20명을 만들어 두고 조건을 넣어, 추천 명단이 레벨·요일·출석률 조건을 실제로 만족하는지로 검증된다.

**Acceptance Scenarios**:

1. **Given** 강사가, **When** 자기 수업을 결제하지 않은 회원의 레벨을 수정하려 하면, **Then** 권한이 없어 거부된다.
2. **Given** 레벨과 출석 이력이 있는 수강생들이, **When** 강사가 개강 조건(장르·레벨대·요일·정원)을 입력하면, **Then** 조건을 만족하는 후보 명단과 각자가 뽑힌 근거(레벨·수강 지속 기간·출석률)가 제시된다.
3. **Given** 추천 명단을 받은 강사가, **When** 연락처 조회를 요청하면, **Then** 수강생이 연락처 제공에 동의한 경우에만 표시되고 조회 사실이 기록으로 남는다. **[신규 제안 — 개인정보 보호 보완]**

### User Story 8 - 수업에서 파티·공연·대회로 이어진다 (Priority: P3)

사용자가 배운 장르의 파티·공연·대회를 한 피드에서 본다. 참가 신청과 예매 연결이 되고, 관심 등록한 항목은 일정이 확정될 때 알림이 온다.

**Why this priority**: 소셜 댄스를 "수업 소비"가 아니라 "활동"으로 만드는 축이지만, 수업 거래가 먼저 돌아야 한다.

**Independent Test**: 파티 1건·공연 1건을 등록해 피드 노출·참가 신청·알림까지 확인한다.

**Acceptance Scenarios**:

1. **Given** 살사/바차타를 수강 중인 회원이, **When** 피드를 열면, **Then** 전 학원의 살사/바차타 파티·공연·대회가 날짜순으로 표시된다.
2. **Given** 예약 가능한 파티가, **When** 회원이 참가 신청을 하면, **Then** 결제 흐름을 거쳐 내 캘린더에 등록된다.
3. **Given** 예매가 외부에서 이뤄지는 공연이, **When** 회원이 상세를 열면, **Then** 예매 링크로 연결되고 내부 결제를 요구하지 않는다.

### User Story 9 - 수강 완료분이 학원과 강사에게 정산된다 (Priority: P3)

강사는 고용된 사람이 아니라 프리랜서라 급여가 없고, 자기가 실제로 진행해 **수업 기간이 끝난 분**에 대해서만 정산을 받는다. 정산은 세 단계로 익는다 — 결제 후 수업 시작 전까지는 **보류**, 수업이 시작되면 **정산 완료 예정**, 기간이 끝나면 **정산 완료**가 되어 강사 전용 계좌로 나간다. 취소가 생기면 환불을 먼저 처리하고 그 결과를 정산에 반영한다. 조회는 전부 플랫폼 안에서 하며, 강사는 본인 것만, 업주는 자기 학원의 모든 수업과 소속 강사 전원의 정산을 본다.

**Why this priority**: 학원을 붙잡아 두는 기능이지만 거래량이 있어야 볼 것이 생긴다. 입점 첫 1년은 수수료를 면제하므로 정산 금액 자체의 긴급도도 낮다(2026-09-25 변경).

**Independent Test**: 결제·환불을 섞어 몇 건 만든 뒤 대시보드 숫자가 원장과 일치하는지로 검증된다.

**Acceptance Scenarios**:

1. **Given** 결제 10건과 환불 2건이 있는 학원이, **When** 정산 대시보드를 열면, **Then** 총 결제액·환불액·수수료·실지급액이 표시되고 합계가 개별 거래 내역의 합과 일치한다.
2. **Given** 쿠폰이 사용된 거래가, **When** 정산에 집계되면, **Then** 쿠폰 사용 건수가 수수료 계산과 분리되어 별도 표기된다.
3. **Given** 베타 기간 중인 학원이, **When** 정산 내역을 보면, **Then** 수수료가 0원으로 표시되고 면제 기간의 종료일이 함께 안내된다.
4. **Given** 결제는 됐지만 수업일이 아직 오지 않은 예약이, **When** 정산 화면을 보면, **Then** 그 금액은 보류분으로만 집계되고 정산 대상에 들어가지 않는다.
5. **Given** 수업이 시작된 예약이, **When** 정산 화면을 보면, **Then** 그 금액이 보류분에서 **정산 완료 예정**으로 옮겨가 금액은 보이되 아직 지급되지 않는다.
6. **Given** 수업 기간이 끝난 예약이, **When** 정산 주기가 돌면, **Then** 정산 완료로 확정되어 강사 전용 계좌로 지급되고 원천징수 항목이 구분 표기된다.
7. **Given** 정산이 이미 확정된 수강 건이, **When** 사후에 환불되면, **Then** 확정분을 되돌리지 않고 다음 정산 주기에 증감으로 반영되며 사유가 내역에 남는다.
8. **Given** 한 학원에 강사 3명이 있을 때, **When** 강사 한 명이 정산 화면을 열면, **Then** 본인 정산만 보이고 다른 강사의 정산은 보이지 않는다.
9. **Given** 같은 학원의 업주가, **When** 정산 화면을 열면, **Then** 학원의 모든 수업과 소속 강사 3명 전원의 정산이 보이고 관리할 수 있다.

### User Story 11 - 물어보면 답이 온다, 못 답하면 사람에게 간다 (Priority: P1)

사용자가 궁금한 것을 자기 말로 묻는다. "내 다음 수업 언제야?" 처럼 내 데이터를 묻는 것도 있고, "24시간 안에 취소하면 얼마 돌려받아요?" 처럼 정책을 묻는 것도 있고, "초급인데 뭐부터 들어야 해요?" 처럼 판단을 묻는 것도 있다. 시스템은 질문의 성격을 가려 답하고, **확신이 없으면 지어내지 않고 사람에게 넘긴다.**

**Why this priority**: 두 가지 이유로 P1 이다.

1. **출시 게이트다.** 스토어 심사와 전자상거래 관련 고지에 고객 문의 창구가 필요하다. 문의 경로가 없으면 앱을 올릴 수 없다.
2. **결제가 있는 앱이다.** 돈이 걸린 질문(환불액·입금 확인·정산)은 답이 틀리면 그대로 분쟁이 된다.

다만 **P1 인 것은 "문의가 접수되고 사람에게 닿는 경로"** 까지다. AI 자동 응답은 그 위에 얹는 층이며 단계적으로 켠다 — 이유는 아래 독립 검증 항목에 적었다.

**Independent Test**: 문의 1건을 넣어 접수 → 응답 → 종결까지 확인한다. AI 층을 전부 꺼도 사람 경로만으로 이 시나리오가 성립해야 한다 — **그게 이 슬라이스가 독립적이라는 뜻이다.** AI 층은 "같은 질문에 더 빨리 답하는" 개선일 뿐 경로를 대체하지 않는다.

**Acceptance Scenarios**:

1. **Given** 예약이 있는 회원이, **When** "내 다음 수업 언제예요?" 라고 물으면, **Then** 실제 예약 데이터에서 읽은 수업명·일시·장소가 표시되고, 그 값이 내 일정 화면의 값과 정확히 일치한다.
2. **Given** 회원이, **When** "지금 취소하면 얼마 돌려받아요?" 라고 물으면, **Then** 환불 계산을 담당하는 로직이 산출한 금액이 그대로 표시되고, 취소 미리보기 화면의 금액과 **원 단위까지 같다**.
3. **Given** 회원이, **When** 정책을 묻는 질문을 하면, **Then** 답변과 함께 근거가 된 약관·정책 항목이 표시된다.
4. **Given** 시스템이 답을 확신하지 못하면, **When** 응답을 생성할 시점이 되면, **Then** 추측해서 답하지 않고 "확인해서 알려드리겠다"며 사람에게 이관하고, 이관됐음을 사용자에게 알린다.
5. **Given** 결제 실패·환불 분쟁·개인정보 관련 문의가 들어오면, **When** 분류가 끝나면, **Then** AI 응답을 시도하지 않고 즉시 사람에게 배정된다.
6. **Given** 학원 수업의 결제·환불을 묻는 문의가 들어오면, **When** 배정이 이뤄지면, **Then** 플랫폼 운영자가 아니라 **그 학원의 업주**에게 배정된다. 개인 레슨의 환불도 강사가 아니라 그 레슨의 소속 학원 업주에게 간다 (2026-09-25 변경 — 환불 요청은 업주만).

### User Story 12 - 여럿이 동시에 물어도 순서와 진행이 보이고, 답은 믿을 수 있다 (Priority: P2)

시험 단계(S0)에서 이 서비스는 **노트북 한 대**에서 돈다. 시험자 한 명이 최대 10명의 사용자를 흉내 내 AI 에이전트에 동시에 질문을 던진다. 각 사용자는 자기 질문이 지금 어느 단계인지(조건 분석 → 후보 찾기 → 답 작성) 보고, 답이 늦어지면 기다릴지 사람에게 넘길지 고른다. 답은 한국어로만 나오고, 입력 데이터에 없는 사실(거리·가격·잔여석)을 지어내지 않는다.

**Why this priority**: US6(AI 추천)·US11(문의 응답)의 T2 경로가 실제로 쓸 만한지를 **데이터가 쌓이기 전에** 판정하는 유일한 방법이다. 실측(`local-ai-capacity.md`)에서 같은 장비·같은 모델로도 구성에 따라 동시 10명 완료 시간이 55초와 18초로 갈렸다 — 요구사항으로 못 박지 않으면 느린 쪽으로 만들어진다. 다만 거래 흐름(US1(수업 찾아 결제)·US2(강사 수업·자리 관리))보다 먼저일 수는 없어 P2 다.

**Independent Test**: 시험 데이터(학원·수업·파티 수십 건)를 넣고, 준비된 질문 세트를 동시 1명·5명·10명으로 보내 응답 시간·오류 수·언어·사실 일치를 잰다. 거래 기능이 없어도 이 슬라이스는 검증된다.

**Acceptance Scenarios**:

1. **Given** 10명이 같은 순간에 판단형(T2) 질문을 보내면, **When** 응답이 끝나면, **Then** 10건 모두 오류 없이 답을 받고, 첫 내용이 보이기까지와 답 완료까지의 시간이 SC-041(동시 10명 15초·25초) 기준 안에 든다.
2. **Given** 판단형 질문 10건이 처리 중일 때, **When** 11번째 사용자가 판단형 질문을 보내면, **Then** 거부되지 않고 1초 안에 대기 순번과 예상 대기 시간이 표시되며, 사람 문의로 넘기는 선택지가 함께 나온다.
3. **Given** 판단형 질문 10건이 처리 중일 때, **When** 다른 사용자가 "내 다음 수업 언제야?"(T0) 를 물으면, **Then** 모델 대기열과 무관하게 SC-042(T0·T1 1초) 기준 안에 답이 온다.
4. **Given** 답을 기다리는 사용자가, **When** 취소를 누르면, **Then** 그 질문의 처리가 멈추고 대기 중인 다음 사람의 차례가 당겨진다.
5. **Given** 같은 사용자가 답을 받기 전에 새 질문을 보내면, **When** 새 질문이 접수되면, **Then** 앞 질문은 자동 취소되어 한 사람이 자원을 둘 이상 붙잡지 않는다.
6. **Given** 후보 데이터에 거리 정보가 없을 때, **When** 답이 "도보 5분" 처럼 거리·이동 시간을 주장하면, **Then** 그 문장은 사용자에게 나가기 전에 제거되거나 답이 다시 만들어진다.
7. **Given** 모델이 한자·영어 등 한국어가 아닌 문장을 섞어 내면, **When** 답을 내보내기 직전에, **Then** 그 답은 내보내지 않고 다시 만들며, 두 번 실패하면 필터 검색 결과로 대체한다.
8. **Given** 강사가 "토요일 고급 룸바 6명 추천해줘" 로 수강생 후보를 받았을 때, **When** 명단 출력 확인에 "예" 를 고르면, **Then** 연락처 제공에 동의한 수강생의 이름·연락처만 표시되고 조회 기록이 남는다(FR-165(후보 연락처 동의)).
9. **Given** 추천 답의 끝에 "해당 수업 화면으로 이동할까요?" 가 나올 때, **When** 사용자가 "예" 를 고르면, **Then** 그 수업의 신청 화면으로 이동할 뿐 신청·결제는 일어나지 않는다(FR-214(AI 쓰기 금지)).
10. **Given** 업주가 포스터 여러 장을 올려 자동 추출이 돌고 있을 때, **When** 사용자 10명이 동시에 질문하면, **Then** 대화 응답 시간이 SC-041(동시 10명 15초·25초) 을 지키고 포스터 추출이 뒤로 밀린다.

### User Story 13 - 플랫폼 관리자가 결산을 보고 수수료를 정한다 (Priority: P3)

플랫폼 관리자가 업주 관리 웹과 같은 로그인 화면으로 들어가면, 업주 화면 대신 플랫폼 정산 콘솔이 열린다. 장르별·학원별·상품별·결제수단별로 결산을 보고, 학원마다 플랫폼이 가져다준 가치와 업주가 이미 부담하는 비용을 비교한다. 수수료율을 바꿔 넣어 모의 계산해 보고, 정하면 미래 날짜부터 적용한다. **[신규 2026-09-25]**

**Why this priority**: 수수료를 정하는 근거라 사업에 꼭 필요하지만, 거래가 몇 달 쌓여야 볼 숫자가 생긴다. 베타 첫 6개월은 수수료가 면제라 그동안 근거를 모으는 용도로 먼저 쓴다.

**Independent Test**: 학원 2곳·장르 2종·결제 10건·환불 2건·쿠폰 사용 3건을 넣고, 장르별·학원별·전체 결산의 합계가 원장 합계와 원 단위까지 같은지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 업주 역할과 관리자 역할을 가진 두 계정이, **When** 같은 로그인 화면으로 들어가면, **Then** 업주는 학원 관리 화면으로, 관리자는 플랫폼 정산 콘솔로 간다.
2. **Given** 관리자가, **When** 기간을 "지난달"로 고르면, **Then** 총 결제액·환불액·이용 수수료(실제·면제가 없었다면)·구독 수입·업주 부담 비용이 카드로 보이고 전월 대비 증감이 함께 보인다.
3. **Given** 관리자가, **When** 장르별 결산에서 "댄스스포츠"를 누르면, **Then** 세부 장르별 결제액·환불률·쿠폰 차액이 보이고 세부 장르 합계가 장르 합계와 같다.
4. **Given** 관리자가, **When** 수수료율을 5% 에서 7% 로 바꿔 지난 3개월로 모의 계산하면, **Then** 플랫폼 수입과 학원별 지급액 증감이 보이고 실제 정산은 바뀌지 않는다.
5. **Given** 관리자가, **When** 수수료율 변경을 오늘 날짜로 적용하려 하면, **Then** 거부되고 미래 날짜만 고를 수 있으며, 저장하면 해당 업주들에게 적용일 전에 알림이 간다.
6. **Given** 관리자가, **When** 학원 상세를 열면, **Then** 수강생 이름·연락처는 보이지 않고 학원·강사·수업 단위 숫자만 보인다.

### Edge Cases

**정원과 동시성**

- 마지막 한 자리에 두 명이 동시에 결제를 시작하면? → 먼저 입금이 확인된 쪽이 자리를 갖고 나머지는 자동 취소·전액 환불 대상이 된다.
- 가상계좌를 발급받은 사람이 입금하지 않고 기한이 지나면? → 잡아 둔 자리가 즉시 풀리고 대기 1순위에게 결제 기회가 간다.
- 대기자가 결제 기회를 받고도 응답하지 않으면? → 정해진 시간이 지나면 다음 순번으로 넘어가고, 넘어간 사실이 당사자에게 통지된다.
- 현장에서 현금으로 등록한 수강생이 있어 앱 정원과 실제 인원이 다르면? → 업주·강사가 오프라인 인원을 별도로 기입해 잔여 자리를 조정할 수 있어야 한다.

**시간과 공간**

- 같은 강의실·같은 시각에 두 수업이 배정되면? → 게시 단계에서 거부한다.
- 한 강사가 서로 다른 학원에서 같은 시각 수업을 등록하면? → 학원이 달라도 거부한다.
- 수업 시각이 변경돼 이미 예약한 사람의 다른 일정과 겹치게 되면? → 예약자에게 충돌을 알리고 취소·유지 선택지를 준다.
- 서머타임이 없는 국내 서비스지만 시각 저장은 시간대를 포함해 다룬다 — 표시만 한국 시각으로 변환한다.

**결제**

- 결제 확인 알림이 중복으로 도착하면? → 같은 거래로 판정해 한 번만 반영한다(멱등 처리).
- 결제 확인 알림이 순서가 뒤바뀌어 도착하면? → 최종 상태를 기준으로 판정하고 과거 상태로 되돌리지 않는다.
- 결제 금액과 요청 금액이 다르면? → 예약을 확정하지 않고 운영자 확인 대상으로 분리한다.
- 환불이 실패하면? → 실패 사유를 기록하고 재시도 가능한 상태로 남긴다. 성공·진행 중 환불은 예약당 1건만 존재한다.
- 결제 후 학원이 폐업하면? → 남은 수강분에 대한 처리 주체와 책임을 약관에 명시한다. 운영자가 조정하지 않는다 — 처리 주체는 Q11(환불 방식 변경의 뒤처리) 에 남아 있다 (2026-09-25 변경 — 운영자는 시스템만, 사람 문의는 업주).
- 이미 정산이 나간 수강 건이 나중에 환불되면? → 다음 정산 주기에서 차감한다. 차감 금액이 그 주기의 정산액을 넘으면 미수로 이월한다.
- 강사가 출석을 체크하지 않은 채 수업일이 지나면? → 수강 완료가 확정되지 않아 정산 보류분에 남는다. 정해진 기간이 지나면 업주 확인 대상으로 올린다 (2026-09-25 변경 — 운영자는 시스템만, 사람 문의는 업주).
- 수강생은 왔다고 하고 강사는 불참으로 체크했으면? → 분쟁으로 접수해 그 학원의 업주가 조정하며 (2026-09-25 변경 — 운영자는 시스템만, 사람 문의는 업주), 조정 전까지 그 건은 정산되지 않는다.
- 강사가 학원을 떠났는데 정산 보류분이 남아 있으면? → 보류분은 수업을 실제로 진행한 강사에게 귀속되며 학원 소속 변경과 무관하게 정산된다.

**자격과 혜택**

- 대학생 혜택을 받은 뒤 졸업하면? → 첫 결제 할인은 1회로 끝나므로 이미 쓴 혜택은 그대로 두고 다시 주지 않는다 (2026-09-25 변경).
- 쿠폰 소멸일 직전에 사용하고 그 수업을 취소하면? → 쿠폰이 소멸된 상태로 복구되지 않도록 사용 시점과 소멸 시점의 관계를 명시한다.
- 미성년자가 가입하려 하면? → 법정대리인 동의 절차 없이 결제가 진행되지 않도록 막는다.

**데이터와 AI**

- 포스터에서 가격을 잘못 읽으면? → 되돌리기 어려운 항목(가격·정원)은 신뢰도가 낮을 때 "확인필요"로 표시되고 검토를 건너뛸 수 없다.
- 추천 결과에 존재하지 않는 수업이 섞이면? → 게시 전 검증 단계에서 제거한다. 실제 데이터에 없는 항목은 사용자에게 노출되지 않는다.
- 추천 응답이 오래 걸리면? → 정해진 시간 안에 응답하지 못하면 단순 필터 검색 결과로 대체한다.

**규모와 장애**

- 인기 수업 오픈 시점에 신청이 몰리면? → 정원 초과 확정이 발생하지 않는다. 대기열로 흡수한다.
- 지하 스튜디오처럼 통신이 불안정한 곳에서 출석 확인이 필요하면? → 통신 없이도 확인 가능한 대체 수단을 둔다. **[신규 제안]**
- 알림 발송이 실패하면? → 실패를 기록하고 재시도하며, 앱을 열었을 때 미확인 알림을 볼 수 있다.

**문의와 응답**

- 모델이 멈췄거나 응답하지 않으면? → `T0`·`T1`·`T3` 경로로 계속 답한다. 문의 창구 자체는 살아 있어야 한다.
- 사용자가 자기 것이 아닌 예약의 환불액을 물으면? → 권한 밖이라 답하지 않는다. 남의 데이터가 답변에 섞이지 않는다.
- 답변 중에 정책이 바뀌면? → 그 정책에 연결된 지식 항목이 재검토 대상으로 표시되고, 검토 전까지 옛 답변을 내보내지 않는다.
- 사용자가 질문에 개인정보나 계좌번호를 적어 보내면? → 그대로 저장하지 않고 가린 뒤 보관하며, 필요한 경우에만 권한 있는 사람이 확인한다.
- 사용자가 AI 를 속여 남의 정보나 할인 코드를 얻어내려 하면? → 권한 검사는 모델이 아니라 시스템이 하므로 프롬프트를 바꿔도 범위가 넓어지지 않는다.
- 응대 시간 밖에 분쟁 문의가 들어오면? → 즉시 접수하고 언제 답변되는지 안내한다. 자동 응답으로 종결 처리하지 않는다.
- 학원이 문의에 응답하지 않으면? → 고지한 기한이 지나면 업주에게 다시 알리고, 문의자에게는 처리 대기 중임을 보여준다. 운영자에게 넘기지 않는다 (2026-09-25 변경 — 운영자는 시스템만, 사람 문의는 업주).
- 학원이 자기 환불 정책을 바꾸면? → 이미 결제한 건에는 결제 시점의 정책을 적용하고, 답변도 그 시점 기준으로 한다.
- 한 회원이 여러 학원에 다니면서 환불을 물으면? → 어느 예약에 대한 질문인지 먼저 특정하고, 그 학원의 정책으로 답한다.
- 학원이 폐업했거나 업주 계정이 비활성이면? → 문의 화면에서 그 학원을 고를 수 없음을 표시한다. 운영자가 대신 받지 않는다 — 이 경우의 처리는 Q11(환불 방식 변경의 뒤처리) 에 남아 있다 (2026-09-25 변경 — 운영자는 시스템만, 사람 문의는 업주).
- 같은 사용자가 짧은 시간에 질문을 쏟아내면? → 사용량 한도를 적용하되 `T3(사람)` 경로는 막지 않는다.

**AI 동시 사용 — 노트북 한 대 (S0)**

- 판단형 질문이 동시에 10건을 넘으면? → 거부하지 않고 대기열에 넣어 순번을 보여준다. 대기열 길이에도 상한을 두고, 넘으면 "지금은 사람 문의로 받겠다" 로 전환한다.
- 모델 서버가 재시작되거나 응답하지 않으면? → 진행 중인 질문은 오류가 아니라 "다시 시도 중" 으로 표시하고, 일정 시간 안에 복구되지 않으면 저하 모드(FR-223(저하 모드))로 넘어간다. 복구되면 자동으로 돌아온다.
- 한 질문이 긴 대화 기록을 끌고 오면? → 맥락 길이 상한을 넘는 오래된 대화는 요약하거나 잘라낸다. 상한 때문에 다른 사용자의 자리를 빼앗지 않는다.
- 사용자가 올린 후기·포스터 글에 "이전 지시를 무시하라" 같은 문장이 있으면? → 명령이 아니라 데이터로 다룬다.
- 포스터 자동 추출과 대화가 겹치면? → 대화가 먼저다. 추출은 늦어져도 되지만 대화 응답 시간 기준은 깨지면 안 된다.
- 노트북이 배터리 전원이거나 과열로 느려지면? → 시험 결과에 전원 상태를 함께 기록한다. 배터리 상태 측정값으로 기준 통과를 판정하지 않는다.

## Requirements *(mandatory)*

표기 규칙: **[신규]** 는 이 재구성에서 새로 제안하는 요구사항이다. 표기가 없으면 기존 문서(정의서·정책 문서·화면 명세)에 근거가 있다.

### Functional Requirements

#### 계정 · 인증 · 권한 (FR-001~FR-019)

- **FR-001**: 시스템은 카카오·구글·네이버 소셜 로그인으로 가입과 로그인을 제공해야 한다.
- **FR-002**: 시스템은 가입 시 나이·성별·연락처를 필수로 수집해야 하며, 각 항목의 수집 목적을 가입 화면에서 고지해야 한다.
- **FR-003**: 시스템은 휴대폰 본인확인을 거친 사람 단위로 계정을 식별해야 한다. 혜택·쿠폰의 중복 수령 판정은 기기가 아니라 이 사람 단위로 한다.
- **FR-004**: 시스템은 Dancer(수강생)·Instructor(강사)·Owner(업주)·Admin(운영자) 네 역할을 구분하고, 한 사람이 여러 역할을 동시에 가질 수 있어야 한다.
- **FR-005**: 시스템은 역할별로 접근 가능한 데이터 범위를 제한해야 한다. 강사는 자기 수업의 결제 완료 수강생만(무료 수업은 신청이 확정된 수강생을 결제 완료와 같게 본다 — 2026-09-25 보완), 업주는 자기 학원 소속 데이터만 조회할 수 있다.
- **FR-006**: 시스템은 대학생 자격을 **학교 이메일 도메인(.ac.kr) 인증**으로 확인해야 한다(2026-09-21 확정). 인증은 선택이며 가입 이후에도 마이 화면에서 할 수 있다.
- **FR-006a**: 시스템은 인증 메일의 확인 링크에 유효 기간을 두고, 기간이 지나면 재발송하게 해야 한다.
- **FR-006b**: 시스템은 하나의 학교 이메일로 여러 계정이 혜택을 받지 못하도록 막아야 한다. **[신규]**
- **FR-006c**: 시스템은 이메일 인증이 **재학 여부까지 보장하지 않는다**는 한계를 전제로, 사후 확인과 혜택 회수 절차(FR-007(허위 인증 혜택 회수))를 반드시 갖춰야 한다. 졸업생 계정이 살아 있으면 인증이 통과하기 때문이다.
- **FR-006d**: 시스템은 대학생 혜택 사용 현황을 학원이 조회할 수 있게 해야 한다. 차액을 부담하는 쪽이 학원이므로 이상 징후를 발견할 수 있어야 한다. **[신규]**
- **FR-007**: 시스템은 대학생 인증이 허위로 판명되면 잔여 혜택을 회수하고 사용분을 정상가 재청구 대상으로 기록해야 한다.
- **FR-008**: 시스템은 인증에 사용한 학교 이메일 원문을 인증 완료 후 보관하지 않아야 한다.
- **FR-009**: 시스템은 미성년자 가입 시 법정대리인 동의 없이 결제가 진행되지 않도록 막아야 한다. **[신규]**
- **FR-010**: 시스템은 탈퇴 후 재가입한 사람이 1회성 혜택을 다시 받지 못하도록 판정해야 한다. **[신규]**
- **FR-011**: 시스템은 강사·업주 계정을 운영자 또는 학원 관리자의 승인을 거쳐 활성화해야 한다.

#### 프로필 · 취향 (FR-020~FR-029)

- **FR-020**: 시스템은 장르를 댄스스포츠·아르헨티나 탱고·스윙댄스·살사/바차타 4종으로 고정해 관리해야 한다.
- **FR-021**: 시스템은 세부 장르를 관리해야 한다 — 라틴(차차차·삼바·룸바·파소도블레·자이브), 스탠다드(슬로우왈츠·탱고·비엔나왈츠·슬로우폭스트롯·퀵스텝), 스윙, 살사, 바차타.
- **FR-022**: 시스템은 사용자의 경험 수준·선호 장르·활동 지역·활동 가능 시간·이동 가능 거리를 프로필로 저장해야 한다.
- **FR-023**: 시스템은 사용자가 관심 강사·관심 학원을 등록하고 그들의 신규 수업·이벤트 알림을 받도록 해야 한다.
- **FR-024**: 시스템은 사용자의 찜·좋아요·싫어요를 기록하고 추천 결과에 반영해야 한다.
- **FR-025**: 시스템은 강사 프로필에 장르·세부장르·경력·자격·활동 지역·소개 영상을 담아야 한다.
- **FR-026**: 시스템은 사용자가 자신의 리드(lead)·팔로우(follow) 역할 선호를 등록하도록 해야 한다. **[신규 — 소셜 댄스는 성별이 아니라 역할로 짝을 이룬다]**
- **FR-027**: 시스템은 취향 설정에 선호 음악 스타일과 선호 강사 수업 스타일을 담아야 한다. **[정의서 근거 — 2026-09-25 이관]**
- **FR-028**: 시스템은 수업에 권장 연령대를 표기할 수 있게 하고 사용자가 연령대로 수업을 거를 수 있게 해야 한다. 연령대는 수강 자격을 막는 조건이 아니라 안내값이다. **[정의서 근거 — 2026-09-25 이관]**
- **FR-029**: 시스템은 프로필의 경험 수준을 정해진 구간으로 받아야 한다 — 입문 0~6개월, 초급 6개월~2년, 중급 2~4년, 고급 5년 이상(2026-09-25 확정: 비어 있던 1~2년을 초급에 넣었다). 4~5년 사이 경계와 점수 레벨(FR-161(레벨 등급 구간))과의 관계는 Q7(경험 수준 구간)에 남아 있다. **[정의서 근거 — 2026-09-25 이관]**

#### 검색 · 추천 (FR-030~FR-049)

- **FR-030**: 시스템은 날짜·지역·장르·세부장르·난이도·강사로 수업을 검색할 수 있어야 한다.
- **FR-031**: 시스템은 강사 프로필·전문 장르·수업 일정으로 강사를 검색할 수 있어야 한다.
- **FR-032**: 시스템은 한 강사가 여러 학원에서 하는 수업을 한 화면에서 일관되게 조회할 수 있어야 한다.
- **FR-033**: 시스템은 사용자가 지정한 시간대에 신청 가능한 수업만 걸러 보여줄 수 있어야 한다.
- **FR-034**: 시스템은 현재 위치에서 이동 가능한 범위의 수업을 탐색할 수 있어야 한다.
- **FR-035**: 시스템은 사용자의 기존 일정과 겹치는 수업을 검색 결과에서 표시해야 한다.
- **FR-036**: 시스템은 입문자에게 입문 수업을 우선 제시해야 한다.
- **FR-037**: 시스템은 자연어 요청을 조건(시간·지역·장르·레벨·예산)으로 분해해 처리해야 한다.
- **FR-038**: 시스템은 추천 후보에 대해 시간 충돌·이동 거리·정원·운영 여부·중복·존재 여부를 검증한 뒤에만 사용자에게 제시해야 한다.
- **FR-039**: 시스템은 추천 결과에 실제 데이터에 존재하지 않는 항목을 포함하지 않아야 한다.
- **FR-040**: 시스템은 각 추천 항목에 대해 추천 근거를 사용자가 읽을 수 있는 문장으로 제시해야 한다. **[신규]**
- **FR-041**: 시스템은 추천이 정해진 시간 안에 완료되지 않으면 필터 기반 검색 결과로 대체해 응답해야 한다. **[신규]**
- **FR-042**: 시스템은 수업 → 파티 → 공연으로 이어지는 연속 활동을 이동 시간을 고려해 제안할 수 있어야 한다.
- **FR-043**: 시스템은 사용자의 선택 이력을 학습해 장르별·학원별·시간대별·강사별·지역별 추천을 정교화해야 한다.

#### 수업 · 일정 (강사) (FR-050~FR-069)

- **FR-050**: 시스템은 강사가 수업을 등록할 수 있어야 한다 — 장르·세부장르·레벨·수업구분·수업명·일시·장소·정원·수강료·신청 방법.
- **FR-051**: 시스템은 수업 구분을 관리해야 한다 — 입문·초급·중급·고급입문·베이직·베이직심화·레이디스타일·공연.
- **FR-052**: 시스템은 수업 운영 형태를 구분해야 한다 — 정규·단기·원데이·개인레슨·그룹레슨·이벤트.
- **FR-052a**: 시스템은 운영 형태에 따라 신청 단위를 달리해야 한다. 원데이·이벤트는 회차 하나를, 정규·단기 과정은 기간 전체를 한 번에 신청·결제하고 그 기간의 회차 전부에 자리가 잡혀야 한다. **[신규 2026-09-25]**
- **FR-053**: 시스템은 강사가 자신의 가능 시간과 개인 일정을 등록하도록 해야 한다.
- **FR-054**: 시스템은 강사의 일정 충돌을 감지하고 충돌하는 수업 등록을 거부해야 한다. 소속 학원이 다른 경우에도 동일하게 적용한다.
- **FR-055**: 시스템은 휴강·보강을 처리하고 영향을 받는 예약자 전원에게 통지해야 한다.
- **FR-056**: 시스템은 수업 시간·장소 변경 시 예약자 전원에게 변경 전후 값을 통지해야 한다.
- **FR-057**: 시스템은 반복 수업 일정을 한 번의 설정으로 생성할 수 있어야 한다.
- **FR-058**: 시스템은 강사에게 오늘·이번 주·한 달·1년 단위의 일정 대시보드를 제공해야 한다.
- **FR-059**: 시스템은 휴강으로 손실이 발생한 수강생에게 환불 또는 보강 크레딧 중 선택지를 제시해야 한다. **[신규]**
- **FR-060**: 시스템은 강사가 특정 수업의 대타(대체 강사)를 요청하고, 조건에 맞는 강사에게 공지할 수 있어야 한다. **[신규 — 정의서의 "강사 급구" 확장]**
- **FR-061**: 시스템은 강사가 올린 사진·영상과 수업 정보로 수업 제목·소개 문구·홍보 이미지 초안을 만들어 주고 강사가 검토·수정한 뒤에만 게시되게 해야 한다. 생성 도구는 요구사항에서 정하지 않는다. **[정의서 근거 — 2026-09-25 이관]**
- **FR-061a**: 시스템은 수업 등록 때 만드는 **홍보 이미지**를 다음 조건으로 생성해야 한다. **[신규 2026-09-25, 사용자 결정]**

  | 학원 · 교습소 | 학원법 교습비 반환 기준 — 수강 시작 전 전액, 총 기간의 1/3 경과 전 2/3, 1/2 경과 전 1/2, 1/2 경과 후 반환 없음(미검증) |
  | 신고 체육시설 | 공정위 소비자분쟁해결기준(체육시설업) |
  | 미등록 | 공정위 소비자분쟁해결기준 |

  1개월 이상 계속되고 10만원 이상인 정규 과정은 등록 형태와 상관없이 방문판매법의 **계속거래** 규정(언제든 해지 가능, 과다 위약금 금지)이 함께 걸릴 수 있다(미검증). 파티·원데이·공연·대회의 취소 규정(FR-099c(파티·원데이·공연·대회 취소 규정))은 등록 형태와 상관없이 같다.
- **FR-087**: 시스템은 증빙을 올리지 않았거나 확인이 끝나지 않은 학원에는 **가장 엄격한 기준(학원법 교습비 반환 기준)**을 정규 과정 템플릿으로 적용해야 한다. 증빙 확인은 계정 승인(FR-011(강사·업주 계정 승인))과 같은 절차로 운영자가 한다. 등록 형태가 바뀌면 **이후 결제부터** 새 템플릿을 적용하고, 이미 결제된 건은 결제 시점의 공지를 따른다(FR-284(주문 시점 값 고정)). **[신규 2026-09-25]**
- **FR-088**: 시스템은 학원 상세 화면에 등록 형태(학원·교습소·신고 체육시설·미등록)를 표시해야 한다. 수강생이 어떤 환불 기준이 적용되는지 결제 전에 알 수 있게 하기 위해서다. **[신규 2026-09-25]**

#### 예약 · 정원 · 대기자 (FR-090~FR-109)

- **FR-090**: 시스템은 수업별 정원과 현재 신청 인원을 표시해야 한다.
- **FR-091**: 시스템은 정원을 초과하는 예약 확정이 발생하지 않도록 보장해야 한다.
- **FR-091a**: 시스템은 수업의 **전체 정원이나 역할별 정원이 찬 경우** 그 수업(또는 그 역할)의 결제 버튼과 쿠폰 선택지를 모두 비활성화해야 한다. 정원이 찬 수업은 결제로 참여할 수 없고 대기 신청(FR-093(대기 신청·순번))만 할 수 있다. 결제가 진행되는 사이에 정원이 차면 그 결제를 확정하지 않고 쿠폰도 쓰지 않은 상태로 되돌린다. **[신규 2026-09-25]**
- **FR-092**: 시스템은 정원을 **리드(lead)·팔로우(follow) 역할** 기준으로 나누어 관리하고 각각의 잔여 자리를 표시해야 한다(2026-09-21 확정). 성별은 정원 판정에 쓰지 않는다.
- **FR-092a**: 시스템은 수강생이 예약 시 참여할 역할을 고르게 해야 하며, 프로필의 역할 선호(FR-026(역할 선호))를 기본값으로 제시해야 한다.
- **FR-092b**: 시스템은 한 사람이 수업마다 다른 역할로 참여할 수 있게 해야 한다. 역할은 계정에 고정되지 않는다.
- **FR-092c**: 시스템은 역할을 구분하지 않는 수업(솔로 스타일·레이디스타일 등)에 대해 단일 정원으로 운영할 수 있게 해야 한다. **[신규]**
- **FR-092d**: 시스템은 학원이 화면 표기를 리드/팔로우 대신 자기 학원에서 쓰는 말로 바꿀 수 있게 해야 한다. 저장되는 값은 역할 그대로다. **[신규]**
- **FR-093**: 시스템은 정원이 찬 수업에 대해 수업 시작 24시간 전까지 대기 신청을 받아야 하며, 대기자에게 본인의 순번을 표시해야 한다. 대기 신청과 대기자 알림은 **구독자와 신규 가입 3개월 체험자만** 쓸 수 있다(FR-112c(구독 전용 혜택)·FR-112d(신규 가입 3개월 체험)) (2026-09-25 변경).
- **FR-094**: 시스템은 결제 취소가 **1건 생길 때마다 대기 1번 한 명에게만** 결제 기회를 알려야 한다. 여러 대기자에게 동시에 알리지 않는다 (2026-09-25 변경) — 이전: 대기 순번대로 결제 기회 통지.
- **FR-094a**: 시스템은 대기 순번을 다음처럼 한 명씩 넘겨야 한다. **[신규 2026-09-25]**
  - 대기 1번이 결제하면 2번이 1번으로 올라가고, 그 사람에게 "대기 1번이 되었습니다" 알림을 보낸다.
  - 다음 결제 취소가 생기면 새 1번에게만 결제 기회 알림이 간다.
  - 결제 기회를 받은 1번이 정해진 시간 안에 결제하지 않으면(FR-095(대기 무응답 승계)) 다음 순번이 1번이 되고, 비어 있는 자리에 대한 결제 기회 알림을 받는다.
  - 결제 기회 알림을 받는 사람은 **언제나 한 명**이다.
- **FR-095**: 시스템은 대기자가 결제 기회를 받고 정해진 시간 안에 응답하지 않으면 다음 순번으로 넘기고 당사자에게 통지해야 한다. **[신규]**
- **FR-096**: 시스템은 결제 대기 상태(입금 전) 동안 해당 자리를 잠그고, 기한이 지나면 잠금을 해제해야 한다.
- **FR-097**: 시스템은 같은 자리에 복수의 결제 대기가 생긴 경우 먼저 입금이 확인된 건만 확정하고 나머지를 자동 취소해야 한다.
- **FR-098**: 시스템은 모든 환불을 수강생이 문의로 요청하고 그 학원이 자기 환불 규정대로 처리하는 방식으로 다뤄야 한다(FR-098b(환불 요청 경로)). (2026-09-25 변경) 기존의 플랫폼 공통 규칙(수업 24시간 전 취소는 전액, 그 안은 학원 비율표 자동 적용)은 폐지한다. 환불 규정이 학원마다 달라 하나의 공통 규칙으로 묶을 수 없기 때문이다.
- **FR-098a**: ~~결제 당일 수업 시작 전 수강생 셀프 전액 환불~~ — **삭제(2026-09-25).** 결제가 계좌이체 방식이라 수강생이 버튼 하나로 즉시 돌려받는 경로를 두기 어렵다는 사용자 판단에 따라 넣은 날 바로 뺐다. 번호는 재사용하지 않는다.
- **FR-098b**: 시스템은 수강생의 환불 요청을 앱 문의로 받아야 한다. 수강생은 문의 화면에서 자기 예약 중 해당 수업을 검색·선택해 요청하고, 요청은 그 예약에 연결된다. 요청이 들어오면 **그 수업의 담당 강사에게 알림이 가서 강사가 내용을 확인**할 수 있고, 환불 여부와 금액의 결정·처리는 **그 학원의 업주에게만** 배정된다. 문의 화면에는 업주 연락처를 함께 표시한다(2026-09-25 보완). 개인 레슨도 강사가 그 레슨에 지정한 소속 학원의 업주에게 간다. 강사는 요청을 확인만 하고 환불을 결정하거나 처리하지 않는다. 운영자·AI 는 환불 요청을 받거나 처리하지 않는다. 업주는 등록한 환불 규정(FR-099(환불 규정 등록·표시))에 따라 환불 여부와 금액을 정하고 **환불도 업주가 직접 실행한다** — 업주가 수강 결제를 관리하기 때문이다. 시스템은 결정된 금액·근거 규정·처리자·실행 결과를 기록하고 수강생에게 결과를 통지한다 (2026-09-25 변경 — 수업 환불은 업주가 실행, 구독권 환불만 플랫폼). 업주가 고지한 기한 안에 답하지 않으면 업주에게 다시 알리고 수강생에게는 처리 대기 중임을 보여준다. 운영자에게 넘기지 않는다. **[신규 2026-09-25]** (2026-09-25 변경 — 환불 요청은 업주만)
- **FR-099**: 시스템은 학원이 자기 환불 규정을 등록하게 해야 하며 그 규정을 **모든 수업 공지(수업 상세 화면)**와 결제 화면에 반드시 표시해야 한다. 환불 규정을 등록하지 않은 학원은 수업을 게시할 수 없다. (2026-09-25 변경)
- **FR-099a**: 시스템은 업주가 환불·취소 공지를 **정해진 양식**으로 작성하게 해야 한다. 양식 항목은 취소 가능 시점, 시점별 환불 기준(비율 또는 금액), 환불이 안 되는 경우, 환불 처리 기간, 환불 요청 방법(앱 문의 — FR-098b(환불 요청 경로)), 업주 연락처다. 모든 학원의 공지가 같은 항목 순서로 보이게 하기 위해서다. **[신규 2026-09-25]**
- **FR-099b**: 시스템은 강사가 앱이나 웹에서 수업을 등록할 때 그 수업이 속한 학원의 업주가 작성한 환불·취소 공지(FR-099a(환불·취소 공지 양식))를 **수업 등록 페이지에 자동으로 채워 넣어야** 한다. 강사는 이 공지를 따로 쓰지 않고, 고치거나 지울 수도 없다. 개인 레슨은 그 레슨에 지정한 소속 학원의 공지가 들어간다. 업주가 공지를 바꾸면 이후 등록·게시되는 수업에 반영되고, 이미 결제된 건에는 결제 시점의 공지가 적용된다(FR-245(결제 시점 정책 적용)). **[신규 2026-09-25]**
- **FR-099c**: 시스템은 **파티·원데이 클래스·공연·대회** 상품에 공연 예매처(인터파크)와 같은 구조의 **취소 수수료 규정**을 적용할 수 있게 해야 한다. 정규 과정에는 적용하지 않는다. 결제 수단과 상관없이 적용한다 — 취소 수수료는 위약금이라, 카드·PG 결제 처리 수수료를 수강생에게 넘기는 것과 다르다(결제 처리 수수료는 계속 업주 부담, FR-125a(카드 수수료 공제 표시)·FR-125d(PG 결제 수수료 업주 부담)). **[신규 2026-09-25, 같은 날 사용자 결정으로 인터파크 원문 기준으로 확정]**
  - **우선순위**: ⓐ 취소 수수료 규정이 ⓑ 결제 취소 조건보다 먼저 적용된다.
  - **결제 당일 자정 전** 취소는 취소 수수료가 없다(취소 기한 안에 한함).
  - **ⓐ 취소 수수료 규정** — 행사·수업일 기준

    | 취소 시점 | 취소 수수료 |
    |---|---|
    | 10일 전까지 | 결제액의 10% 이내(업주가 정함) |
    | 9일 전 ~ 7일 전 | 결제액의 10% |
    | 6일 전 ~ 3일 전 | 결제액의 20% |
    | 2일 전 ~ 취소 기한까지 | 결제액의 30% |
    | 취소 기한이 지난 뒤 | 취소·환불 불가 |

  - **ⓑ 결제 취소 조건**: 결제 후 7일 이내 취소는 전액 환불한다. **ⓐ가 우선하는 것은 행사·수업 9일 전부터의 구간이다** — 결제 후 7일 이내라도 9일 전 이후에 취소하면 그 구간의 수수료를 뗀다. 행사까지 **10일 이상 남았으면 결제 후 7일 이내 취소는 전액**, 7일이 지났으면 "10일 전까지" 수수료를 적용한다(인터파크 운영 방식, 2026-09-25 문구 명확화).
  - **환불 마감일**(원데이·이벤트·파티·공연·대회): 예산을 미리 확보해야 행사 운영을 예측할 수 있으므로, 취소·환불 마감은 개최 당일이 아니라 **업주·강사가 등록 때 정한 개최일 이전 날짜**다. 입력·적용 방식은 FR-099d(환불 마감일 필수 입력·결제 적용). 예: 10월 30일 개최 → 환불 마감 10월 15일 → 10월 16일부터 취소·환불 불가. 마감일까지는 위 ⓐ·ⓑ를 적용하고, **마감일이 지나면 ⓑ(결제 후 7일 이내 전액)도 적용하지 않는다.** **[2026-09-25 사용자 결정, 같은 날 원데이·이벤트까지 확대]**
    - ⚠ 마감일 뒤에 결제하는 회원은 결제 순간부터 환불이 안 된다. 결제 전 "환불 불가 상품" 확인 동의를 받는다. 개최 한참 전 마감 + 이후 전면 불가는 공정위 소비자분쟁해결기준(공연업: 당일까지 수수료 공제 후 환불)과 법정 청약철회 7일보다 회원에게 불리해 약관규제법상 다퉈질 수 있다 — 법률 검토 대상.
  - **취소 기한**은 업주가 상품마다 정하고 예약 상세 내역에 표시한다. 취소 기한이 지난 날짜의 상품을 결제하면 결제와 동시에 취소·환불이 불가하다는 점을 결제 전에 알린다.
  - 업주는 비율을 낮출 수만 있고 높일 수는 없다. 예매 수수료 2,000원은 이 비율과 별도로 붙고 취소해도 환불하지 않는다(FR-282a(예매 수수료 2,000원)). 학원·강사 사정의 휴강·폐강에는 적용하지 않는다(FR-059(휴강 환불·보강 선택)).
  - ⚠ **법적 위험(출시 전 법률 검토 필수)**: 두 항목이 공정거래위원회 소비자분쟁해결기준(공연업)보다 수강생에게 불리하다 — ① 10일 전까지 수수료(기준: 전액 환급) ② 취소 기한 뒤 취소 불가(기준: 당일 시작 전까지 90% 공제 후 환급). 이 기준은 권고 기준이라 곧바로 불법은 아니지만, 분쟁 조정에서는 기준대로 환급하라는 판단이 나올 수 있고, 한국소비자원은 ②와 같은 규정을 불합리하다고 지적한 적이 있다(Q11(환불 방식 변경의 뒤처리) ①).
- **FR-099d**: 시스템은 **원데이·이벤트·파티·공연·대회** 상품을 등록할 때 업주·강사가 **환불 마감일(환불 가능한 마지막 날짜)을 반드시 입력**하게 해야 한다. **결제 시스템의 핵심 기능이다.** **[신규 2026-09-25, 사용자 결정]**
  - **필수 입력**: 환불 마감일이 비어 있으면 상품을 등록·공개할 수 없고 결제도 열리지 않는다. 마감일은 개최일(회차가 여럿이면 첫 회차) 당일 또는 그 이전이어야 한다.
  - **결제 시스템 적용**: 입력한 마감일은 결제 화면·상품 안내·예약 상세에 표시되고, 결제 시스템이 그대로 집행한다 — 마감일까지는 FR-099c(파티·원데이·공연·대회 취소 규정)의 ⓐ·ⓑ로 환불하고, **마감일 다음 날부터는 취소·환불 버튼이 막힌다**(ⓑ 결제 후 7일 이내 전액도 적용하지 않음).
  - **마감 뒤 결제**: 마감일이 지난 상품을 결제하면 결제 전에 "환불 불가 상품" 확인 동의를 받는다.
  - **변경**: 결제한 회원이 있으면 마감일을 회원에게 불리하게(앞당겨) 바꿀 수 없다. 늦추는 것은 가능하다.
  - **제외**: 정규·일반(단기·개인 레슨 등) 수업은 대상이 아니다. 이들의 환불은 업주 문의로 처리한다(FR-098b(환불 요청 경로)).
  - ⚠ 마감 뒤 전면 불가는 공정위 공연업 기준·법정 청약철회보다 회원에게 불리해 법률 검토 대상이다.
- **FR-100**: 시스템은 환불 금액 계산에 부동소수를 사용하지 않고 정수 연산만 사용해야 한다. 반올림은 회원에게 유리한 방향(올림)으로 한다.
- **FR-101**: 시스템은 취소·환불의 모든 상태 전이를 수정·삭제 불가능한 감사 기록으로 남겨야 한다.
- **FR-102**: 시스템은 같은 취소 요청이 여러 번 도착해도 환불이 한 번만 실행되도록 보장해야 한다.
- **FR-103**: 시스템은 환불 실패 시 실패 사유를 기록하고 재시도 가능한 상태로 유지해야 한다.
- **FR-103a**: ~~계좌이체 딥링크 경로로 결제한 건의 환불 수단·처리 주체·예상 소요 시간을 결제 전에 고지~~ — **삭제(2026-09-25).** 딥링크 결제를 없애고 PG 로 통일해 해당 결제건이 생기지 않는다. 번호는 재사용하지 않는다.
- **FR-104**: 시스템은 출석·불참을 기록해야 하며, 불참 체크로 실제 참여 인원을 파악할 수 있어야 한다. 이 기록은 노쇼·분쟁 판정의 근거(FR-135b(출석은 분쟁 근거))이므로 수업 종료 후 수정하려면 사유가 남아야 한다.
- **FR-104a**: 시스템은 수강생이 수업 전에 스스로 불참 예정을 표시할 수 있게 하고, 그 결과를 역할별 예상 참석 인원에 반영해 강사·업주에게 보여줘야 한다. 불참 표시만으로 자리를 반납하지는 않으며 반납하려면 취소(FR-098(업주 처리 환불 방식))를 거친다. **[정의서 근거 — 2026-09-25 이관]**
- **FR-105**: 시스템은 파트너와 함께 2인 동반 신청을 받을 수 있어야 하며, 동반 신청은 두 자리를 함께 확정하거나 함께 실패해야 한다. **[신규]**
- **FR-106**: 시스템은 오프라인(현장 등록) 인원을 업주·강사가 기입해 잔여 자리에 반영하도록 해야 한다. **[신규]**
- **FR-107**: 시스템은 수업 전날 기준 역할별 인원이 크게 불균형하면 강사·업주에게 경보하고, 부족한 역할에 한정한 모집 수단을 제안해야 한다. **[신규]**
- **FR-108**: 시스템은 수업 시작 24시간 이내에는 새 대기 신청을 받지 않아야 한다. 이미 대기 중인 사람에게 가는 결제 기회는 수업 시작 전 정해진 시각까지만 발생하고 그 뒤에는 대기가 종료됐음을 통지해야 한다. **[신규 2026-09-25]**
- **FR-109**: 시스템은 학원이 허용한 경우 수강생이 같은 수업의 다른 회차로 예약을 옮길 수 있게 해야 한다. 옮기기는 취소·재결제가 아니라 자리 이동이며 옮길 회차에 해당 역할 자리가 있어야 한다. **[신규 2026-09-25]**

#### 결제 · 요금 · 정산 (FR-110~FR-139)

- **FR-110**: 시스템은 **모든 유료 결제를 결제대행(PG) 한 경로로** 처리해야 한다 (2026-09-25 변경 — 딥링크 폐지, PG 로 통일). 금액에 따라 경로를 나누지 않는다. 이전의 "9만원 이하 계좌이체 딥링크 / 그 위 PG" 분리는 없앴다 — 경로가 하나여야 결제 확정·환불·수수료 공제·정산이 모두 자동으로 맞기 때문이다.
- **FR-111**: 시스템은 단건 예약의 기본 결제수단으로 가상계좌(무통장입금)를 제공해야 한다.
- **FR-111a**: 시스템은 **모든 유료 결제**(파티·원데이·공연·대회·이벤트·단기·개인 레슨·정규 과정·구독)에서 **신용카드와 체크카드**를 고를 수 있게 해야 한다 (2026-09-25 변경 — 모든 유료 결제에 카드 허용) — 이전: 정규 과정과 구독에만 카드. 카드 결제는 PG 로 처리하며 수업·과정 금액을 한 번에(일시불) 결제한다. 구독은 카드 자동결제다(FR-112(월 구독 카드)). 수업 결제의 카드 수수료는 **업주(판매자)가 부담**하며 학원 정산에서 실비로 공제하고(FR-125a(카드 수수료 공제 표시)), 구독의 카드 수수료는 플랫폼이 부담한다. 수강생에게는 카드 수수료를 더 받지 않는다(여신전문금융업법). **[신규 2026-09-25]**
- **FR-112**: 시스템은 월 구독(정기결제)을 카드로만 제공해야 한다.
- **FR-112b**: 시스템은 월·연 구독을 **플랫폼이 파는 상품**으로 다뤄야 한다. 구독료는 플랫폼 수입이며 학원 정산(FR-125(학원 월 정산)) 대상이 아니다. 구독 할인·환불도 플랫폼이 처리한다. 다만 1+1 쿠폰의 추가 수업 50% 할인분은 참여 학원이 부담한다(FR-119(쿠폰·할인 차액 업주 부담)). **[신규 2026-09-25]**
- **FR-112a**: 시스템은 **연 구독**을 함께 제공해야 한다. 연 구독 가격은 **월 구독료 × 12개월에서 10% 할인한 금액**이다(원 단위 정수, 1원 미만은 버린다 — 할인이 1원이라도 줄지 않게 회원에게 유리한 쪽). 카드로 1년치를 한 번에 결제하고, 1년 뒤 같은 조건으로 자동 갱신된다. 결제 화면에는 월 구독 12개월 합계·할인액·연 구독 가격을 나란히 보여준다. 구독은 **플랫폼 상품**이라 10% 할인은 **플랫폼이 부담**한다(Q13(구독 판매 주체·요금) 판매 주체 2026-09-25 확정). **[신규 2026-09-25]**
- **FR-112c**: 시스템은 다음 세 가지를 **구독자 전용 혜택**으로 두어야 한다 — ① 1+1 쿠폰(FR-120(구독 1+1 쿠폰)) ② **AI 에이전트 검색**(자연어로 조건을 말하면 수업을 찾아 추천하는 기능 — US6(AI 근거 추천), 판단형 `T2` 질문) ③ **정원 초과 시 대기 신청과 대기자 알림**(FR-093(대기 신청·순번)·FR-094(대기 1번 결제 기회)). 내 예약 조회·자주 묻는 질문(`T0`·`T1`)과 일반 필터 검색, 사람 문의는 구독과 상관없이 모두 쓸 수 있다. **[신규 2026-09-25]**
- **FR-112d**: 시스템은 구독하지 않은 회원에게 **가입일부터 3개월 동안** AI 에이전트 검색과 대기 신청·대기자 알림을 체험으로 열어 줘야 한다. **쿠폰은 체험에 들어가지 않는다.** 체험이 끝나면 두 기능이 닫히고 구독 안내를 보여준다. 체험 중에 걸어 둔 대기는 그 수업이 끝날 때까지 유지한다. 체험은 사람 단위로 1회뿐이다(FR-010(재가입 혜택 차단)과 같은 판정). **[신규 2026-09-25]**
- **FR-113**: 시스템은 정기결제 실패(카드 만료 등) 시 재시도 정책에 따라 처리하고 사용자에게 통지해야 한다.
- **FR-114**: 시스템은 결제 확인을 SMS 가 아니라 앱 내 알림으로 전달해야 하며, 구매자와 학원 관리자 양쪽에 발송해야 한다.
- **FR-115**: 시스템은 결제 요청 금액·결제대행사 응답 금액·저장 금액이 모두 일치하는지 대조해야 하며, 불일치 시 예약을 확정하지 않아야 한다.
- **FR-116**: 시스템은 결제 확인 통지가 중복으로 도착해도 한 번만 반영해야 한다.
- **FR-117**: 시스템은 체크아웃 화면에 정가·할인·쿠폰·최종 결제액을 항목별로 순차 표시해야 한다.
- **FR-118**: 시스템은 대학생 인증 회원의 **최초 첫 결제 1회에만 자동으로 50% 할인**을 적용해야 한다. 첫 결제에 수업이 여러 개거나 여러 달치가 묶여 있으면 수업 1건 1달치에만 적용한다. 두 번째 결제부터는 정상가다 (2026-09-25 변경) — 이전: 1개월차 무료, 그 전에는 3개월 램프(무료 → 반값 → 정상가).
- **FR-118a**: 시스템은 대학생 할인을 **이벤트 팝업**으로 알려야 한다 — 인증을 마친 직후 "대학생 첫 수강 50% 할인 이벤트" 안내를, 첫 결제 화면에서 "대학생 첫 결제 50% 자동 적용" 안내를 띄우고, 가격 내역(FR-117(체크아웃 가격 내역))에 할인액을 따로 보여준다. **[신규 2026-09-25]**
- **FR-118b**: 시스템은 대학생 첫 결제 할인을 **학원의 고객 유치 이벤트**로 다뤄야 한다. 할인 차액은 업주가 부담하고(FR-119(쿠폰·할인 차액 업주 부담)), 그 결제를 환불할 때 돌려받지 못한 PG 수수료도 업주가 부담한다(FR-125c(환불 PG 수수료 업주 부담)). **[신규 2026-09-25]**
- **FR-119**: 시스템은 쿠폰·할인으로 발생한 차액을 학원 부담으로 정산해야 한다. 1+1 쿠폰의 추가 수업 50% 할인, 휴면·우수 회원 반값 쿠폰(FR-084(휴면·우수 회원 쿠폰)), 대학생 할인(FR-118(대학생 첫 결제 50%))으로 줄어든 수업료는 **모두 업주가 부담**한다(2026-09-25 재확인). 그 대신 플랫폼 이용 수수료는 정산 콘솔의 근거(FR-312~FR-315(학원별 플랫폼 기여 ~ 학원 규모 구간))를 보고 적절하게 정한다.
- **FR-120**: 시스템은 월 구독자에게 1+1 쿠폰을 자동 지급해야 한다. **구독을 유지한 채 3개월이 지날 때마다 1장씩** 지급하므로 1년 내내 유지하면 4장이다(2026-09-25 변경 — 이전: 분기 1회 지급, 조건은 FR-120a(쿠폰 생성 조건)).
- **FR-120a**: 시스템은 1+1 쿠폰의 생성 조건을 다음으로 판정해야 한다. **[신규 2026-09-25]**
  - **세는 단위**: 구독 결제가 **연속으로 성공한 달 수**. 구독을 시작한 달이 1개월째다. 달력 분기와는 상관없다.
  - **발급 시점**: 구독을 시작한 날로부터 **3개월이 지난 시점**에 그 3개월을 끊김 없이 유지했으면 1장을 발급한다. 그다음부터는 **3개월마다**(6개월·9개월·12개월이 지난 시점…) 직전 3개월을 유지했을 때만 1장씩 발급한다. 3개월째 결제가 된 순간이 아니라 3개월이 **다 지난 뒤**다(2026-09-25 변경).
  - **끊김**: 재시도(FR-113(정기결제 재시도))까지 실패해 결제되지 않은 달이 생기거나 구독이 해지돼 결제가 멈추면 세던 개월 수는 0 으로 돌아간다. 다시 구독하면 1개월째부터 센다.
  - **결제 실패 뒤 재시도 성공**: 그달 결제가 결국 성공하면 끊기지 않은 것으로 본다.
  - **해지 예약**: 해지(FR-297(구독 해지))를 신청해도 이미 결제한 달까지는 센다.
  - **연 구독(FR-112a(연 구독 10% 할인))**: 월 구독과 같은 기준이다. 결제한 날로부터 **3개월·6개월·9개월·12개월이 지난 시점**에 1장씩, 1년에 4장이다. 1년치를 한 번에 결제했으므로 결제한 기간은 모두 유지한 것으로 본다. 월 구독에서 연 구독으로 바꾸면 세던 개월 수를 이어서 센다.
  - **화면 표시**: 구독 화면에 지금 몇 개월째인지와 다음 쿠폰까지 남은 달을 보여준다(예: "구독 2개월째 — 11월 15일에 쿠폰 1장").
- **FR-121**: 시스템은 1+1 쿠폰을 다음 조건에서만 쓰게 해야 하며, 조건은 모두 서버에서 검증한다(2026-09-25 구체화 — 이전: 유료 수업 1건 포함·장르·레벨 적합성 검증).
  - **1+1 의 뜻**: 수업 1달치를 정가로 신청하면서 **비슷한 레벨의 다른 수업 1달치를 함께 신청**하면, 그 추가 1달치를 **50% 할인**한다. 무료 좌석이 아니다.
  - **수업 하나만 신청하면 적용하지 않는다.** 반드시 정가 수업 1달치 + 추가 수업 1달치를 한 번에 신청해야 한다.
  - **할인 범위는 1달치뿐이다.** 예를 들어 9월~10월 2달치 수업을 신청해도 50% 할인은 1달치에만 들어간다.
  - **다음 달 수업 신청 때 쓴다.** 쿠폰은 발급된 뒤 다음 달에 시작하는 수업을 신청할 때 같이 쓴다.
  - 레벨 범위는 FR-121a(쿠폰 레벨 범위), 적용 장르는 FR-121b(쿠폰 베타 적용 장르), 학원 참여 여부는 FR-121c(쿠폰 참여 학원)를 따른다.
- **FR-121a**: 시스템은 1+1 쿠폰을 **본인 레벨 범위 안의 수업**에만 쓰게 해야 한다. 레벨은 프로필의 경험 수준(FR-029(경험 수준 구간))으로 판정한다. **[신규 2026-09-25]**
  - 입문(0~6개월)·초급(6개월~2년)·중급(2~4년)은 **자기 레벨 수업에만** 쓸 수 있다. 예: 입문 6개월차 이내는 입문 수업만.
  - 고급(5년 이상)만 **고급 이하 모든 레벨** 수업에 쓸 수 있다.
- **FR-121b**: 시스템은 1+1 쿠폰을 베타 기간 동안 **댄스스포츠 장르의 라틴 수업**(차차차·삼바·룸바·파소도블레·자이브)에만 적용해야 한다. 다른 장르·세부 장르 수업에서는 쿠폰 선택지가 활성화되지 않는다. 적용 장르를 넓힐 때는 이 요구사항을 고친다. **[신규 2026-09-25 — 베타 서비스]**
- **FR-121c**: 시스템은 업주가 1+1 쿠폰에 **참여할지 고르게** 해야 한다. 참여하지 않은 학원은 다음처럼 처리한다. **[신규 2026-09-25]**
  - 수강 신청 화면에 그 학원 수업이 **"쿠폰 미적용"** 으로 표시된다.
  - 그 학원 수업에서는 쿠폰 선택지가 비활성화된다.
  - 수강생이 그 학원 수업에 쿠폰을 쓰려 하면 **"쿠폰은 참여 업체에 한해 적용됩니다"** 경고 팝업을 띄운다.
  - 참여한 학원만 50% 할인 차액을 부담한다(FR-119(쿠폰·할인 차액 업주 부담)).
- **FR-122**: 시스템은 1+1 쿠폰을 **다음 쿠폰이 발급되기 전까지** 쓸 수 있게 하고, **발급일로부터 3개월 안에 쓰지 않으면** 소멸시키며, 소멸 예정일을 사용자 화면에 상시 표시해야 한다. 쿠폰 하나를 쓰는 기간이 다음 쿠폰이 생기기까지의 3개월과 같다(2026-09-25 변경 — 이전: 분기 말 소멸). 다른 쿠폰의 소멸 규칙은 각 요구사항을 따른다(예: 우수 회원 쿠폰 FR-084a(우수 회원 산정)).
- **FR-123**: 시스템은 쿠폰의 타인 양도를 허용하지 않아야 한다.
- **FR-124**: 시스템은 **모든 수업 결제**에 플랫폼 이용 수수료 **5%**를 적용하고 95%를 지급해야 하며, 학원의 **입점일부터 1년 동안** 수수료를 면제해야 한다(2026-09-25 변경 — 이전: 8%, 베타 첫 6개월 면제). 면제 종료일은 정산 화면에 표시한다.
- **FR-125**: 시스템은 학원 정산을 매월 정해진 날에 실행하고 총 결제액·수수료·실지급액·쿠폰 사용 건수·신규 회원 수를 내역으로 제공해야 한다.
- **FR-125a**: 시스템은 학원 정산 내역에 **카드 결제 수수료**를 플랫폼 수수료(FR-124(플랫폼 수수료 5%·1년 면제))와 따로 한 줄로 보여줘야 한다 — 카드 결제 건수·카드 결제액·공제한 카드 수수료. 입점 1년 수수료 면제 기간(FR-124(플랫폼 수수료 5%·1년 면제))에도 카드 수수료는 실비로 공제한다. 수업 결제를 환불할 때 돌려받지 못한 PG 수수료는 FR-125c(환불 PG 수수료 업주 부담)에 따라 따로 한 줄로 공제한다. **[신규 2026-09-25 — Q12(정규 과정 카드 수수료 부담) 확정]**
- **FR-125d**: 시스템은 **PG 결제 수수료**(가상계좌·간편 계좌이체 등 카드가 아닌 PG 결제)를 **업주 부담**으로 학원 정산에서 공제하고, 정산 내역에 따로 한 줄로 보여줘야 한다. 수강생에게 더 받지 않는다. 플랫폼 수수료 면제 기간에도 공제한다. **[신규 2026-09-25]**
- **FR-125e**: 시스템은 플랫폼 몫을 다음 두 가지로 나눠 계산해야 한다. **[신규 2026-09-25, 같은 날 사용자 결정으로 취소 수수료 5:5 확정]**
  - **판매 수수료 5%** — 실제로 제공된(취소되지 않은) 판매에만 받는다(FR-124(플랫폼 수수료 5%·1년 면제), 입점 1년 면제). 취소된 결제에는 판매 수수료를 받지 않고, 이미 뗐으면 전액 돌려준다.
  - **취소 수수료 5:5** — 정규 과정을 **제외한** 파티·원데이·공연·대회 상품에서, 취소 수수료 규정(FR-099c(파티·원데이·공연·대회 취소 규정))에 따라 환불하지 않고 남은 금액은 수업을 제공하지 않고 생긴 이익이므로 **플랫폼 50% · 업주 50%**로 나눈다. 판매 수수료 5%와는 별도이며, **입점 1년 면제 기간에도 적용한다**(2026-09-25 사용자 확정).
  - **노쇼는 판매로 본다** — 취소 기한이 지나 취소하지 못했거나 연락 없이 오지 않은 경우, 수업은 열렸으므로 불로소득이 아니라 판매로 처리하고 판매 수수료 5%만 적용한다(입점 1년 면제 기간에는 0%)(2026-09-25 사용자 확정). **이유**: 취소 기한 뒤에는 업주가 그 자리를 다시 채울 기회가 없어 공석으로 남는다. 남은 금액은 빈자리에 대한 업주의 손실 보전이지 추가 이익이 아니다. 반대로 취소 기한 전의 취소는 대기자에게 자리를 다시 팔 수 있어(FR-094a(대기 순번 한 명씩 넘김)) 취소 수수료와 새 판매금을 함께 얻는 추가 이익이 생기므로 5:5 로 나눈다.
  - **정규 과정의 중도 환불**은 이미 제공한 수업분이 남는 것이라 5:5 를 쓰지 않고, 남은 금액(순매출)에 판매 수수료 5%를 적용한다.
  - 환불로 돌려받지 못한 PG·카드 수수료는 업주가 부담한다(FR-125c(환불 PG 수수료 업주 부담)).

  | 예: 5만원 원데이, 입점 1년 뒤, PG 수수료 750원 | 환불 | 남은 금액 | 플랫폼 | 업주 |
  |---|---|---|---|---|
  | 취소 없음(수업 제공) | 0 | 50,000 | 2,500(판매 수수료 5%) | 50,000 − 2,500 − 750 = 46,750 |
  | 3일 전 취소(20% 공제) | 40,000 | 10,000 | 5,000(취소 수수료 50%) | 5,000 − 750 = 4,250 |
  | 1일 전 취소(30% 공제) | 35,000 | 15,000 | 7,500 | 7,500 − 750 = 6,750 |
  | 전액 환불 | 50,000 | 0 | 0 | −750 |

  - 모든 금액 변화는 **학원 정산 원장**(`AcademyLedgerEntry(학원 정산 원장)`)에 추가만 하는 기록으로 남긴다 — 판매·판매 수수료·고객 환불·취소 수수료·취소 수수료 배분·판매 수수료 환급·카드 수수료·PG 결제 수수료·환불 PG 수수료·쿠폰·대학생 할인 부담·조정. 항목마다 주문 시점의 수수료율과 배분 비율을 함께 적는다(FR-284(주문 시점 값 고정)). 정산 콘솔 합계는 이 원장과 대조한다(FR-318(원장 대사)).
- **FR-125c**: 시스템은 **수업 결제**를 환불할 때 돌려받지 못한 PG 수수료를 **업주 부담**으로 학원 정산에서 공제하고, 정산 내역에 "환불 PG 수수료"로 따로 보여줘야 한다. 수강생 환불액에서는 빼지 않는다. **월·연 구독**의 환불 PG 수수료만 플랫폼이 부담한다 — 구독은 플랫폼 상품이기 때문이다(FR-112b(구독은 플랫폼 상품)). 반값 쿠폰 등 수업 할인 차액이 업주 몫인 것(FR-119(쿠폰·할인 차액 업주 부담))과 같은 원리다 — 수업을 파는 쪽이 수업 거래 비용을 낸다. **[신규 2026-09-25 — 이전: 모든 환불 PG 수수료 플랫폼 부담]**
- **FR-125b**: 시스템은 업주가 입점할 때 카드 결제 수수료를 업주가 부담한다는 조건과 공제 방식을 고지하고, 업주의 동의와 동의 시각을 기록해야 한다(FR-249(약관 동의 기록) 와 같은 방식). 동의하지 않은 학원은 카드 결제를 열 수 없다. **[신규 2026-09-25 — Q12(정규 과정 카드 수수료 부담) 확정, 같은 날 모든 결제로 확대]**
- **FR-126**: 시스템은 강사별 수업 매출을 집계해 강사와 업주가 조회하도록 해야 한다.
- **FR-127**: 시스템은 강사를 고용 관계가 아니라 **프리랜서**로 다뤄야 한다. 월급·시급 같은 급여 개념을 두지 않으며, 강사의 수입은 온라인 수강 신청과 개인 레슨의 **수업 기간이 끝난 분에 대한 정산**으로만 발생한다.
- **FR-128**: 시스템은 정산 상태를 세 단계로 관리해야 한다 — 결제 완료부터 수업 시작 전까지 `보류`, 수업 시작부터 기간 종료 전까지 `정산 완료 예정`, 수업 기간 종료 시점에 `정산 완료`.
- **FR-129**: 시스템은 정산 상태 전이를 **시각**으로 판정해야 한다. 수업 시작 시각이 되면 보류에서 예정으로, 수업 기간 종료 시각이 되면 예정에서 완료로 넘긴다.
- **FR-130**: 시스템은 각 단계의 금액을 구분해 표시해야 한다. 보류분·예정분·완료분이 각각 얼마인지 조회할 수 있어야 한다.
- **FR-131**: 시스템은 수업 취소(휴강·폐강)와 수강생 취소를 **예외 처리 경로**로 다뤄야 한다. 환불을 먼저 처리하고 그 결과를 정산 금액에 반영한다.
- **FR-132**: 시스템은 정산 조정을 두 갈래로 처리해야 한다 — 보류·예정 구간이면 그 자리에서 차감하고, 이미 완료된 건이면 되돌리지 않고 다음 정산 주기에 증감으로 반영한다.
- **FR-133**: 시스템은 정산금을 **강사 전용 계좌**로 지급해야 하며, 강사 1인당 하나의 전용 계좌를 두고 정산 이력이 그 계좌에 묶이게 해야 한다.

- **FR-135a**: 시스템은 개인 레슨을 학원 수업과 **별도 정산 경로**로 처리해야 한다. 학원을 거치지 않는 강사 직접 상품이므로 학원 수수료·정산 분배가 적용되지 않는다. **[신규]**
- **FR-135b**: 시스템은 출석 기록을 노쇼·분쟁 판정의 근거로 사용해야 한다. 출석은 정산 단계 전이의 트리거가 아니라 **예외를 가릴 때 꺼내 보는 근거**다.
- **FR-135c**: 시스템은 무단 불참(노쇼) 회차의 정산 처리 기준을 학원·강사가 사전에 정하도록 하고, 그 기준을 수강생에게 결제 전에 고지해야 한다. **[신규]**
- **FR-135d**: 시스템은 프리랜서 강사에게 지급하는 금액에 대해 원천징수 항목을 정산 내역에 구분 표기해야 한다. **[신규]**
- **FR-135e**: 시스템은 강사에게 기간별 정산 내역을 제공해야 한다 — 수업 건수, 보류분, 예정분, 완료분, 조정분, 공제 항목, 실지급액.
- **FR-136**: 시스템은 여러 학원에서 함께 쓸 수 있는 통합 회차권을 발행할 수 있어야 한다. **[신규 — 사용처별 정산 분배 규칙이 선행 조건]**
- **FR-137**: 시스템은 결제·환불 관련 자격 증명을 소스 코드에 포함하지 않아야 한다.
- **FR-138**: 시스템은 수강생이 결제·환불 내역과 영수증을 앱에서 조회할 수 있게 하고 현금영수증 발급 신청을 받을 수 있어야 한다. **[신규 2026-09-25]**
- **FR-139**: 시스템은 강사 전용 계좌(FR-133(강사 전용 계좌))를 바꿀 때 본인확인을 다시 거치게 하고, 변경 사실을 감사 기록으로 남기며 강사에게 통지해야 한다. **[신규 2026-09-25]**

#### 결제 상세 — 2026-09-25 확정안 기준 (FR-280~FR-299)

##### 결제수단 결정 (FR-280~FR-282)

- **FR-280**: 시스템은 상품과 금액에 따라 결제 경로와 고를 수 있는 수단을 아래 표대로 정해야 한다. 사용자가 경로를 직접 고르지 않는다.

  | 상품 | 경로 | 고를 수 있는 수단 |
  |---|---|---|
  | 파티·원데이·공연·대회·이벤트·단기 과정 | PG | 가상계좌(기본) · 간편 계좌이체 · **신용·체크카드** |
  | 정규 과정(정기 수업) | PG | 가상계좌(기본) · 간편 계좌이체 · **신용·체크카드** |
  | 개인 레슨 | PG | 가상계좌(기본) · 간편 계좌이체 · **신용·체크카드** |
  | 월 구독 | PG | 카드 자동결제만 |
  | 연 구독 | PG | 카드(1년치 한 번에, 1년마다 자동 갱신) |
  | 무료 수업 | 결제 없음 | 신청만으로 확정 |
  | 외부 예매 공연 | 결제 없음 | 예매 링크로 이동(FR-153(외부 예매 연결)) |

  2026-09-25 에 금액 기준(9만원) 분기와 딥링크 경로를 없앴다. 신용·체크카드는 모든 유료 결제에서 받는다(FR-111a(모든 결제 카드 허용), 2026-09-25 확대).
- **FR-281**: 시스템은 결제 화면에 고를 수 있는 수단만 보여야 하며 수단마다 **환불 방식이 어떻게 다른지** 결제 전에 알려야 한다 — 카드는 승인 취소로 돌려받고 가상계좌·간편 계좌이체는 환불계좌를 받아 따로 송금한다.
- **FR-282**: 시스템은 결제 화면에 다음을 반드시 함께 표시해야 한다 — 그 학원의 환불·취소 공지(FR-099b(공지 자동 입력)), 회사가 통신판매중개자라는 고지(FR-240(통신판매중개자 고지)), 가격 내역(FR-117(체크아웃 가격 내역)). 셋 중 하나라도 빠지면 결제 버튼이 동작하지 않아야 한다.
- **FR-282a**: 시스템은 **파티·원데이 클래스·공연·대회** 결제에 1명당 **예매 수수료 2,000원**을 붙이고, 결제 화면에 수업료와 따로 표시해야 한다. 예매 수수료는 **플랫폼에 귀속**되며 학원 정산·판매 수수료·취소 수수료 배분(FR-125e(취소 수수료 5:5·판매 수수료 5%))의 계산에 넣지 않는다. **취소해도 환불하지 않는다**(사용자 결정). 정규 과정·구독권에는 붙지 않는다. ⚠ 학원·강사 사정의 휴강·폐강과 법정 청약철회에서는 환불하지 않는 것이 무효로 다퉈질 수 있어 법률 검토 대상이다(Q11(환불 방식 변경의 뒤처리) ①). **[신규 2026-09-25]**

##### 결제 금액 계산 (FR-283~FR-284)

- **FR-283**: 시스템은 최종 결제액을 **정가 → 혜택 할인 → 쿠폰 → 최종액** 순서로 원 단위 정수로 계산해야 한다. 대학생 첫 결제 할인(FR-118(대학생 첫 결제 50%))과 쿠폰(FR-120(구독 1+1 쿠폰))이 동시에 해당되면 **할인액이 큰 쪽 하나만** 적용하고 나머지는 쓰지 않은 상태로 남긴다. 1+1 쿠폰은 주 수업이 정가여야 하므로(FR-121(1+1 쿠폰 사용 조건)) 대학생 할인 결제와 한 주문에 묶이지 않는다. 계산 결과가 0원 미만이 되지 않는다.
- **FR-284**: 시스템은 주문을 만들 때 계산한 금액·적용한 할인·쿠폰·그 시점의 환불·취소 공지 판본을 주문에 고정해 저장해야 한다. 이후 가격이나 공지가 바뀌어도 이 주문에는 저장된 값이 적용된다(FR-245(결제 시점 정책 적용)).

##### 결제 생성과 입금 대기 (FR-285~FR-288)

- **FR-285**: 시스템은 결제를 시작하는 순간 자리를 `held(대기)` 로 잡고(FR-096(결제 대기 자리 잠금)), 수단별 결제 기한을 정해야 한다.

  | 수단 | 결제 기한 | 기한이 지나면 |
  |---|---|---|
  | 신용·체크카드 | 결제 창을 연 뒤 정해진 몇 분 | 주문 만료, 자리 해제 |
  | 가상계좌 | 발급 시각부터 정해진 시간, 또는 수업 시작 시각 중 **이른 쪽** | 주문 만료, 발급 계좌 폐기, 자리 해제 |
  | 간편 계좌이체 | 결제 창을 연 뒤 정해진 몇 분 | 주문 만료, 자리 해제 |

  각 기한의 구체 값은 전제 18 에서 정한다. 자리가 풀리면 대기 1순위에게 결제 기회가 간다(FR-094(대기 1번 결제 기회)).
- **FR-286**: 시스템은 입금 대기 중인 수강생이 **입금 전에는 스스로 주문을 취소**할 수 있게 해야 한다. 아직 돈이 오가지 않아 환불이 아니며 자리를 곧바로 푼다. 입금이 확인된 뒤에는 이 버튼이 사라지고 환불 요청(FR-098b(환불 요청 경로))으로만 되돌릴 수 있다.
- **FR-287**: 시스템은 PG 경로(방식 B)의 결제 확정을 PG 결과 통지(웹훅)로만 판정해야 한다. 통지의 서명을 검증하고, 요청 금액·PG 응답 금액·저장 금액을 대조하며(FR-115(결제 금액 대조)), 같은 통지가 여러 번 와도 한 번만 반영한다(FR-116(결제 통지 중복 반영 방지)). 앱 화면에서 "결제 완료"로 돌아왔다는 사실만으로 확정하지 않는다.
- **FR-288**: ~~딥링크 경로의 입금을 계좌 입금 내역 조회로 확인~~ — **삭제(2026-09-25).** 딥링크 폐지로 모든 입금은 PG 결과 통지(FR-287(웹훅 확정))로 확인한다. 번호는 재사용하지 않는다.
- **FR-288a**: ~~딥링크 결제 처리(학원 계좌 수금·앱 버튼 전달·필요할 때 입금 조회·수강생 수령 확인·다음 정산 수수료 차감)~~ — **삭제(2026-09-25).** 딥링크를 없애고 PG 로 통일했다. 번호는 재사용하지 않는다.
- **FR-289**: 시스템은 결제가 확정되면 한 번에 다음을 처리해야 한다 — 예약 `confirmed(확정)`, 신청 인원 증가, 사용한 쿠폰·혜택 소진 기록, 내 캘린더 등록, 수강생·업주 앱 알림(FR-114(결제 확인 앱 알림)), 정산 `hold(보류)` 금액 적립(FR-128(정산 3단계)). 이 중 일부만 처리된 상태가 남지 않아야 한다.

##### 실패와 예외 (FR-290~FR-292)

- **FR-290**: 시스템은 가상계좌에 **주문 금액과 다른 금액**이 입금되면 예약을 확정하지 않아야 한다. 들어온 금액은 전액 돌려줄 대상으로 기록하고 수강생과 업주에게 알린다.
- **FR-291**: 시스템은 같은 주문에 결제가 두 번 확인되면(중복 결제) 먼저 확인된 건만 유효로 두고 나머지를 자동으로 전액 환불해야 한다. 이는 결제 시스템 문제이므로 운영자 관리 대상이다(FR-204(운영자 역할 한정)).
- **FR-292**: 시스템은 결제 확인 통지가 늦게 도착해 이미 만료된 주문에 입금이 확인되면, 자리가 남아 있을 때만 확정하고, 남은 자리가 없으면 확정하지 않고 전액 돌려줄 대상으로 기록해야 한다.

##### 환불 실행 (FR-293~FR-296)

- **FR-293**: 시스템은 업주가 환불 요청(FR-098b(환불 요청 경로))을 처리할 때 **환불 여부, 환불 금액(0원 ~ 결제액), 근거가 된 공지 항목**을 입력하게 해야 한다. 금액은 결제액을 넘을 수 없고 입력하지 않은 항목이 있으면 처리 완료로 넘어가지 않는다. 거절할 때도 근거 항목을 고른다.
- **FR-294**: 시스템은 정규 과정의 중도 환불 요청이면 업주 화면에 **진행한 회차 수·남은 회차 수·회차당 금액**을 계산 보조로 보여줘야 한다. 금액은 업주가 정하며 시스템이 대신 정하지 않는다.
- **FR-295**: 시스템은 업주가 정한 금액을 **업주가 직접** 결제수단에 맞게 실행할 수 있게 해야 한다. 플랫폼은 수업 결제 환불을 실행하지 않고, 실행 수단과 기록만 제공한다 (2026-09-25 변경 — 수업 환불은 업주가 실행, 구독권 환불만 플랫폼).

  | 원래 결제수단 | 전액 환불 | 부분 환불 |
  |---|---|---|
  | 신용·체크카드 | 업주가 업주 화면에서 환불 실행 → PG 승인 취소 | PG 부분 취소 |
  | 가상계좌 · 간편 계좌이체 | 업주가 업주 화면에서 환불 실행 → 수강생 환불계좌로 송금. 환불계좌 입력 필수, `pending` 은 정상 상태 | 같음 |
  | 월·연 구독권 | **플랫폼이** 실행(FR-297a(구독 환불 14일 이내)) — 플랫폼이 판매자인 유일한 상품 | 없음 |

  실행 결과(`succeeded` · `pending` · `failed`)와 실패 사유를 기록하고(FR-103(환불 실패 기록)), 같은 요청이 여러 번 와도 한 번만 실행한다(FR-102(환불 1회 보장)).
- **FR-296**: 시스템은 환불이 끝나면 쿠폰·혜택을 다음 규칙으로 처리해야 한다 — **전액 환불**이고 쿠폰의 유효기간이 남아 있으면 쿠폰을 되살리고, **부분 환불**이면 되살리지 않는다. 대학생 혜택 회차는 전액 환불일 때만 되돌린다. 환불 결과는 정산에 반영한다(FR-131(취소 예외 경로)·FR-132(정산 조정)).

##### 월 구독 (FR-297)

- **FR-297**: 시스템은 구독자가 **스스로 구독을 해지**할 수 있게 해야 한다. 해지하면 다음 결제일부터 청구하지 않고 이미 결제한 달은 끝까지 쓸 수 있다. 연 구독(FR-112a(연 구독 10% 할인))을 해지하면 다음 해 자동 갱신만 멈추고, 이미 결제한 1년은 끝까지 쓸 수 있다. 해지는 환불이 아니므로 업주 승인을 거치지 않는다. 이미 결제한 구독의 환불은 FR-297a(구독 환불 14일 이내)를 따른다. 환불 요청은 **플랫폼**에 한다 — 구독은 플랫폼 상품이라(FR-112b(구독은 플랫폼 상품)) 업주에게 가는 수업 환불 요청(FR-098b(환불 요청 경로))과 경로가 다르다. 받는 쪽은 운영자다(2026-09-25 변경).
- **FR-297a**: 시스템은 구독권(월·연)을 **구매 후 14일 이내에만** 환불할 수 있게 해야 한다. 14일 이내면 결제액 전액을 돌려주고, 14일이 지나면 환불하지 않는다(해지만 가능 — FR-297(구독 해지)). 이 조건은 구독 구매 화면과 결제 화면에 결제 전에 표시한다. 자동 갱신 결제도 그 갱신 결제일부터 14일을 새로 센다. 환불로 돌려받지 못한 PG 수수료는 플랫폼이 부담한다(FR-125c(환불 PG 수수료 업주 부담)). **[신규 2026-09-25]**

##### 상태와 보안 (FR-298~FR-299)

- **FR-298**: 시스템은 주문 상태를 다음으로 관리해야 한다. 상태는 되돌아가지 않으며 모든 전이를 감사 기록으로 남긴다(FR-101(환불 감사 기록)).

  | 상태 | 뜻 | 다음 상태 |
  |---|---|---|
  | `pending(미결제)` | 주문 생성, 결제·입금 대기 | `paid` · `expired` · `cancelled` |
  | `expired(만료)` | 결제 기한이 지남 | — |
  | `cancelled(입금 전 취소)` | 수강생이 입금 전에 취소(FR-286(입금 전 셀프 취소)) | — |
  | `paid(결제완료)` | 결제 확정 | `partially_refunded` · `refunded` |
  | `partially_refunded(부분 환불)` | 업주가 일부만 환불 | `refunded` |
  | `refunded(환불)` | 전액 환불 완료 | — |

  기존 구현의 주문 상태는 `pending` · `paid` · `refunded` 셋뿐이라, `expired` · `cancelled` · `partially_refunded` 를 더해야 한다.
- **FR-299**: 시스템은 카드번호를 저장하지 않고 PG 가 준 식별값만 저장해야 한다. 환불계좌는 암호화해 저장하고 화면에는 가려서 보여주며, 업주는 환불 실행에 필요한 경우에만 전체를 볼 수 있고 그 열람은 기록으로 남는다(FR-187(연락처 마스킹) 과 같은 방식).

#### 플랫폼 관리자 정산 콘솔 (FR-300~FR-319)

플랫폼이 업주에게 받을 수수료를 정하려면 근거가 필요하다. 이 묶음은 플랫폼 관리자가 보는 **정산 콘솔**을 정한다 — 업주 관리 웹과 같은 로그인 화면을 쓰고, 플랫폼 관리자로 로그인하면 이 콘솔이 열린다. 콘솔은 **보고 판단하는 곳**이다. 학원의 수업·가격·환불 결정은 고치지 않는다. **[신규 2026-09-25]**

**비용을 누가 내는가 (콘솔이 보여주는 숫자의 기준)**

| 비용 | 부담 | 근거 |
|---|---|---|
| 쿠폰(1+1 추가 수업 50% · 반값 쿠폰)과 할인으로 줄어든 수업료 | **업주** (1+1 은 참여 학원만) | FR-119 · FR-121c |
| 대학생 첫 결제 50% 차액과 그 환불 PG 수수료 | 업주 | FR-118b · FR-119 |
| 카드 결제 수수료 | 업주 | FR-125a |
| 플랫폼 이용 수수료(5%, 입점 1년 면제) | 업주 → 플랫폼 수입 | FR-124 |
| PG 결제 수수료(카드 외) | 업주 | FR-125d |
| 수업 결제 환불로 돌려받지 못한 PG 수수료 | **업주** | FR-125c |
| 구독(월·연) 환불로 돌려받지 못한 PG 수수료 | 플랫폼 | FR-125c |
| 연 구독 10% 할인 | 플랫폼 | FR-112a · FR-112b |

##### 접근과 권한 (FR-300~FR-303)

- **FR-300**: 시스템은 업주 관리 웹과 **같은 로그인 화면**을 쓰고, 로그인한 계정의 역할에 따라 첫 화면을 나눠야 한다 — 업주는 학원 관리 화면, 플랫폼 관리자(`Admin`)는 플랫폼 정산 콘솔. 한 사람이 두 역할을 다 가지면 로그인 뒤 어느 쪽으로 들어갈지 고르게 한다.
- **FR-301**: 시스템은 플랫폼 정산 콘솔을 **조회 전용**으로 두어야 한다. 학원의 수업·가격·환불 결정·정산 금액을 콘솔에서 바꿀 수 없다. 예외는 플랫폼 수수료율 설정(FR-316(수수료율 변경)) 하나다.
- **FR-302**: 시스템은 콘솔에 수강생 개인을 알아볼 수 있는 정보(이름·연락처·나이)를 보여주지 않아야 한다. 학원·강사·수업 단위로 모은 숫자만 보여준다. 학원별 매출은 보이지만, 콘솔에서 무엇을 조회했는지는 감사 기록으로 남는다(FR-185(조작 감사 기록)).
- **FR-303**: 시스템은 플랫폼 관리자 계정에 2단계 인증을 요구해야 한다. 관리자 계정은 업주가 만들거나 부여할 수 없고 플랫폼이 직접 발급한다.

##### 대시보드 (FR-304~FR-305)

- **FR-304**: 시스템은 콘솔 첫 화면에 기간(일·주·월·분기·연·직접 지정)을 고르면 다음 지표를 카드로 보여줘야 한다.

  | 묶음 | 지표 |
  |---|---|
  | 거래 | 총 결제액 · 결제 건수 · 환불액 · 환불률 · 순결제액(결제 − 환불) |
  | 플랫폼 수입 | 취소 수수료 배분 수입(5:5, FR-125e) · 이용 수수료 수입(실제 징수) · **면제가 없었다면 받았을 수수료**(베타 면제 효과) · 구독 수입(월·연 구분) |
  | 플랫폼 비용 | 연 구독 할인액 · 구독 환불 PG 수수료 |
  | 업주 부담 | 쿠폰·할인 차액 · 대학생 혜택 차액 · 카드 결제 수수료 · 수업 환불 PG 수수료 |
  | 규모 | 활동 학원 수 · 활동 강사 수 · 결제한 수강생 수 · 신규 회원 수 |

- **FR-305**: 시스템은 각 지표를 기간별 추이 그래프로 보여주고, **직전 같은 길이 기간과 비교한 증감**을 함께 표시해야 한다.

##### 결산 화면 (FR-306~FR-311)

- **FR-306**: 시스템은 **장르별 결산**을 제공해야 한다 — 장르 4종(FR-020(장르 4종))을 먼저 보여주고 누르면 세부 장르(FR-021(세부 장르))로 내려간다. 항목마다 결제액·건수·평균 결제액·환불률·쿠폰 사용률·쿠폰 차액·이용 수수료를 보여준다.
- **FR-307**: 시스템은 **학원별 결산**을 제공해야 한다. 목록은 결제액·수수료·쿠폰 부담액·환불률로 정렬할 수 있고, 학원을 누르면 그 학원의 상세를 보여준다 — 수업별·강사별 매출, 정산 단계별 금액(보류·예정·완료 — FR-128(정산 3단계)), 쿠폰·혜택 부담액, 카드 결제 수수료, 수수료 면제 여부와 면제 종료일.
- **FR-308**: 시스템은 **상품 유형별 결산**(정규·단기·원데이·개인 레슨·이벤트·파티)과 **결제수단별 결산**(가상계좌·간편 계좌이체·카드)을 제공해야 한다. 수단별 결산에는 수단마다 드는 결제 비용을 함께 보여준다.
- **FR-309**: 시스템은 **지역별 결산**(시·구 단위)을 제공해야 한다.
- **FR-310**: 시스템은 **전체 결산표**를 기간 단위로 제공해야 한다. 한 표에서 돈의 흐름을 위에서 아래로 따라갈 수 있어야 한다.

  ```text
  총 결제액
   − 환불액
   = 순결제액
     ├─ 업주 부담: 쿠폰·할인 차액 / 대학생 혜택 차액 / 카드 결제 수수료 / 수업 환불 PG 수수료
     ├─ 플랫폼 이용 수수료 (면제분은 따로 표시)
     └─ 학원 지급액
  플랫폼 손익 = 판매 수수료 + 취소 수수료 배분(50%) + 구독 수입 − 연 구독 할인 − 구독 환불 PG 수수료
  ```

- **FR-311**: 시스템은 **지급 현황**을 제공해야 한다 — 학원 정산 지급 예정·완료·보류 금액과 건수, 강사 정산 합계(학원 수업분과 개인 레슨분 구분 — FR-135a(개인 레슨 별도 정산)), 다음 정산일(매월 5일).

##### 수수료 책정 근거 (FR-312~FR-316)

- **FR-312**: 시스템은 학원마다 **플랫폼이 가져다준 가치**를 보여줘야 한다 — 플랫폼을 통해 처음 온 회원 수, 그 회원들의 결제액, 재결제율(SC-021(30일 재결제 40%) 과 같은 정의), 검색·추천 노출에서 결제로 이어진 비율. 수수료를 학원마다 달리 매길 근거가 된다.
- **FR-313**: 시스템은 학원마다 **업주가 이미 부담하고 있는 비용**(쿠폰·혜택 차액·카드 수수료)을 결제액 대비 비율로 보여줘야 한다. 수수료를 올릴 때 업주 부담이 얼마나 커지는지 함께 보기 위해서다.
- **FR-314**: 시스템은 **수수료 모의 계산**을 제공해야 한다. 수수료율(전체 또는 학원별·상품 유형별)을 바꿔 넣으면 선택한 과거 기간의 실제 거래에 대입해 플랫폼 수입·학원 지급액·학원별 증감을 계산해 보여준다. 모의 계산은 실제 정산에 적용되지 않는다.
- **FR-315**: 시스템은 **학원 규모 구간별 분포**를 보여줘야 한다 — 학원별 월 결제액 구간(예: 100만원 미만 · 100~500만원 · 500만원 이상)마다 학원 수와 수수료 수입. 구간별 차등 수수료를 검토하는 근거다.
- **FR-316**: 시스템은 플랫폼 관리자가 **수수료율을 바꿀 수 있게** 하되 다음을 지켜야 한다.
  - 적용 시작일을 미래 날짜로만 정한다. 이미 결제된 거래에는 **결제 시점의 수수료율**이 적용된다(FR-245(결제 시점 정책 적용) · FR-284(주문 시점 값 고정)).
  - 업주에게 적용 시작일 전에 알린다. 수수료가 오르는 변경은 더 긴 기간을 두고 개별 통지한다(FR-243(약관 변경 공지) 과 같은 기준).
  - 수수료율은 전체 기본값과 학원별 예외값을 둘 수 있다. 모든 변경은 누가·언제·무엇을 바꿨는지 감사 기록으로 남는다.
  - 입점 1년 면제 기간(FR-124(플랫폼 수수료 5%·1년 면제))이 남은 학원에는 면제가 끝난 날부터 적용된다.

##### 내보내기와 정합성 (FR-317~FR-319)

- **FR-317**: 시스템은 모든 결산 화면을 **파일로 내보낼 수 있게** 해야 한다(세무·회계용 표 형식). 내보낸 파일에도 수강생 개인정보는 들어가지 않는다(FR-302(콘솔 개인정보 비노출)).
- **FR-318**: 시스템은 콘솔의 합계가 **결제·환불·정산 원장 합계와 일치하는지** 매일 검사하고, 어긋나면 콘솔 첫 화면에 경고와 어긋난 금액을 보여줘야 한다(SC-010b(정산 합계 일치) 와 같은 원리).
- **FR-319**: 시스템은 각 화면에 **데이터 기준 시각**을 표시하고, 정산이 끝난 달은 **마감**으로 잠가야 한다. 마감 뒤 생긴 환불·조정은 그 달 숫자를 바꾸지 않고 다음 달에 조정 항목으로 보인다(FR-132(정산 조정) 와 같은 원리).

#### 알림 (FR-140~FR-149)

- **FR-140**: 시스템은 사용자가 수업 전 알림 시점을 하루 전·2시간 전·1시간 전·30분 전 중에서 고르도록 해야 한다.
- **FR-141**: 시스템은 수업 시간·장소 변경, 휴강, 취소 발생 시 영향을 받는 모든 대상에게 알림을 발송해야 한다.
- **FR-142**: 시스템은 관심 강사·관심 학원의 신규 수업과 이벤트를 알림으로 전달해야 한다.
- **FR-143**: 시스템은 대기 순번 변동과 결제 기회 발생을 대기자에게 알림으로 전달해야 한다.
- **FR-144**: 시스템은 알림 발송 실패를 기록하고 재시도해야 하며, 사용자가 앱에서 미확인 알림을 확인할 수 있어야 한다.
- **FR-145**: 시스템은 관리자 웹에도 동일한 실시간 알림을 전달해야 한다.
- **FR-146**: 시스템은 광고성 알림(관심 강사 신규 수업 홍보·쿠폰·이벤트)의 수신 동의를 거래 알림(예약·결제·변경)과 따로 받아야 하며 야간에는 광고성 알림을 보내지 않아야 한다. **[신규 2026-09-25]**

#### 파티 · 공연 · 대회 (FR-150~FR-159)

- **FR-150**: 시스템은 전 학원의 파티·공연·대회를 하나의 피드로 통합 노출해야 한다.
- **FR-151**: 시스템은 장르별·날짜별·지역별로 파티를 검색하도록 해야 한다.
- **FR-152**: 시스템은 파티 참가 신청과 결제를 처리해야 한다.
- **FR-153**: 시스템은 외부 예매가 필요한 공연에 대해 예매 링크로 연결하고 내부 결제를 요구하지 않아야 한다.
- **FR-154**: 시스템은 관심 등록한 파티·공연의 일정 확정·변경을 알림으로 전달해야 한다.
- **FR-155**: 시스템은 파티·공연·대회마다 주최자를 표시해야 한다. 학원 외 개인·동호회가 주최자로 등록할 수 있는지는 Q9(파티 주최 주체)가 정해지면 확정한다. **[정의서 근거 — 2026-09-25 이관]**
- **FR-156**: 시스템은 대회 참가 신청에서 종목·부문·파트너 정보를 받아야 한다. 파티 참가 신청과 같은 양식을 쓰지 않는다. **[신규 2026-09-25]**
- **FR-157**: 시스템은 공연 상세에 출연자와 장르를 표시해야 한다. **[정의서 근거 — 2026-09-25 이관]**

#### 레벨 · 출석 · 분석 (FR-160~FR-174)

- **FR-160**: 시스템은 강사가 세부 장르별로 수강생 레벨을 0~10 범위에서 부여하도록 해야 한다.
- **FR-161**: 시스템은 레벨 등급을 구간으로 해석해야 한다 — 0~1 입문, 2~3 초급, 4~7 중급, 8~10 고급.
- **FR-162**: 시스템은 결제를 완료한 수강생에 한해 해당 강사가 레벨을 부여·수정하도록 제한해야 한다. 무료 수업은 신청이 확정된 수강생을 결제 완료와 같게 본다(2026-09-25 보완 — 정의서 3장 「무료·유료」 근거).
- **FR-163**: 시스템은 수강 이력·장르·세부장르·출석률을 바탕으로 개인별·단체별 레벨 분포를 시각적으로 제공해야 한다.
- **FR-164**: 시스템은 강사가 개강 조건(장르·레벨대·요일·시간·정원)을 제시하면 적합한 수강생 후보와 선정 근거를 제시해야 한다.
- **FR-165**: 시스템은 후보 명단의 연락처를 수강생이 제공에 동의한 경우에만 노출해야 하며, 조회 사실을 기록으로 남겨야 한다. **[신규 — 개인정보 보호 보완]**
- **FR-166**: 시스템은 출석 확인을 통신이 불안정한 환경에서도 가능한 수단으로 제공해야 한다. **[신규]**
- **FR-167**: 시스템은 반복적인 노쇼(무단 불참)를 기록하고 대기 승계 우선순위에 반영해야 한다. **[신규]**
- **FR-168**: 시스템은 강사 화면에 수강생의 나이를 그대로 보여주지 않고 연령대(예: 20대)로 보여줘야 한다. 정확한 나이는 법정대리인 동의 판정(FR-009(미성년자 결제 차단))처럼 시스템 판정에만 쓴다. **[신규 2026-09-25]**

#### 커뮤니티 · 문의 (FR-175~FR-184)

- **FR-175**: 시스템은 사용자가 수강·참여 이력을 조회하도록 해야 한다.
- **FR-176**: 시스템은 사용자 문의(Q&A) 접수와 답변을 제공해야 한다. 상세는 「사용자 문의 · AI 응답」 묶음(FR-200~)에 있다.
- **FR-177**: 시스템은 수업 후기를 작성·조회하도록 해야 하며, 실제 수강 이력이 있는 경우에만 작성을 허용해야 한다. **[신규 — 후기 신뢰성]**
- **FR-178**: 시스템은 크루·동호회 단위로 묶어 단체 신청을 받을 수 있어야 한다. **[신규]**

#### 사용자 문의 · AI 응답 (FR-200~FR-229)

**설계의 출발점은 제약이다.** 기존 문서는 GPU 1대의 동시 처리를 "체감상 1~4건" 으로
추정했다(`docs/kdance-beta-infra.html`). 2026-09-24 에 이 노트북에서 실측해 보니 구성에
따라 동시 10명의 답 완료 시간이 **55초(한 건씩 처리)와 18초(10건 병렬)** 로 갈렸다
(`local-ai-capacity.md`). 병렬로 돌려도 모델은 여전히 가장 비싼 자원이라, 모든 질문을
모델에 보내면 사용자 수가 늘 때 대기열이 먼저 밀린다. 그래서 이 묶음은 **"질문을 네 갈래로 나눠 대부분을 모델 없이
처리한다"** 를 전제로 한다.

##### 질문 분류와 경로 (FR-200~FR-209)

- **FR-200**: 시스템은 들어온 질문을 네 등급으로 분류해 서로 다른 경로로 처리해야 한다.

  | 등급 | 무엇을 묻는가 | 어떻게 답하는가 | 모델 사용 |
  |---|---|---|---|
  | `T0(내 데이터 조회)` | 내 예약·결제·환불액·일정·대기 순번·정산 | 저장된 값과 도메인 계산 결과를 그대로 읽어준다 | 쓰지 않음 |
  | `T1(정해진 지식)` | 약관·환불 정책·요금제·학원 정보·자주 묻는 질문 | 승인된 답변을 찾아 제시한다 | 검색만, 생성 없음 |
  | `T2(판단이 필요한 질문)` | 무엇부터 배울지, 일정을 어떻게 짤지 같은 복합 질문 | 멀티에이전트가 답을 만든다 | 사용 |
  | `T3(사람)` | 결제·환불 분쟁, 개인정보, 신고, 그리고 위 셋이 확신하지 못한 것 | 문의자가 **검색해서 고른 업주**에게 알림이 가고 업주가 답한다. 앱·웹 시스템 문의만 운영자가 받는다(2026-09-25 변경) | 쓰지 않음 |

- **FR-201**: 시스템은 결제·환불 분쟁, 개인정보, 신고, 미성년자 관련 문의를 **모델에 보내지 않고** 곧바로 사람에게 배정해야 한다.
- **FR-202**: 시스템은 답변 신뢰도가 기준에 못 미치면 추측해 답하지 않고 사람에게 이관해야 하며, 이관 사실을 사용자에게 알려야 한다.
- **FR-203**: 시스템은 사람에게 가는 문의를 **문의자가 검색해서 고른 업주**에게 보내야 한다. 문의자는 문의 화면에서 학원이나 수업을 검색하거나 자기 예약에서 고르고 그 학원의 업주가 받는 사람으로 정해지면 업주에게 알림이 간다. 결제·환불·수강 규정·수업 운영·출석·레벨 문의가 모두 이 경로다. 개인 레슨도 그 레슨에 지정된 소속 학원의 업주가 받는다. 환불 요청은 담당 강사에게도 확인 알림이 간다(FR-098b(환불 요청 경로)). (2026-09-25 변경 — 운영자는 시스템만, 사람 문의는 업주)

  | 문의 내용 | 받는 사람 |
  |---|---|
  | 학원·수업에 관한 모든 문의 (결제·환불·수강 규정·운영·보강·정원·출석·레벨) | **문의자가 고른 학원의 업주** |
  | 개인 레슨에 관한 문의 | **그 레슨의 소속 학원 업주** |
  | 앱·웹 시스템 문의 (계정·로그인·앱 오류·개인정보 삭제·신고·결제 시스템 장애) | 운영자 |
  | 구독(월·연) 결제·해지·환불 — 플랫폼 상품(FR-112b(구독은 플랫폼 상품)) | 운영자 (2026-09-25 추가) |

- **FR-203a**: 시스템은 AI 가 답하지 못해 사람에게 넘길 때(FR-202(저신뢰 이관)·FR-208(불만족 이관)) 학원에 관한 질문이면 **업주를 고르는 화면**으로, 시스템에 관한 질문이면 운영자 문의로 넘겨야 한다. 대화 맥락은 그대로 따라간다. **[신규 2026-09-25]**
- **FR-204**: 시스템은 운영자를 **앱·웹 시스템 관리자**로만 두어야 한다. 운영자는 FR-203(업주 선택 문의) 표의 시스템 문의만 받고 학원 문의의 2차 조정자가 되거나 업주가 답하지 않은 문의를 대신 받지 않는다. (2026-09-25 변경 — 운영자는 시스템만, 사람 문의는 업주) 예외는 **구독(FR-112b(구독은 플랫폼 상품))** 하나다 — 플랫폼이 판매자인 상품이라 구독의 결제·해지·환불 문의는 운영자가 받는다(2026-09-25). 플랫폼 관리자는 이와 별개로 **플랫폼 정산 콘솔**(FR-300~FR-319(역할별 로그인 분기 ~ 기준 시각·월 마감))을 쓴다 — 조회와 수수료율 설정만 하고 학원 문의·분쟁은 다루지 않는다.
- **FR-205**: 시스템은 환불 문의에 답할 때 그 학원의 환불 규정을 근거로 안내하고, 환불 여부와 금액은 학원이 정한다는 점을 함께 밝혀야 한다. 플랫폼 공통 환불 규칙은 두지 않는다. (2026-09-25 변경)
- **FR-206**: 시스템은 환불 관련 답변에 **그 학원이 등록한 환불 규정**을 근거로 제시해야 한다. 다른 학원의 정책이나 일반론으로 답하지 않으며 규정에 없는 금액을 확정해 말하지 않는다. (2026-09-25 변경)
- **FR-207**: 시스템은 학원이 자기 학원에 들어온 문의만 조회·응답하도록 제한해야 한다. 다른 학원의 문의는 볼 수 없다.
- **FR-208**: 시스템은 사용자가 답변에 만족하지 못했다고 표시하면, **대화 맥락을 그대로 유지한 채** 사람에게 이관해야 한다. 같은 내용을 다시 쓰게 하지 않는다.
- **FR-209**: 시스템은 사용자가 언제든 사람 응대를 직접 요청할 수 있게 해야 한다. AI 응답을 거쳐야만 사람에게 닿는 구조를 만들지 않는다.
- **FR-209a**: 시스템은 강사의 운영 문의(정산 금액 근거·정원·출석)를 소속 학원의 업주에게, 업주의 시스템 문의를 운영자에게 보내야 한다. (2026-09-25 변경 — 운영자는 시스템만, 사람 문의는 업주)

##### 답변의 정확성 (FR-210~FR-219)

이 절이 이 묶음에서 가장 중요하다. **돈이 걸린 질문에 틀린 답을 하면 그 자체가 분쟁이 된다.**

- **FR-210**: 시스템은 금액·일시·정원·순번 같은 **수치를 모델이 생성하지 않아야 한다.** 도메인 로직이 산출한 값을 그대로 끼워 넣는다.
- **FR-211**: 시스템이 안내하는 환불 예상액은 취소 미리보기가 계산한 금액과 **원 단위까지 일치**해야 한다. 두 경로가 각자 계산하지 않는다.
- **FR-212**: 시스템은 답변의 모든 사실 주장에 근거(정책 항목 또는 데이터 출처)를 붙여야 하며, 근거가 없는 문장은 답변에 포함하지 않아야 한다.
- **FR-213**: 시스템은 실제 데이터에 없는 수업·강사·학원·이벤트를 답변에 포함하지 않아야 한다.
- **FR-214**: 시스템은 답변 생성 과정에서 **쓰기 동작을 수행하지 않아야 한다.** 예약·취소·환불·결제를 AI 가 실행하지 않으며, 해당 화면으로 가는 버튼을 제시하는 데까지만 한다.
- **FR-215**: 시스템은 질문자가 볼 권한이 없는 데이터를 답변에 포함하지 않아야 한다. 강사가 다른 강사의 정산을 묻더라도 답하지 않는다.
- **FR-216**: 시스템은 각 답변에 대해 어떤 근거로 무엇을 답했는지 기록해야 한다. 분쟁 시 되짚을 수 있어야 한다.
- **FR-217**: 시스템은 답할 수 없을 때 "모른다"고 답해야 한다. 그럴듯한 추측으로 채우지 않는다.

##### 부하와 비용 (FR-220~FR-224)

- **FR-220**: 시스템은 `T0(내 데이터 조회)`·`T1(정해진 지식)` 질문을 모델을 거치지 않고 처리해, 모델 호출이 전체 질문의 일부에만 발생하도록 해야 한다.
- **FR-221**: 시스템은 모델 응답이 밀릴 때 순서와 예상 대기 시간을 표시하고, 기다리지 않고 사람 문의로 전환하는 선택지를 함께 제시해야 한다.
- **FR-222**: 시스템은 사용자당 모델 사용량 한도를 두어야 하며, 한도 초과 시에도 `T0`·`T1`·`T3` 경로는 계속 동작해야 한다.
- **FR-223**: 시스템은 부하가 임계를 넘으면 `T2(판단이 필요한 질문)` 를 일시적으로 끄고 나머지 경로로 운영하는 **저하 모드**를 제공해야 한다. 서비스 전체가 멈추지 않아야 한다.
- **FR-224**: 시스템은 같은 취지의 질문에 대한 답변을 재사용해야 한다. 정책 질문처럼 답이 고정된 것은 매번 생성하지 않는다.

##### 지식이 쌓이는 구조 (FR-225~FR-229)

- **FR-225**: 시스템은 반복되는 질문을 모아 **자주 묻는 질문 후보**로 제시해야 한다.
- **FR-226**: 시스템은 승인된 답변만 — 학원에 관한 답변은 그 업주가, 앱·약관에 관한 답변은 운영자가 승인한 것만 — `T1(정해진 지식)` 지식으로 등록해야 한다. 모델이 만든 답이 검토 없이 지식이 되지 않아야 한다.
- **FR-227**: 시스템은 승격된 지식에 유효 기간 또는 재검토 시점을 두어, 정책이 바뀌었는데 옛 답변이 계속 나가는 일을 막아야 한다.
- **FR-228**: 시스템은 정책·요금·환불 규정이 변경되면 그에 연결된 지식 항목을 **재검토 대상으로 표시**해야 한다.
- **FR-229**: 시스템은 사람이 답한 내용도 지식 후보로 수집해야 한다.

##### 출시 요건 (FR-230~FR-232)

- **FR-230**: 시스템은 앱 안에서 고객 문의 창구에 닿는 경로를 제공해야 한다. **AI 층이 전부 꺼져 있어도 이 경로는 동작해야 한다.**
- **FR-231**: 시스템은 문의에 대한 응답 소요 시간 기준을 사용자에게 고지해야 하며, 응대 시간 밖에 접수된 문의에는 언제 답변되는지 안내해야 한다.
- **FR-232**: 시스템은 문의 이력을 사용자가 다시 열어볼 수 있게 보관해야 한다.

#### 약관 · 고지 (FR-240~FR-249)

- **FR-240**: 시스템은 회사가 **통신판매중개자**이며 수업의 판매 당사자가 아님을 약관과 거래 화면에 고지해야 한다.
- **FR-241**: 시스템은 각 학원의 결제·환불 정책을 **결제 전에** 그 학원 화면에 표시해야 한다.
- **FR-242**: 시스템은 표시된 정책과 학원의 실제 운영이 다를 경우 **표시된 내용**이 회원에게 적용되도록 해야 한다.
- **FR-243**: 시스템은 약관 변경 시 적용일 전에 공지해야 하며, 회원에게 불리한 변경은 더 긴 기간을 두고 앱 알림으로 개별 통지해야 한다.
- **FR-244**: 시스템은 약관의 각 판본과 적용 기간을 보관하고, 회원이 **자신이 동의한 판본**을 다시 확인할 수 있게 해야 한다.
- **FR-245**: 시스템은 **결제 시점의 약관과 정책**을 그 거래에 적용해야 한다. 이후 변경된 기준을 소급 적용하지 않는다.
- **FR-246**: 시스템은 환불 규정을 등록하지 않은 학원의 수업 게시를 막아야 한다(FR-099(환불 규정 등록·표시)). 규정 없이 결제가 일어나지 않게 하기 위해서다. (2026-09-25 변경)
- **FR-247**: 시스템은 자동 응답이 **확정된 계약 내용이 아님**을 고지해야 하며, 결제 화면과 학원이 표시한 정책이 우선함을 밝혀야 한다.
- **FR-248**: 시스템은 사업자 정보·고객센터·개인정보 보호책임자를 앱 안에서 확인할 수 있게 해야 한다.
- **FR-249**: 시스템은 회원이 동의한 약관 항목과 동의 시각을 기록해야 한다.

#### AI 에이전트 동시 사용 · 로컬 운영 (FR-260~FR-279)

**2026-09-24 신설.** 시험 단계(S0)는 노트북 1대에서 시험자 1명이 AI 동시 사용자 최대 10명을 흉내 낸다. 이 묶음은 그 조건에서 **자원을 최대로 쓰되 사용자에게는 순서·진행·신뢰가 보이게** 하는 요구사항이다. 수치 근거는 `local-ai-capacity.md` 다.

##### 동시성과 공정성 (FR-260~FR-265)

- **FR-260**: 시스템은 판단형(`T2`) 질문을 **최소 10건 동시에** 처리해야 한다. 한 건씩 줄 세워 처리하는 구성은 S0 통과 조건(SC-041(동시 10명 15초·25초))을 만족하지 못한다. **[신규 — 실측 F1·F2]**
- **FR-261**: 시스템은 동시 처리 한도를 넘는 판단형 질문을 **거부하지 않고 대기열에 넣어** 순번과 예상 대기 시간을 보여야 한다. 대기열 길이에도 상한을 두고, 넘으면 사람 문의 접수(FR-209(사람 응대 요청))로 안내한다. **[신규]**
- **FR-262**: 시스템은 답을 **만들어지는 대로 조금씩** 보여 줘야 하며, 첫 내용이 나오기 전에는 지금 단계(조건 분석·후보 찾기·답 작성)를 표시해야 한다. 빈 화면으로 기다리게 하지 않는다. **[신규]**
- **FR-263**: 시스템은 사용자가 대기 중이거나 생성 중인 질문을 취소하게 해야 하며, 취소된 질문은 즉시 처리 자원을 돌려줘야 한다. **[신규]**
- **FR-264**: 시스템은 사용자 한 명이 동시에 **판단형 질문 1건**만 진행하게 해야 한다. 답을 받기 전에 새 질문을 보내면 앞 질문을 자동 취소한다. **[신규 — 한 사람이 10자리를 다 쓰는 것을 막는다]**
- **FR-265**: 시스템은 사용자가 기다리는 대화 응답을 **배경 작업보다 먼저** 처리해야 한다. 포스터 자동 추출(FR-073(포스터 자동 추출))·검색 색인 갱신·요약 같은 배경 작업은 대화 부하가 있을 때 뒤로 밀리며, 대화 응답 시간 기준(SC-041(동시 10명 15초·25초))을 깨지 않아야 한다. 검색용 벡터 계산·재정렬도 대화 생성과 같은 자원을 두고 다투지 않게 배치한다. **[신규 — 실측 F7]**

##### 답의 품질 (FR-266~FR-270)

- **FR-266**: 시스템은 AI 답을 **한국어로만** 내보내야 한다. 한국어가 아닌 문자(한자 등)가 섞인 답은 내보내기 전에 걸러 다시 만들고, 두 번 실패하면 필터 검색 결과(FR-041(추천 시간 초과 대체))로 대체한다. 고유명사·장르명의 로마자 표기는 예외다. **[신규 — 실측 F4]**
- **FR-267**: 시스템은 답에 **입력 데이터에 없는 사실**(거리·이동 시간·가격·잔여석·운영 여부)이 들어가지 않게 해야 한다. 이런 주장은 내보내기 전에 규칙으로 검사해 제거하거나 다시 만든다. 이 검사는 모델의 자기 검토에 맡기지 않는다. **[신규 — 실측 F3, FR-210(수치 생성 금지)·FR-213(없는 항목 답변 금지) 의 구체화]**
- **FR-268**: 시스템은 판단형 질문 1건이 부르는 **모델 호출 횟수와 맥락 길이에 상한**을 둬야 한다(기준: 호출 2회 — 조건 분해 1회·답 작성 1회). 후보 검증(FR-038(추천 후보 검증))은 모델 호출 없이 규칙으로 한다. 상한을 넘는 긴 대화는 요약하거나 오래된 부분부터 잘라낸다. **[신규 — 실측 5절·F6]**
- **FR-269**: 시스템은 같은 대화 안의 후속 질문("그럼 일요일은?")이 앞 조건을 이어받게 해야 한다. 대화 맥락은 정해진 시간 동안만 유지하고, 새 대화에서는 이어받지 않는다. **[신규]**
- **FR-270**: 시스템은 사용자가 올린 글·포스터·후기에 들어 있는 지시문을 **명령이 아니라 데이터**로 다뤄야 한다. 그 안의 문장이 권한·필터·검증을 바꾸지 못한다. **[신규 — FR-215(권한 밖 데이터 차단) 의 보강]**

##### 대화형 확인과 역할별 질문 (FR-271~FR-273)

- **FR-271**: 시스템은 AI 가 화면 이동이나 명단 출력을 제안할 때 **사용자의 명시적 확인(예/아니오)** 을 받은 뒤에만 진행해야 한다. 이동한 화면에서 신청·결제는 사용자가 직접 한다(FR-214(AI 쓰기 금지)). **[신규 — 정의서 7장 Writer 예시의 "Y/N" 전환]**
- **FR-272**: 시스템은 강사의 수강생 후보 추천(FR-164(개강 후보 추천)) 뒤에 명단 출력 여부를 묻고, 출력 시 **연락처 제공에 동의한 수강생만** 이름·연락처를 보여야 한다(FR-165(후보 연락처 동의)). **[신규 — 정의서 3.4 예시]**
- **FR-273**: 시스템은 학원 정보 질문("이 학원 시간표 알려줘", "이번 주 월요일반 정상 운영해?") 을 모델 생성 없이 저장된 운영시간·시간표·휴강 정보로 답해야 한다(`T0`·`T1`). **[신규 — 정의서 4.2]**

##### 측정과 운영 (FR-274~FR-279)

- **FR-274**: 시스템은 AI 질문마다 등급(`T0`~`T3`)·대기 시간·첫 내용 표시 시간·완료 시간·모델 호출 수·취소 여부·이관 여부를 기록해야 한다. 질문 본문의 개인정보는 가린 뒤 기록한다(엣지 케이스 「문의와 응답」). **[신규]**
- **FR-275**: 시스템은 운영자에게 최근 1시간의 AI 응답 시간(중앙값·95번째 백분위)·대기열 길이·저하 모드 여부를 보여야 한다. **[신규]**
- **FR-276**: 시스템은 **고정 평가 세트**(등급별 질문과 기대 답·금지 답, 최소 50문항)를 갖추고, 모델·설정·AI 지시문을 바꿀 때마다 돌려 SC-044(비한국어 답 0건)·SC-045(없는 사실 주장 0건) 통과를 확인해야 한다. 통과하지 못한 변경은 반영하지 않는다. **[신규 — 정의서 20장 Phase 6(AI 고도화) 「Agent 평가」의 앞당김]**
- **FR-277**: 시스템은 동시 1명·5명·10명 부하 시험을 **같은 절차로 반복 실행**할 수 있어야 하며, 결과에 측정 시각과 장비 전원 상태를 함께 남겨야 한다. **[신규 — 재현 수단은 `infra/ai-bench/`]**
- **FR-278**: 시스템은 모델 서버가 멈추거나 응답하지 않으면 이를 감지해 판단형 경로를 저하 모드(FR-223(저하 모드))로 전환하고, 복구되면 사람 개입 없이 되돌려야 한다. 진행 중이던 질문은 실패로 끝내지 않고 재시도하거나 대체 답으로 마무리한다. **[신규]**
- **FR-279**: 시스템은 시간이 오래 걸리는 심층 추론 방식을 기본으로 쓰지 않아야 한다. 응답 시간 기준(SC-040(혼자 3초·8초)·SC-041(동시 10명 15초·25초))을 지키는 것이 기본이고, 심층 추론은 평가 세트(FR-276(고정 평가 세트))에서 효과가 확인된 질문 유형에만 켠다. **[신규 — 실측 F5]**

#### 운영 · 감사 · 개인정보 (FR-185~FR-199)

- **FR-185**: 시스템은 결제·환불·개인정보 관련 조작에 대해 수행자·시각·대상·변경 전후 값을 감사 기록으로 남겨야 한다.
- **FR-186**: 시스템은 위치 정보를 저장하지 않고 요청 시점에만 사용해야 한다.
- **FR-187**: 시스템은 수강생 연락처를 기본적으로 마스킹해 표시하고, 전체 열람 시 사유와 열람자를 기록해야 한다. **[신규]**
- **FR-188**: 시스템은 신고 접수와 처리 흐름을 제공해야 한다.
- **FR-189**: ~~시스템은 환불 분쟁에 대한 운영자 조정 결과를 양측에 통지하고 정산에 반영해야 한다.~~ **삭제 (2026-09-25 변경 — 환불 요청은 업주만).** 번호는 재사용하지 않는다.
- **FR-190**: 시스템은 사용자가 자신의 데이터 삭제를 요청할 수 있게 하고, 법정 보관 의무가 있는 거래 기록과 구분해 처리해야 한다. **[신규]**

### Key Entities

- **User(사용자)**: 사람 단위 계정. 본인확인 정보, 역할 집합(Dancer/Instructor/Owner/Admin), 대학생 인증 상태, 취향, 역할 선호(리드/팔로우), 알림 설정을 갖는다.
- **Academy(학원)**: 지점·주소·운영시간·시설 정보, **등록 형태·증빙·업종코드**(2026-09-25 추가, FR-085(학원 등록 형태·증빙))와 **환불 규정**(2026-09-25 변경, 이전: 환불 비율표)을 보유한다. 소속 강사·강의실·수업의 상위 단위다. *(구현됨)*
- **Room(강의실)**: 학원에 속한 물리 공간. 같은 시간대 중복 배정 금지의 판정 단위다.
- **Instructor(강사)**: 프로필·장르·경력·활동 학원 목록. 여러 학원에 동시에 속할 수 있다.
- **Class(수업) / ClassSchedule(수업 회차)**: 수업의 정의와 개별 회차. 회차가 일시·장소·정원·신청 인원·수강료를 갖는다. *(구현됨 — 역할별 정원은 미반영)*
- **Reservation(예약)**: 한 사람의 한 회차에 대한 자리. 상태는 대기 중(held)·확정(confirmed)·취소(cancelled). *(구현됨)*
- **Waitlist(대기)**: 정원이 찬 회차에 대한 순번. 승계 시각과 응답 기한을 갖는다.
- **Order(주문)**: 결제 단위. 상태는 미결제(pending)·결제완료(paid)·환불(refunded). *(구현됨)*
- **Payment(결제)**: 주문에 대한 실제 결제 원거래. 수단(가상계좌/카드), 금액, 결제 시각, 결제대행사 식별자. *(구현됨)*
- **Refund(환불)**: 예약 취소에 따른 환불. 멱등키, 산정 금액, 적용 비율(만분율), 상태, 실패 사유. *(구현됨)*
- **RefundEvent(환불 감사 로그)**: 환불의 상태 전이를 추가만 하는 기록. *(구현됨)*
- **Coupon(쿠폰)**: 발급 시각, 유효기간, 사용 여부, 사용된 예약, 양도 불가 속성.
- **StudentBenefit(대학생 혜택)**: 인증 시각, 첫 결제 50% 할인 사용 여부와 사용한 결제 (2026-09-25 변경).
- **Attendance(출석)**: 회차별 참석·불참 기록. 노쇼·분쟁 판정의 근거다. 정산 단계 전이의 트리거는 아니다. 수업 종료 후 수정하면 사유가 남는다.
- **SkillLevel(레벨)**: 수강생 × 세부장르 × 부여 강사 × 시각. 이력으로 쌓인다.
- **Event(파티·공연·대회)**: 유형, 예약 가능 여부, 일정, 장소, 주최자, 외부 예매 링크.
- **Notification(알림)**: 대상, 유형, 발송 시각, 확인 여부, 실패 이력.
- **Settlement(학원 정산)**: 학원 × 기간. 총 결제액, 환불액, 수수료, 실지급액, 쿠폰 사용 건수.
- **InstructorPayout(강사 정산)**: 강사 × 기간. 보류분·예정분·완료분·조정분·공제 항목·실지급액. 학원 수업분과 개인 레슨분을 구분해 담는다. 급여가 아니라 **수업 이행에 대한 정산**이다.
- **PayoutHold(정산 보류분)**: 결제는 됐지만 아직 수업이 시작되지 않은 금액.
- **PayoutSchedule(정산 예정분)**: 수업이 시작되어 정산이 예정된 금액. 금액은 보이되 아직 나가지 않는다.
- **PayoutAdjustment(정산 조정)**: 수업 취소·수강생 취소로 생긴 증감. 어느 정산 주기에 반영됐는지 남는다.
- **InstructorPayoutAccount(강사 전용 계좌)**: 정산금이 실제로 나가는 계좌. 강사 1인당 전용이며 정산 이력이 이 계좌에 묶인다.
- **AcademyLedgerEntry(학원 정산 원장)**: 학원 × 주문 단위의 금액 변화 한 줄. 항목 종류(판매·판매 수수료·고객 환불·취소 수수료·취소 수수료 배분·판매 수수료 환급·카드 수수료·PG 결제 수수료·환불 PG 수수료·쿠폰·대학생 할인 부담·조정), 업주 기준 금액(원 단위 정수, +/−), 적용 수수료율, 발생 시각, 정산 주기, 원인 이벤트. 추가만 하고 고치거나 지우지 않는다(FR-125e(취소 수수료 5:5·판매 수수료 5%)). *(2026-09-25 신설)*
- **AuditLog(감사 기록)**: 수행자, 시각, 대상, 변경 전후. 수정·삭제 불가.
- **Inquiry(문의)**: 하나의 문의 건. 질문자, 대상(플랫폼/학원), 분류 등급, 상태, 접수·종결 시각.
- **InquiryMessage(문의 대화)**: 문의 안의 주고받은 말. 누가(사용자/AI/운영자/학원 관리자) 썼는지 구분한다.
- **AnswerEvidence(답변 근거)**: 답변 문장이 어떤 정책 항목 또는 어떤 데이터에 근거했는지. 분쟁 시 되짚는 자리다.
- **KnowledgeEntry(승인된 지식)**: `T1(정해진 지식)` 경로가 쓰는 답변. 승인자, 유효 기간, 재검토 시점, 연결된 정책을 갖는다.
- **Escalation(이관)**: 사람에게 넘긴 기록. 사유(저신뢰·민감·사용자 요청·불만족·학원 무응답)와 배정 대상.
- **TermsVersion(약관 판본)**: 약관의 한 판본. 본문, 적용 시작일, 종료일.
- **TermsConsent(약관 동의)**: 누가 어느 판본의 어느 항목에 언제 동의했는지.
- **AgentConversation(AI 대화)**: 한 사용자의 AI 대화 묶음. 이어받을 조건, 유지 기한, 진행 중인 질문(최대 1건)을 갖는다. *(2026-09-24 신설)*
- **AgentRunMetric(AI 응답 측정)**: 질문 1건의 등급·대기 시간·첫 내용 표시 시간·완료 시간·모델 호출 수·취소·이관 여부. 개인정보는 가린다. *(2026-09-24 신설)*
- **EvaluationCase(평가 문항)**: 평가 세트의 한 문항. 질문, 등급, 기대 답의 요건, 나오면 안 되는 내용(지어낸 사실·다른 언어), 최근 통과 여부. *(2026-09-24 신설)*

## Success Criteria *(mandatory)*

### 기능 완결성

- **SC-001**: 신규 사용자가 앱 설치부터 첫 수업 결제 완료까지 5분 안에 끝낼 수 있다.
- **SC-002**: 강사가 수업 하나를 등록해 공개하기까지 3분 안에 끝낼 수 있다.
- **SC-003**: 업주가 포스터 1장을 올려 게시 완료하기까지 2분 안에 끝낼 수 있고, 자동 추출된 항목 중 손으로 고쳐야 하는 항목이 평균 2개 이하다.
- **SC-004**: 사용자의 90%가 첫 시도에 원하는 수업을 찾아 예약까지 도달한다.

### 정합성 — 돈과 자리

- **SC-005**: 정원을 초과한 예약 확정이 **0건**이다. 동시 신청 부하 시험에서도 마찬가지다.
- **SC-006**: 결제 요청 금액과 최종 기록 금액의 불일치가 **0건**이다.
- **SC-007**: 같은 취소 요청이 중복 도착했을 때 중복 환불이 **0건**이다.
- **SC-008**: 같은 강의실·같은 시각에 두 수업이 게시된 사례가 **0건**이다.
- **SC-009**: 한 강사가 같은 시각 두 수업에 배정된 사례가 **0건**이다.
- **SC-010**: 환불 금액이 결제 금액을 초과한 사례가 **0건**이다.
- **SC-010a**: 수업 기간이 끝나지 않은 건이 정산 완료로 지급된 사례가 **0건**이다.
- **SC-010b**: 각 기간의 (완료분 + 예정분 + 보류분 + 환불분 ± 조정분)이 그 기간 결제 총액과 정확히 일치한다. 차이가 나는 금액이 **0원**이다.
- **SC-010c**: 강사가 다른 강사의 정산을 조회할 수 있었던 사례가 **0건**이다.

### 신뢰성 — 추천과 알림

- **SC-011**: 추천 결과에 실제로 존재하지 않는 수업·강사·파티가 포함된 사례가 **0건**이다.
- **SC-012**: 추천 결과의 95%가 사용자가 지정한 시간·거리 제약을 위반하지 않는다.
- **SC-013**: 수업 전 알림이 설정한 시점 기준 ±1분 이내에 도착하는 비율이 99% 이상이다.
- **SC-014**: 수업 변경·휴강 알림이 변경 저장 후 1분 이내에 전체 예약자에게 도달한다.

### 성능 · 규모

- **SC-015**: 검색 결과가 사용자 체감상 즉시 표시된다 — 95%의 검색이 1초 안에 결과를 보여준다.
- **SC-016**: 인기 수업 오픈 시점에 동시 신청이 몰려도 정원 초과나 중복 확정 없이 처리된다.
- **SC-017**: 가입자 1만 명 규모(S3 운영 목표, 3년 이후)에서 검색·예약 흐름이 성능 저하 없이 동작한다. *(2026-09-24 두 번 수정 — ① 기존 "동시 사용자 10만 명" 은 가입자 규모를 동시 접속으로 잘못 옮긴 표현이었다 ② 같은 날 규모 목표가 10만 명에서 1만 명으로 바뀌었다. 이 목표는 노트북 단계(S0)의 판정 대상이 아니다)*
- **SC-018**: 서비스 가용성이 월 99.5% 이상이다.

### S0 로컬 운영 — 노트북 1대 · AI 동시 사용자 10명 *(2026-09-24 신설)*

수치의 근거는 `local-ai-capacity.md` 3절 실측이다. "첫 내용" 은 사용자 화면에 답의 첫 글자가 보이는 시점, "완료" 는 답이 끝난 시점이다. 측정은 AC 전원에서 한다.

- **SC-040**: 혼자 쓸 때 판단형 질문의 첫 내용이 **3초 안에**, 답 완료가 **8초 안에** 보인다. *(실측 2.8초 / 5.7초)*
- **SC-041**: 10명이 같은 순간에 판단형 질문을 보내도 95%가 첫 내용을 **15초 안에**, 답 완료를 **25초 안에** 받는다. *(실측 12.4초 / 18.0초 — 한 건씩 처리하는 구성은 50.2초 / 55.4초라 통과하지 못한다)*
- **SC-042**: 판단형 질문 10건이 처리되는 중에도 내 데이터 조회·정해진 지식 질문(`T0`·`T1`)의 95%가 **1초 안에** 답을 받는다.
- **SC-043**: 동시 10명 부하 시험에서 오류로 끝난 질문이 **0건**이다. 11번째 이후 질문은 **1초 안에** 대기 순번을 받는다.
- **SC-044**: 평가 세트에서 한국어가 아닌 문장(한자 등)이 섞인 답이 **0건**이다.
- **SC-045**: 평가 세트에서 입력 데이터에 없는 사실(거리·가격·잔여석·존재하지 않는 수업)을 주장한 답이 **0건**이다.
- **SC-046**: 사용자가 판단형 질문을 보낸 뒤 **1초 안에** 진행 단계 표시나 대기 순번 중 하나가 화면에 나타난다.
- **SC-047**: 배경 작업(포스터 추출 등)이 도는 동안 측정해도 SC-041(동시 10명 15초·25초) 을 만족한다.
- **SC-048**: 모델 서버를 강제로 멈췄을 때 **30초 안에** 저하 모드로 전환되고, 그동안 `T0`·`T1`·`T3` 질문은 모두 답을 받는다. 서버가 돌아오면 사람 개입 없이 판단형 경로가 복구된다.

### 사업 성과

- **SC-019**: 베타 종료 시점에 입점 학원 대비 실제로 수업을 게시한 학원 비율이 80% 이상이다.
- **SC-020**: 대학생 인증 사용자가 첫 결제 할인 뒤 정상가 수업을 다시 결제하는 비율이 30% 이상이다 (2026-09-25 변경).
- **SC-021**: 첫 수업을 들은 사용자 중 30일 안에 두 번째 수업을 결제하는 비율이 40% 이상이다.
- **SC-022**: 예약·결제 관련 문의가 전체 결제 건수의 2% 미만이다.
- **SC-022a**: 강사가 자기 정산 금액을 확인하기까지 앱 진입 후 3번 이하의 이동으로 도달한다.
- **SC-022b**: 정산 금액에 대한 강사 이의 제기가 정산 건수의 1% 미만이다.

### 플랫폼 정산 콘솔 *(2026-09-25 신설)*

- **SC-050**: 콘솔의 장르별·학원별·상품별·결제수단별 결산 합계와 전체 결산표 합계가 결제·환불·정산 원장과 다른 금액이 **0원**이다.
- **SC-051**: 콘솔 화면과 내보낸 파일에 수강생 개인정보(이름·연락처·나이)가 나온 사례가 **0건**이다.
- **SC-052**: 수수료율 변경이 이미 결제된 거래에 소급 적용된 사례가 **0건**이다.
- **SC-053**: 수수료율이 오르는 변경을 업주가 적용일 전에 통지받지 못한 사례가 **0건**이다.
- **SC-054**: 관리자가 로그인 후 학원별 결산 상세까지 3번 이하의 이동으로 도달한다.

### 보안 · 개인정보

- **SC-023**: 스토어 출시 시점에 보안 점검 결과 치명(Critical) 등급 발견이 **0건**이다.
- **SC-024**: 소스 코드에 포함된 자격 증명이 **0건**이다.
- **SC-025**: 수강생 연락처 전체 열람 100%에 열람자·사유 기록이 남는다.

### 문의 응답

- **SC-026**: 시스템이 안내한 환불 예상액과 취소 미리보기 금액이 다른 사례가 **0건**이다.
- **SC-027**: 답변에 실제로 존재하지 않는 수업·강사·학원이 포함된 사례가 **0건**이다.
- **SC-028**: 질문자가 볼 권한이 없는 데이터가 답변에 노출된 사례가 **0건**이다.
- **SC-029**: 결제·환불 분쟁과 개인정보 문의가 사람을 거치지 않고 종결된 사례가 **0건**이다.
- **SC-029a**: 환불 문의 답변에 **다른 학원의 정책**이 근거로 쓰인 사례가 **0건**이다.
- **SC-029b**: 학원이 자기 학원 외의 문의를 조회한 사례가 **0건**이다.
- **SC-029c**: 학원·수업에 관한 문의가 업주를 건너뛰고 운영자에게 배정된 사례가 **0건**이다(앱·웹 시스템 문의 제외). *(2026-09-25 변경)*

### 약관과 고지

- **SC-034**: 결제 전에 그 학원의 환불 정책이 표시되지 않은 결제가 **0건**이다.
- **SC-035**: 변경된 약관이 이미 결제된 건에 소급 적용된 사례가 **0건**이다.
- **SC-036**: 회원이 자신이 동의한 약관 판본을 확인하지 못한 사례가 **0건**이다.
- **SC-030**: 전체 질문의 70% 이상이 모델을 거치지 않고(`T0`·`T1`) 처리된다.
- **SC-031**: 사용자가 사람 응대를 요청한 뒤 실제로 배정되기까지 걸리는 시간이 고지한 기준 안에 드는 비율이 95% 이상이다.
- **SC-032**: 답변을 받은 사용자의 70% 이상이 추가 질문 없이 대화를 종료한다.
- **SC-033**: 문의로 접수된 내용 중 반복 질문의 비율이 운영 3개월 시점에 초기 대비 절반 이하로 줄어든다.

## 범위 경계와 출시 단계

### 이번 범위에 포함

사용자·강사·업주 3주체의 수업 거래 전 과정(발견 → 예약 → 결제 → 출석 → **수강 완료 → 정산** / 취소 → 환불), 개인 레슨, 대학생 혜택과 구독 쿠폰, 파티·공연·대회 연결, AI 추천, 운영자 도구.

**돈의 흐름이 두 단계다.** 결제는 수업 전에 일어나지만 정산은 수업이 끝난 뒤에 일어난다. 그 사이 금액은 정산 보류분으로 남는다. 이 구분이 데이터 구조와 화면 양쪽에 그대로 드러나야 한다.

### 이번 범위에서 제외

- **iOS 배포** — Android(갤럭시 스토어) 단일. 정의서·배포 정책과 동일하다.
- **해외 서비스·다국어** — 국내 한국어 단일.
- **강사 급여 관리(월급·시급·근태)** — 강사는 프리랜서라 고용 관계가 없다. 급여 대신 수강 완료분 정산이 그 자리를 대신한다(FR-127(강사 프리랜서)). 근로계약·4대보험·근태 기능은 만들지 않는다.
- **플랫폼 자체 영상 스트리밍** — 소개 영상은 업로드·재생까지, 온라인 수업 실시간 중계는 제외.

역할별 재분석에서 나온 확장 아이디어다. **아직 요구사항이 아니다.** 필요가 확인되면 FR 로 올린다.

### 규모 단계와 통과 조건

사용자 요청의 **"베타 1명~최대 10명, 3년 이후 1천~1만 명 운영"**(2026-09-24 수정)을 단계로 나눈다. 각 단계는 **앞 단계의 통과 조건을 만족해야** 다음으로 간다.

베타가 최대 10명이라 **베타 사용자 수와 S0 의 AI 동시 사용자 수(10명)가 같다.** 즉 베타 기간 전체를 S0 에서 실측한 노트북 수용량 안에서 운영할 수 있다 — 이게 규모 변경이 만든 가장 큰 차이다. 서버 이전은 S2(운영 초기) 로 넘어가기 전에 정한다.

| 단계 | 규모 | 무엇을 확인하나 | 통과 조건 |
|---|---|---|---|
| S0 내부 | **노트북 1대 · 시험자 1명 · AI 동시 사용자 최대 10명** | 거래 한 건이 끝까지 도는가 · AI 가 동시 10명을 감당하는가 | 결제·출석·수강 완료·정산·취소·환불 각 1건이 정합성 지표(SC-005~SC-010b(정원 초과 0건 ~ 정산 합계 일치)) 위반 없이 완료 · **SC-040~SC-048 통과**(시험 데이터 기준) |
| S1 베타 | **실사용자 1~10명** / 학원 1~3곳 | 업주·강사·수강생이 도구를 실제로 쓰는가 | 포스터 자동 등록 성공, 학원이 스스로 수업 게시, **강사가 첫 정산을 이의 없이 수령**, 문의(SC-022(결제 문의율 2% 미만)) 경로 동작 |
| S2 운영 초기 | ~1,000명 / 학원 10곳 (3년 이후 목표의 하한) | 수요·공급이 붙는가 | 재결제율(SC-021(30일 재결제 40%)) 측정, 문의율(SC-022(결제 문의율 2% 미만)) 2% 미만, 정산 이의율(SC-022b(정산 이의 1% 미만)) 1% 미만 |
| S3 운영 목표 | ~10,000명 (3년 이후 목표의 상한) | 부하에서 정합성이 유지되고 운영이 사람 손 없이 도는가 | SC-016(동시 신청)·SC-017(1만 규모) 부하 시험 통과, SC-018(가용성 99.5%)·SC-023(보안 치명 0건) 충족 |

> **S4(10만 명) 단계는 지웠다**(2026-09-24). 규모 목표의 상한이 1만 명으로 내려가 해당 단계가 없어졌다. 그 단계의 통과 조건(SC-018(가용성 99.5%)·SC-023(보안 치명 0건))은 S3 로 옮겼다.

**AI 추천(US6(AI 근거 추천))은 실사용자에게 S1(베타) 에서 게시 수업 데이터가 쌓인 뒤에 켠다.** 추천할 데이터가 없는 상태에서 켜면 사용자에게 빈 결과만 준다. 켜는 기준은 **사용자 수가 아니라 추천할 수업이 있는가**다 — 베타가 최대 10명이라, 인원 기준(예전의 "S2 이후") 을 그대로 두면 핵심 기능이 3년 뒤로 밀린다(2026-09-24 수정). **다만 S0 에서 시험 데이터로 먼저 켜서** 속도·동시성·언어·사실 일치(SC-040~SC-048(혼자 3초·8초 ~ 저하 모드 30초))를 판정한다(2026-09-24 수정). 느리거나 지어내는 구조를 데이터가 쌓인 뒤에 발견하면 고치는 비용이 크다.

**문의(US11(문의 응답·사람 이관))는 계층별로 시점이 다르다.** 전부를 한꺼번에 켜지 않는다.

| 계층 | 언제 |
|---|---|
| `T3(사람)` · `T0(내 데이터 조회)` | **S0 부터** — 출시 게이트다. 이것만 있어도 앱을 올릴 수 있다 |
| `T1(정해진 지식)` | S1 부터 — 반복 질문이 쌓이면 효과가 난다. 베타 인원이 적어 초기에는 업주(학원 정보)와 운영자(앱·약관)가 직접 등록한 항목이 대부분이다 |
| `T2(판단이 필요한 질문)` | 실사용자에게는 **S1 에서 AI 추천과 같은 시점** — 게시 수업 데이터가 쌓인 뒤. S0 에서는 시험 데이터로 켜서 SC-040~SC-048(혼자 3초·8초 ~ 저하 모드 30초) 을 판정한다 |

**정산(US9(수강 완료분 정산))은 P3 이지만 출석은 S0 부터 필요하다.** 강사 정산이 출석 기록으로 수강 완료를 판정하므로(FR-129(정산 시각 전이)), 출석 없이 결제만 먼저 열면 나중에 정산할 근거가 사라진다. 돈을 받는 시점과 정산 근거를 쌓는 시점이 같아야 한다 — 정산 **화면**은 뒤로 미뤄도 되지만 출석 **기록**은 첫 거래부터 남겨야 한다.

## Assumptions

정보가 없어 합리적 기본값으로 정한 것들이다. 다르게 정해야 하면 이 절을 고친다.

1. **서비스 지역·언어** — 국내, 한국어 단일. 정의서의 모든 화면·정책이 국내 전제다.
2. **배포 대상** — Android 단일(갤럭시 스토어). `docs/distribution-policy.md` 확정 사항.
3. **결제대행사** — 포트원을 전제로 설계한다. `docs/payment-method-policy.md`에서 방식 B 의 결제대행사로 확정됐다.
4. ~~**9만원 초과 ~ 10만원 미만 구간** — 방식 B 로 처리~~ — 2026-09-25 에 금액 기준 분기를 없애 해당 없음.
5. **정산 주기** — 매월 5일. 기존 문서 값을 그대로 쓴다. 그달에 **수강이 완료된 분**만 대상이다.
5a. **정산 주체와 창구** — 정산은 **전부 플랫폼 안에서** 확인한다(사용자 확인 2026-09-21). 지급은 강사 전용 계좌로 나간다. 조회 권한은 비대칭이다 — 강사는 본인 것만, 업주는 자기 학원 전체 수업과 소속 강사 전원.
5e. **약관은 검토 전 초안이다** — 회원 이용약관 `docs/terms-of-service.md` 과 입점(학원·강사) 이용약관 `docs/merchant-terms.md`, 개인정보 처리방침 `docs/privacy-policy.md` 에 출시용 초안을 두었다(2026-09-25 — 회원 약관은 17개 조로 압축, 상세 근거판은 `_workspace/terms-archive-2026-09-25/`). 전자상거래법·통신판매중개·전자금융거래법이 걸려 있어 공개 전 변호사 검토가 필요하고, 검토가 필요한 지점 5가지와 미정 값 8개를 문서 말미에 남겼다. 이 spec 의 FR-240~FR-249(통신판매중개자 고지 ~ 약관 동의 기록) 는 **시스템이 갖춰야 할 기능**을 정할 뿐, 약관 문구의 법적 타당성을 보증하지 않는다.
5d. **업주의 개인 레슨 가시성** — 명시되지 않았다. 학원 공간에서 이뤄진 개인 레슨을 업주가 볼 수 있는지는 정하지 않았고, 이 spec 은 개인 레슨을 별도 정산 경로로만 두었다(FR-135a(개인 레슨 별도 정산)). 개인 레슨 상품을 열기 전에 정해야 한다. **2026-09-25 일부 확정** — 개인 레슨의 환불 요청은 그 레슨에 지정된 소속 학원 업주가 받는다(FR-098b(환불 요청 경로)). 그러려면 개인 레슨에 소속 학원을 하나 지정해야 하고, 업주는 적어도 환불 요청이 들어온 개인 레슨의 결제액·환불 규정은 보게 된다. 그 밖의 가시성은 여전히 미정이다.
5b. **개인 레슨의 플랫폼 수수료율** — 미정. 학원 수수료 5%는 학원 경유 거래의 값이라 개인 레슨에 그대로 쓸 근거가 없다. 결제 경로를 만들기 전에 정해야 한다.
5c. **원천징수** — 프리랜서에게 지급하는 이상 사업소득 원천징수가 따라붙는다. 세율과 처리 주체는 세무 확인 대상이며 이 spec 은 내역에 구분 표기할 것만 정한다(FR-134(플랫폼 내 정산 조회)).
6. **플랫폼 수수료 면제** — 학원 입점일부터 1년, 이후 5%(2026-09-25 사용자 결정. 이전: 8%, 첫 6개월).
7. **유료 API 도입** — 결제대행사를 제외하고는 무료·오픈 수단만 쓴다. 예외가 필요하면 사유를 먼저 남긴다(`payment-method-policy.md` 무료 API 우선 원칙).
8. **시각 처리** — 저장은 시간대를 포함한 형태로, 표시는 한국 시각으로 변환한다. 대기 마감(FR-108(대기 마감)) 판정의 기준이 된다.
9. **금액 처리** — 원 단위 정수만 쓰고 부동소수를 쓰지 않는다. 비율은 만분율(basis point) 정수다. 이미 구현된 환불 계산이 이 규칙을 따른다.
10. **개인 레슨** — 정원 1명인 수업으로 다루되, **정산 경로는 학원 수업과 분리한다**(FR-132(정산 조정)). 학원을 거치지 않는 강사 직접 상품이기 때문이다.
11. **한 사람 여러 역할** — 강사가 다른 학원에서 수강생일 수 있다. 역할은 배타적이지 않다.
12. **대학생 혜택의 "최소 1회"** — 대학생 할인은 최초 첫 결제 1회뿐이다. 2026-09-25 에 첫 달 무료를 첫 결제 50% 할인으로 바꿨다.
13. **AI 추천 응답 지연 한계** — 지정 시간 안에 못 끝내면 필터 검색으로 대체한다(FR-041(추천 시간 초과 대체)). 구체적 한계값은 구현 단계에서 측정해 정한다.
14. **자동 추출 정확도 목표** — 미정. 검토 단계가 필수라 오인식이 사용자에게 바로 노출되지는 않는다(`admin-input-policy.md` 오픈 이슈).
15. **S0 장비** — 개발 노트북 1대(GPU 8GB·WSL 메모리 15GB, 실측). 서버·클라우드 GPU 없이 시작한다(`docs/kdance-beta-infra.html` 의 "B+C 먼저" 방침과 같다). *(2026-09-24)*
16. **"동시 사용자 10명"의 뜻** — 10명이 **같은 순간에** 판단형 질문을 보내는 최악의 경우로 판정한다. 실제 사용에서는 이보다 느슨하다. 시험자 1명이 10명분 요청을 자동으로 발생시킨다. *(2026-09-24)*
17. **사용량 한도 수치** — FR-222(모델 사용량 한도) 의 사용자당 한도는 S0 에서 시험을 막지 않도록 넉넉히 두고(시험자 1명), 값은 운영자가 바꿀 수 있게 한다. 구체 값은 S1 전에 정한다. *(2026-09-24)*
18. **결제 기한 기본값** — FR-285(결제 기한) 의 기한은 다음을 기본값으로 둔다: 카드 일시불·간편 계좌이체는 결제 창을 연 뒤 15분, 가상계좌는 발급 뒤 24시간과 수업 시작 1시간 전 중 이른 쪽. 수업 직전에 입금 확인이 늦어 자리를 잃는 일을 줄이려고 수업 시작 1시간 전에 닫는다. 값은 운영하면서 바꿀 수 있게 설정으로 둔다. *(2026-09-25)*

## Dependencies

### 기존 산출물에 의존

- **기술 스택 버전** — 정의서 「11. 기술 스택 고정표」가 단일 진실 원천. 이 spec 은 버전을 정하지 않는다.
- **환불 비율표 구조** — 이미 구현된 학원별 비율표(만분율 배열)가 있다. 2026-09-25 에 환불이 학원 처리 방식으로 바뀌어 요구사항에서는 빠졌다. **폐기하기로 했다**(Q11(환불 방식 변경의 뒤처리) ② 2026-09-25 확정). 업주 화면의 계산 보조로도 남기지 않는다.
- **취소·환불 경로** — 이미 구현된 계산·오케스트레이션·감사 로그를 재사용한다. 결제 **생성** 경로가 붙으면 앞뒤가 이어진다.
- **정책 문서** — `pricing-policy.md`(차액 부담) · `payment-method-policy.md`(결제 경로) · `genre-taxonomy-policy.md`(장르 4종) · `admin-input-policy.md`(자동 등록) · `distribution-policy.md`(배포 채널).

## 해결된 질문

초안에서 열어 둔 질문 3건 — Q1~Q3(대학생 인증 수단·정원 기준·강사 정산 범위) — 은 모두 답을 받았다. 2026-09-25 역할별 재분석과 환불 방식 변경·카드 결제 허용에서 새로 생긴 질문 10건 — Q4~Q13(개인정보 수집 방식 ~ 구독 판매 주체·요금) — 은 아래 「재분석이 남긴 질문」에 있다.

| 질문 | 확정 | 반영 |
|---|---|---|
| **Q1(대학생 인증 수단)** | **학교 이메일(.ac.kr) 도메인 인증 단독.** QR 현장 인증은 채택하지 않는다 | FR-006~FR-006d |
| **Q2(정원 기준)** | **리드/팔로우 역할 기준.** 성별은 정원 판정에 쓰지 않는다 | FR-092~FR-092d |
| **Q3(강사 정산 범위)** | 프리랜서. 급여 없음. 수업 기간 종료 기준 3단계 정산, 강사 전용 계좌 지급 | FR-127~FR-135e |

### Q1(대학생 인증 수단) 확정이 남긴 숙제

이메일 도메인 인증은 **재학 여부를 보장하지 않는다.** 졸업생 계정이 살아 있으면 그대로
통과한다. 인증 수단이 약한 만큼 **사후 통제가 그만큼 중요해졌다.**

- FR-007(허위 인증 시 혜택 회수·정상가 재청구)이 형식적 조항이 아니라 실제로 동작해야 한다
- FR-006b(같은 이메일로 여러 계정 혜택 수령 차단)를 새로 넣었다
- FR-006d(학원이 혜택 사용 현황 조회)를 새로 넣었다 — 차액을 부담하는 쪽이 이상 징후를 볼 수 있어야 한다

혜택 남용이 실제로 관측되면 그때 인증 수단을 강화한다. 지금 단계에서 미리 만들지 않는다.

### 아직 정해지지 않은 것 (질문이 아니라 전제)

답이 없어도 진행에 막힘이 없어 전제로만 기록한 항목이다.
